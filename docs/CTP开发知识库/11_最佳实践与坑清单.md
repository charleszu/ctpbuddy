## A. 线程模型与 API 生命周期

**A-01 API 与 SPI 分属不同线程，Req* 可多线程并发调用**
- 现象：担心多线程调用 `Req*` 是否安全；在 SPI 回调里做耗时业务后，行情/回报整体变慢甚至断线。
- 原因：API 调用线程与 SPI 回调线程是不同线程；`Req*` 可被多个线程同时调用（与平台无关）。但 API 底层是“异步单底线程”架构：请求从缓存读出、经 socket 发出，socket 读写与 SPI 回调由同一个底层线程负责，所以 SPI 内的阻塞会直接阻塞收发。
- 处理：SPI 回调里只做“拷贝数据 → 入队 → 立即返回”，业务逻辑放到自己的业务线程（工程建议：每个 SPI 事件按到达顺序入同一个 FIFO 队列，由单线程消费，保证回报顺序不被打乱）。

**A-02 禁止在 SPI 回调线程内调用 Release**
- 现象：在 `OnFrontDisconnected` 等回调里调用 `Release()`，程序崩溃或死锁。
- 原因：释放动作要等待底层线程结束，而当前正处在底层线程的回调中，形成自我等待。低版本 API 在频繁断连时本身也有极低概率崩溃（6.3.19 起已修复）。
- 处理：需要释放 API 时，在别的线程中执行；创建与释放 API 实例最好在同一个线程；非交易时段释放、开盘前重建。若只是想“重新登录”，不必释放：登出→等待自动重连→重新认证登录，复用同一 API 实例。

**A-03 释放顺序：先摘 SPI，再 Release，再删 SPI**
- 现象：退出程序时偶发死机。
- 原因：Release 过程中底层线程仍可能回调已销毁的 SPI。
- 处理：固定顺序 `RegisterSpi(NULL)` → `Release()` → 指针置空 → `delete` SPI。

**A-04 初始化顺序必须规范**
- 现象：收不到任何回调；或收到回调但订阅无效。
- 原因：`RegisterSpi` 必须在 `Init()` 之前；`Init()` 必须在 `RegisterFront`、`SubscribePrivateTopic`、`SubscribePublicTopic` 之后；`Init()` 之后底层才启动内部读写线程并开始连接。
- 处理：固定序列：创建 SPI 实例 → `CreateFtdcTraderApi(流文件目录)` → `RegisterSpi` → `RegisterFront`（可多个，或 `RegisterNameServer`）→ `SubscribePublicTopic` → `SubscribePrivateTopic` → `Init()` → 在 `OnFrontConnected` 中认证/登录 → `Join()`。

**A-05 Join() 会阻塞调用线程**
- 现象：主线程卡在 `Join()`，后续代码不执行；或用 sleep 代替 Join 时，业务在连接建立之前就往下走。
- 原因：`Join()` 的作用就是阻塞等待内部线程结束，内部线程只有 `Release` 后才会结束。
- 处理：把 `Join()` 放在主线程最后；若用 sleep/信号量代替，必须自行用“已连接/已登录”状态门控业务推进（工程建议）。

**A-06 流文件目录不可共用**
- 现象：多账号或多实例运行时，一个账号收到回报，另一个收不到；重启后数据流不连续。
- 原因：流文件（`.con`）在 API 初始化时本地生成，记录各类报文当日计数以供续传。多个实例、或 TradeApi 与 MdApi 的两个动态库放在同一目录，会互相覆盖流文件。
- 处理：`CreateFtdcTraderApi` / `CreateFtdcMdApi` 的第一个参数为每个账号、每个 API 实例指定各自独立的目录（如以账户名建目录）；同一账户每次启动使用相同路径，便于 RESUME 续传，同时避免与其他账户混淆。

**A-07 头文件与动态库版本必须配套**
- 现象：订阅合约却收到退订响应；结构体字段错位；莫名崩溃；一直 4097 或根本无回调。
- 原因：不同版本的 API 不能混用头文件和库文件（接口、结构体字段的新增/修改/删除都会导致二进制不兼容）；头文件 6.3.15 配库 6.3.19 即出现过“订阅却收到退订响应”。CTP 库为标准 8 字节对齐。此外 CTP 要求 API 版本与后台版本一致，版本不对时会不停回调 `OnFrontDisconnected`、输出 `Decrypt handshake data failed`，或毫无反应。
- 处理：同一版本的头文件与库成套使用；启动时打印 `GetApiVersion()`；与期货公司确认生产/仿真前置的版本（资料中已知期货公司生产与 SimNow 均为 v6.3.15_20190220，评测可用 6.3.13 或 6.3.16，小版本号不影响评测）。

**A-08 调试器与信号**
- 现象：Linux 下用 GDB 调试时程序莫名停止。
- 原因：CTP API 内部使用 SIGUSR1。
- 处理：GDB 中执行 `handle SIGUSR1 nostop noprint`。

**A-09 OnHeartBeatWarning 不要依赖**
- 现象：想用它做心跳监控却永远收不到。
- 原因：该回调永远不会触发，已对 API 用户屏蔽。
- 处理：自行以“最近收到任何回调/行情的时间”做存活判断（工程建议）；断线靠 `OnFrontDisconnected`。

**A-10 回调函数与请求函数名一一对应**
- 现象：重写了回调但不触发。
- 原因：请求函数与回调函数名存在对应关系，如 `ReqUserLogin` ↔ `OnRspUserLogin`；参数签名必须与基类一致才算重写。
- 处理：继承对应 Spi 类并严格按基类签名重写；Python 等封装中注意回调参数类型。

## B. 连接、重连与状态恢复

**B-01 断线后 API 会自动重连，重连后必须重新认证、登录**
- 现象：断线重连后，下单/查询失败，提示未登录或未认证。
- 原因：`OnFrontDisconnected` 之后 API 自动重新连接（自动重连地址可能是原注册地址，也可能是系统支持的其他可用地址）；6.7.9 及以后版本自动重连间隔固定为 1 秒。重连成功仅回调 `OnFrontConnected`，会话状态并不保留。
- 处理：在 `OnFrontConnected` 里（每次，不只是第一次）执行 认证 → 登录；登录成功后再做“状态恢复”（见 B-04~B-07）。客户端无需自己做 TCP 级重连逻辑。

**B-02 断连原因码 nReason 速查，4097 并不总是网络抖动**
- 现象：反复打印 4097，程序“无限重连”仍无法登录。
- 原因：`nReason` 取值：0x1001(4097) 网络读失败；0x1002(4098) 网络写失败；0x2001(8193) 接收心跳超时（前置约每 53 秒心跳，API 超过 120 秒未收到任何数据即断）；0x2002(8194) 发送心跳失败（API 每 15 秒心跳，超 40 秒无发送即断）；0x2003(8195) 收到不能识别的错误报文。持续 4097 循环的首要成因是 API 版本与后台不匹配，重连无用；其次是仿真平台用户多导致前置拥堵、7×24 地址不稳定；再次是前置连接数流控把连接主动断开（见 H 组）。
- 处理：排查顺序：①核对 `GetApiVersion()` 与后台版本；②用 telnet 检查前置地址是否可达；③切换其他前置地址（仿真有多套）；④排除连接数流控；⑤仍不行联系期货公司。不要把 4097 一律当网络抖动而无限快速重试（工程建议：退避重连）。

**B-03 前置连接数流控与“立刻重连”会互相放大**
- 现象：一连接前置就被断开，重连后又被立即踢开，循环往复。
- 原因：前置对每秒允许的 API 连接请求数设有上限（如配置 20，则 1 秒内最多 20 个会话建立连接），超限时前置主动断开并回调 `OnFrontDisconnected`；该流控按前置（即不同 IP 地址）分别配置。
- 处理：先排除版本问题；对多个实例的启动错开时间（工程建议）；同一套前置触发流控时换另一套前置地址；不要在被踢后做高频重连。

**B-04 登录后的数据同步目标：持仓准确 + 本地订单准确**
- 现象：重启程序后，本地订单状态与柜台不一致（未成交变成交、其他终端有新报单），持仓对不上。
- 原因：程序关闭期间订单状态可能已变化，账户也可能在其他终端报单、成交。持仓只需向柜台查询即可覆盖；订单的恢复则取决于私有流订阅模式。
- 处理：登录成功后先完成“同步阶段”，同步完成之前禁止接收新的报单或撤单请求（工程建议：以状态位 `Synced` 门控）。

**B-05 私有流三种订阅模式的语义与选择**
- 现象：登录后把上次的下单结果重推一遍；或者漏掉登出期间的成交。
- 原因：`THOST_TERT_RESTART` 从本交易日开始重传（重演当日全部回报，登录后重推旧单就是它造成的）；`THOST_TERT_RESUME`（默认）从上次收到的位置续传，依赖本地流文件确定续传点；`THOST_TERT_QUICK` 只传送登录之后的内容，不追溯历史。登录前不同模式的取舍：QUICK 靠查询补全，开发成本低；RESUME 靠历史回报增量补全，数据一致性更好但对本地订单数据准确度要求高；对本地数据不自信可改用 RESTART 重演当日全部流水。
- 处理：QUICK 模式流程：从本地缓存恢复今日订单 → 订阅 QUICK → 认证并登录 → 查询今日全部订单 `ReqQryOrder`、再查询今日全部成交 `ReqQryTrade`、查询持仓 `ReqQryInvestorPosition` → 按订单号/报单引用等唯一标识去重融合 → 同步完成。简化做法是只维护未结束的订单（已结束订单的影响已体现在持仓中）。RESUME 模式流程：恢复本地订单 → 订阅 RESUME → 登录 → 按顺序处理登出后的历史回报，同时把其他终端的订单也存入本地 → 之后继续接收实时回报。两种模式都应以查询接口作兜底。

**B-06 QUICK 模式的注意点与缺陷**
- 现象：查询回来的订单只有最终状态，看不到中间过程；融合期间来了新报单，状态混乱。
- 原因：查询得到的订单是当前最新状态，不含中间状态；同步完成前订单与持仓数据不完整。
- 处理：先查订单并融合完毕，再查成交，确保成交都有对应订单；可直接用查询得到的持仓覆盖本地持仓；同步期间禁止新报单/撤单。

**B-07 RESUME 模式的注意点与缺陷**
- 现象：不知道历史回报何时推送完毕，无法判断“同步完成”；成交回报先于订单回报，找不到订单；同一回报重复到达。
- 原因：历史回报推送结束时没有“推送结束”的通知（不像查询响应有 `bIsLast`）；历史回报按历史实际发生顺序推送，乱序处理会出错；后台可能重复推送历史回报（几率不大）；本地订单数据此前若有缺失，RESUME 无法再发现。
- 处理：按到达顺序处理历史回报；用唯一标识去重（成交回报用 `ExchangeID + TradeID`，并配合 `Direction`，见 E 组）；用“登录后 X 秒内为同步阶段”作为不完美的判断办法（工程建议：X 取值需结合订单量测试）；同一账户必须使用相同的流文件路径；理论上可用遗漏的回报更新持仓，但仍建议登录后查询持仓兜底。

**B-08 TERT_RESTART 会重推旧单**
- 现象：每次登录都收到今天所有旧回报，误以为是新单。
- 原因：RESTART 的定义就是从本交易日开始重传。
- 处理：不需要重演时选 QUICK 或 RESUME；若用 RESTART，所有回报处理必须幂等（按 OrderSysID / TradeID 去重）。

**B-09 行情断线不回补，要自己做容灾**
- 现象：断线期间行情丢失，K 线出现缺口。
- 原因：平台不提供行情回补；无历史行情接口。
- 处理：程序化终端可通过多路连接降低断线风险，或托管到策略服务器；重连后以最新快照为准继续合成，缺口用外部历史数据补（工程建议）。

**B-10 多会话：同一账号可多处登录，回报要按会话过滤**
- 现象：多个实例登录同一账号后，回报里混有别的会话的单子。
- 原因：同一投资者账号可创建多个 TradeApi 对象同时登录；一个会话由 `FrontID + SessionID` 共同确定；同一用户在线会话数有上限（后台可配置，默认 6；6.6.3+ 按用户维度计）。
- 处理：登录后保存本会话的 `FrontID`、`SessionID`；用它们过滤 `OnRtnOrder` 中属于本会话的单子，再用 `FrontID+SessionID+OrderRef` 映射到 `ExchangeID+OrderSysID`，以后者过滤 `OnRtnTrade`（该办法仅对本会话内报的单有效）。超限时在 `OnRspUserLogin` 收到“CTP:用户在线会话超出上限”，该上限按 `UserID` 计，登录成功在线即算 1 个会话，用其他客户端登录也计入。

## C. 认证与登录

**C-01 自开发程序必须先 ReqAuthenticate，再 ReqUserLogin**
- 现象：登录被拒，提示未认证（“CTP:客户端认证失败”/未认证类错误）。
- 原因：穿透式监管要求：监控中心采集所有通过期货公司入场的客户终端信息；自开发程序须在 `ReqUserLogin` 之前先调用 `ReqAuthenticate`。使用快期、博易等厂商客户端的投资者无需做任何事，因为厂商已备案。
- 处理：在 `OnFrontConnected` 回调内发起 `ReqAuthenticate`；在 `OnRspAuthenticate` 中判断 `ErrorID == 0` 再调用 `ReqUserLogin`，否则打印错误、不发登录。

**C-02 认证字段是 AppID + AuthCode，UserProductInfo 已废弃**
- 现象：认证一直失败，但 `UserProductInfo` 填得没错。
- 原因：旧版本通过 `UserProductInfo` 与 `AuthCode` 绑定验证，现在 `UserProductInfo` 废弃，改为 `AppID`。`AppID` 由客户自己命名（监控中心给出命名规范，如 `client_abcdf_1.0.0`），`AuthCode` 由期货公司发放，两者一一对应。
- 处理：向期货公司申请时提交客户号、软件名称、自命名的 AppID、连接方式（直连类型终端）；认证请求中填写 `BrokerID`、`UserID`、`AppID`、`AuthCode`。

**C-03 终端信息采集与加密：不是“扫描硬盘文件”**
- 现象：担心程序被采集隐私。
- 原因：采集内容为 IP、MAC、操作系统版本、硬盘序列号、系统分区等；API 底层已用监控中心下发的公钥加密，只有监控中心持有私钥，柜台厂商、期货公司、交易所都看不到明文。
- 处理：无需额外处理；不要自行去掉或绕过采集库（工程建议）。

**C-04 四种接入模式：直连、中继、多对多、多对一**
- 现象：中继服务器或多终端场景下，不知道该由谁认证、谁上报。
- 原因：直连模式下终端连前置，先 `ReqAuthenticate` 再 `ReqUserLogin`，API 自动采集终端信息并上报，全程一个 API 实例。中继模式下终端用采集库 `CTP_GetSystemInfo` 采集 `ClientSystemInfo`，连同 AppID 一起交给中继服务器，由中继服务器上报：“多对多”（每终端一个 API 实例、终端断开即销毁）用 `RegisterUserSystemInfo`（终端认证成功后、用户登录前调用）；“一对多”（只有一个 API 实例，操作员登录后代客下单、客户无需给密码）用 `SubmitUserSystemInfo`（操作员登录后可多次调用）。多账户回报靠 `InvestorID` 区分。
- 处理：上报接口返回 0 表示成功，非 0 表示 CTP 对该终端认证失败，此时应断开与该终端的连接（中继服务器对终端的认证是间接通过上报接口完成的）；终端信息是可能含 `'\0'` 的字符数组，必须 `memcpy`，不可用 `strcpy/strncpy`；Python、Java 用字节/字符数组而非字符串。

**C-05 登录所需的六项信息**
- 现象：不知道登录要填什么。
- 原因：`BrokerID`（期货公司编码，四位）、交易前置/行情前置地址（同一期货公司同一套系统对所有客户相同）、`InvestorID`（普通投资者无需关心 `UserID`、`InvestUnitID`）、`Password`（开户首次登录必须修改密码）、`AppID`、`AuthCode`。
- 处理：向开户的期货公司索取；首次登录先改密码；仿真环境因暂无穿透式柜台，可能不需要 AppID/AuthCode（以实际前置为准）。

**C-06 登录响应里的 FrontID / SessionID / MaxOrderRef 要保存**
- 现象：后续报单、撤单、回报过滤找不到会话信息。
- 原因：登录响应给出前置编号、会话编号和最大报单引用；这三项在本次连接中不变，重连/重登后改变。
- 处理：`OnRspUserLogin` 成功时保存，并以 `MaxOrderRef` 初始化本地 OrderRef 计数（见 D 组）；重连后重新保存。

**C-07 交易日首次登录必须确认结算单**
- 现象：登录成功后报单/撤单被拒，提示结算单未确认。
- 原因：每天首次登录成功后必须先 `ReqQrySettlementInfo`（并确认状态）、`ReqSettlementInfoConfirm` 确认结算单，才能发报单、撤单、预埋单；当天已确认的会话再次登录可直接交易。
- 处理：登录后查询确认状态（`ReqQrySettlementInfoConfirm`），未确认则展示并确认，详见 K 组。

**C-08 初始化后一直没有 OnFrontConnected**
- 现象：`Init()` 之后没有任何回调。
- 原因：地址不通、API 版本与后台不一致、用成交前置地址连行情（或相反）、协议前缀写错。
- 处理：先 telnet 前置地址；核对 API 版本；行情与交易地址分开；地址以 `tcp://` 开头（SSL 用 `ssl://`、IPv6 用 `tcp6://`，代理形如 `socks5://user:pass@host:port`）；`RegisterFront` 可多次注册形成地址池，断线时自动择优。

## D. OrderRef 与报单标识管理

**D-01 OrderRef 必须在同一会话内严格递增**
- 现象：报单被拒，提示“重复的报单”。
- 原因：`FrontID + SessionID + OrderRef` 是会话内唯一主键，后台只要求该字段单调递增，不自增（或多线程并发导致乱序）会被判重复。`FrontID+SessionID` 变更后 `MaxOrderRef` 重置。
- 处理：登录后以 `MaxOrderRef + 1` 起始，用线程安全的原子计数器生成（工程建议：计数器加锁或使用原子自增，多线程报单时尤其注意）；不填 OrderRef 时 Thost 自动分配，但回报解析时需保持格式（是否右对齐）一致。

**D-02 OrderRef 是有符号 32 位整数（读作字符串、写作整数）**
- 现象：计数到很大后报单失败。
- 原因：超过 ±2147483647 范围可能被服务器判定为 0，从而不符合递增规则；部分期货公司柜台使用 64 位，但应按 32 位对待。
- 处理：每次登录会话 OrderRef 重新从 `MaxOrderRef` 起计，天然不会溢出；不要把时间戳等大数塞进 OrderRef。

**D-03 报单的四组标识各有用途**
- 现象：不知道用哪个字段关联回报、撤单、成交。
- 原因：①`(FrontID, SessionID, OrderRef)` 用户自设，会话内唯一，在收到下单响应之前即可用其撤单；②`(BrokerID, BrokerOrderSeq)` 由 Thost 维护的连续序号，期货公司据此查询对账；③`(ExchangeID, TraderID, OrderLocalID)` 由交易席位生成，`TraderID` 是交易所交易员代码（不是成交编号 TradeID），`OrderLocalID` 为席位内序号，一般投资者可忽略；④`(ExchangeID, OrderSysID)` 由交易所生成，全交易所唯一、跨交易所不唯一，区分交易所必须带 `ExchangeID`。
- 处理：本地订单表同时记录第①组与第④组；`OnRtnTrade` 无 FrontID/SessionID，用第④组（或第③组）反查订单。

**D-04 OrderSysID 在第 1 次回报中为空，且右对齐带空格**
- 现象：用第 1 个 `OnRtnOrder` 里的 OrderSysID 撤单失败；撤单提示找不到报单。
- 原因：报单第一次到达 CTP、风险检查通过后返回的第 1 个回报，交易所编号尚未产生，OrderSysID 为空；之后为数字字符串且右对齐（如 20 字节中前面有空格），不同交易所位数不齐。
- 处理：第 1 次回报阶段只能用 `FrontID+SessionID+OrderRef` 定位；拿到 OrderSysID 后原样保存、原样用于撤单，不要截断或去空格；比较时统一用同一种格式（如 trim 后比较，但发送时用原值）（工程建议）。

**D-05 RequestID 不能用来区分会话**
- 现象：想用 RequestID 关联回报。
- 原因：CTP 允许 RequestID 重复，无法区分同账户不同会话的下单；回报结构中的 `RequestID` 也不等同于函数参数 `nRequestID`。
- 处理：以 D-03 的标识关联；`nRequestID` 仅用于匹配 `OnRsp*` 响应（工程建议：自增并保存请求上下文）。

**D-06 UserID 必须填写，否则收不到错单通知**
- 现象：报单被拒，却收不到 `OnErrRtnOrderInsert`（撤单同理收不到 `OnErrRtnOrderAction`）。
- 原因：CTP 交易核心收到报单时并不校验 UserID，但拒单后向该账户各 API 会话推送错单通知时，是按报单中的 UserID 推送的。
- 处理：报单、撤单一律同时填写有效的 `UserID` 与 `InvestorID`（普通投资者二者相同；操作员代客下单时 `UserID`=操作员、`InvestorID`=客户）。

**D-07 InvestUnitID 不要当策略标识用**
- 现象：想借 `InvestUnitID` 传策略编号。
- 原因：该字段在回报、成交中回显，不像 OrderRef 要求必须是整数，且允许重复，所以有人借以携带策略号；但这是钻系统空子，且该字段原为子账号分组设计，该功能被监管判为违规后已废弃。
- 处理：不依赖它；策略归属请在本地用 OrderRef 号段或本地映射表管理（工程建议）。

**D-08 多策略、多连接下的 OrderRef 方案**
- 现象：多个策略/连接并发报单，难以归属回报。
- 原因：方案一：用 `FrontID+SessionID+OrderRef` 维护本地订单，第 2 个 `OnRtnOrder` 回来后填入 OrderSysID，之后用 `ExchangeID+OrderSysID` 维护；方案二：本地维护交易日内跨连接单调递增的 OrderRef，无需关心 FrontID/SessionID，但多策略多连接间 OrderRef 需互相同步。
- 处理：单进程单连接推荐方案一；多连接推荐每连接独立会话并保存各自 FrontID/SessionID（工程建议）。

**D-09 BrokerID 会重复**
- 现象：以 BrokerID 作为期货公司的唯一键，数据串了。
- 原因：BrokerID 由期货公司自行设置，不同期货公司的 BrokerID 完全可能相同（例如多家公司都是 8888）。
- 处理：多公司场景下以“BrokerID + 前置地址/账户”共同标识（工程建议）；不要以 BrokerID 单独作主键。

**D-10 报单必填与固定值**
- 现象：报单被 CTP 拒绝，字段校验类错误。
- 原因：必填项：`BrokerID`、`InvestorID`（及建议的 `UserID`）、`ExchangeID`（仿真平台必填，生产逐步要求，应一律填写，且全部大写：CFFEX/CZCE/DCE/INE/SHFE）、`InstrumentID`、`OrderPriceType`、`Direction`、`LimitPrice`（仅限价单需要，且须为最小变动价位整数倍，否则被拒）、`VolumeTotalOriginal`（必须大于 0）、`CombOffsetFlag`、`CombHedgeFlag`（数组类型，目前只填第 [0] 位）、`ContingentCondition`、`TimeCondition`、`VolumeCondition`、`ForceCloseReason`。固定值：`VolumeCondition=AV`、`MinVolume=1`、`ForceCloseReason=NotForceClose`、`IsAutoSuspend=0`、`UserForceClose=0`。
- 处理：把报单封装为统一的构造函数，一次性填好固定值，业务层只传合约、方向、开平、价格、数量；价格在发送前按 `PriceTick` 取整（工程建议）。

## E. 报单回报时序

**E-01 成交判断以 OnRtnTrade 为准，不以 OnRtnOrder 为准**
- 现象：用 `OnRtnOrder` 的“全部成交”状态立即发出平仓指令，极小概率被拒（平仓失败）。
- 原因：报单回报与成交回报之间存在理论上的微小时间差，而 CTP 后台是以成交回报为准更新持仓状态的；以报单回报判成交并立刻平仓时，平仓指令到达时持仓状态可能尚未更新。
- 处理：成交数量、价格、是否成交一律以 `OnRtnTrade` 为准；持仓与资金只由成交回报驱动更新；`OnRtnOrder` 只用于状态变化、冻结与解冻（见 G 组）。

**E-02 OnRtnOrder 与 OnRtnTrade 的先后顺序不固定（Late Fill）**
- 现象：收到“全部成交/已撤单”的 `OnRtnOrder` 就把订单从内存删除，随后到达的 `OnRtnTrade` 找不到订单。
- 原因：订单完全成交（或刚撤单时恰好发生一笔成交）时，最后一笔 `OnRtnTrade` 与最后一个 `OnRtnOrder` 并无严格先后，两种顺序都会出现：情况 1：未知态 OnRtnOrder → … → 终态 OnRtnOrder → OnRtnTrade（可能不止一笔）；情况 2：未知态 OnRtnOrder → … → OnRtnTrade → 终态 OnRtnOrder。
- 处理：为每个订单维护两个累计量：A=由 `OnRtnOrder.VolumeTraded` 得到的总成交量，B=累加各 `OnRtnTrade.Volume`；仅当状态为终态（AllTraded/Canceled）且 A==B 时才认为订单真正结束，否则继续等待后续回报。对不确定的行为留出容错空间。（官方资料口径：对同一场景给定交易所报单回报顺序时，CTP 给 API 的回调顺序固定，`OnRtnTrade` 总在新状态的 `OnRtnOrder` 之后；上述容错是应对不同交易所/场景下的实际差异，属于工程建议。）

**E-03 重复的前态回报：同一报单会收到相同状态的多条 OnRtnOrder**
- 现象：一个报单先收到“已报”，撤单后又收到一次“未成交”再收到“已撤销”；按条数统计成交/状态会翻倍。
- 原因：投资者每发出 1 个操作，会收到 2 条回报：CTP 应答一下，交易所再应答一下；交易所每来一次状态迁移，CTP 先补推一条“前状态”的 `OnRtnOrder`，再推“新状态”的 `OnRtnOrder`。
- 处理：状态机按 `OrderStatus`（结合 `VolumeTraded`、`OrderSubmitStatus`）推进，对同状态重复回报做去重/幂等处理，不要当成新事件；成交量不要用回报条数累计，用 `OnRtnTrade` 累计。

**E-04 报单后的完整回调路径**
- 现象：不知道什么时候算“报单成功”，什么时候算被拒。
- 原因：交易指令异步分阶段提交，但拒单回调会随发生层级、版本和环境变化。CTP 参数/资金/持仓校验、交易所拒绝、接受和成交的具体回调组合，需按对应版本官方回调规则及接入环境核验；不能仅凭旧 FAQ、当前项目实现或单一实测样本断言。
- 处理：不要等 `OnRspOrderInsert` 作为成功信号；以 `OnRtnOrder` 的状态推进为准；被动撤单的识别见 E-06。

**E-05 CTP 层拒单与交易所层拒单走不同的回调**
- 现象：只挂了 `OnRspOrderInsert`，漏掉了一部分拒单。
- 原因：不同资料对 CTP 层、交易所层拒绝的回调面存在年代/场景差异。官方 HTML 的报单回调规则需结合具体场景阅读；项目 `notes/09` 的分层是实现对齐记录，不足以证明所有真实柜台普遍如此。
- 处理：同时处理 `OnRspOrderInsert`、`OnErrRtnOrderInsert`、`OnRtnOrder` 三条路径；任一路径的拒单都要触发本地冻结的解冻；`OnRspOrderInsert` 的指针参数先判空。

**E-06 交易所拒单在 CTP 中用“已撤单”表示**
- 现象：订单显示已撤单，却不是自己撤的。
- 原因：CTP 没有表示“被拒单”的报单状态，被交易所拒绝的单以“已撤单（Canceled）”表示，且 `OnRtnOrder` 本身不带错误码，原因在 `StatusMsg`（以数字错误码开头，由交易所原因转发）。
- 处理：以“Canceled + OrderSubmitStatus=InsertRejected(4)”判断为被交易所拒单；`StatusMsg` 原样记录日志；可用 OrderSysID 是否为空、`ActiveUserID`、OrderSubmitStatus 区分自撤与被拒（见 F-03）。

**E-07 OrderStatus 与 OrderSubmitStatus 的取值**
- 现象：不知道哪些状态是终态、哪些暂不使用。
- 原因：OrderStatus：'0' 全部成交；'1' 部分成交还在队列中；'2' 部分成交不在队列中（暂不使用）；'3' 未成交还在队列中；'4' 未成交不在队列中（暂不使用）；'5' 撤单；'a' 未知（CTP 已收单并发给交易所，未收到确认，含废单）；'b' 尚未触发、'c' 已触发（条件单保留，暂不使用）。OrderSubmitStatus：'0' 报单已提交；'1' 撤单已提交；'2' 修改已提交（暂不使用）；'3' 已经接受；'4' 报单已被拒绝；'5' 撤单已被拒绝；'6' 改单已被拒绝（暂不使用）。终态：AllTraded、Canceled、NoTradeNotQueueing、PartTradedNotQueueing，“部成部撤”的终态就是 Canceled。
- 处理：终态判断至少包含 '0' 与 '5'（并按 E-02 配合 A==B）；“不在队列中”是上期所自动挂起标志的历史产物，现在 IsAutoSuspend 恒为 0，永不挂起；见《15_枚举常量速查表》。

**E-08 成交回报的唯一键与去重**
- 现象：同一笔成交被重复处理，持仓翻倍；或误把对手方成交当成重复。
- 原因：`TradeID` 是交易所对每笔成交的编号，除郑商所外，互为对手方的两笔成交编号相同，因此成交的唯一确定需要 `ExchangeID + TradeID + Direction`。此外，`TradeID` 每个交易日可能重复编号，因此跨日持久化的数据（如持仓明细）需要再加 `OpenDate`。
- 处理：成交回报按 `(ExchangeID, TradeID, Direction)` 去重，重复者直接丢弃；持仓明细键用 `OpenDate + TradeID`（可能自成交时再加 `Direction`）；RESUME/RESTART 重推历史回报时尤其依赖这一去重。

**E-09 OnRtnTrade 的数量是单笔，不是累计**
- 现象：4 手单分 1+3 两笔成交，只记了一笔。
- 原因：`OnRtnTrade.Volume` 只是本笔成交数量；总成交量要看 `OnRtnOrder.VolumeTraded`；组合合约订单按腿至少推送 2 次 `OnRtnTrade`。
- 处理：成交累计用求和；组合单按腿分别入账。

**E-10 成交开平标志可能不同于报单开平标志**
- 现象：报单是平今/平昨，成交回报里变成“平仓”，本地按开平标志更新今昨仓时错位。
- 原因：上期所和能源中心成交与报单的开平方向相同；大商所、郑商所、中金所对平仓一律返回 `THOST_FTDC_OF_Close('1')`。而 SimNow 却按上期所规则随报单返回平今/平昨，导致仿真与实盘不一致。
- 处理：持仓更新按“交易所规则”处理：非上期所/能源中心，不区分今昨仓，按“先开先平”扣减；不要依赖成交回报里的平今/平昨标志去判断；仿真上通过的逻辑务必在实盘环境再验证。

**E-11 成交回报用于更新持仓的字段**
- 现象：不知道该用哪些字段把成交归入持仓。
- 原因：`InstrumentID`、`Direction`、`OffsetFlag` 三个字段可以确定该笔成交应更新哪条持仓；国内持仓需区分多头和空头，上期/能源还需区分今昨仓。成交价是本次成交的价格，数量是本次成交数量。
- 处理：先按 `(合约, 方向, 开平)` 映射到持仓方向（买开→多头；卖开→空头；买平→空头；卖平→多头）再更新。

**E-12 大商所的特殊回报形态**
- 现象：对大商所合约，全部成交后收不到“全部成交”的报单回报，或回报顺序与其他所不同。
- 原因：全部成交后大商所只返回成交回报，不返回全部成交报单回报，由 CTP 自补全部成交报单回报，且不重复前态；大商所只要委托进入报单簿就必返回未成交回报（即使立即成交）。
- 处理：跨交易所使用同一套成交判定时，必须容忍上述差异；用 E-02 的 A==B 方法最稳妥。

**E-13 FAK/FOK 的回报形态随交易所而异**
- 现象：FAK 部分成交后回报条数、顺序与限价单不同；同一套状态机在不同交易所上表现不一致。
- 原因：上期所/能源中心/中金所：先收到“撤单行”再收到成交（每笔成交一行带 Trade）；大商所/广期所：先未成交、再每笔成交一行“部分成交”加 Trade、最后撤单；郑商所：每笔成交前后各有状态行。三所收尾均为交易所主动撤单。（具体序列以官方回调规则文档为准。）
- 处理：对 FAK/FOK 不要假设回报条数；终态以 A==B 和终态状态判断（E-02）；见《05_报单撤单与回报》《08_交易所规则与特殊指令》。

**E-14 报单指令 = 四字段组合**
- 现象：FAK/FOK/市价单被拒或行为与预期不同。
- 原因：指令由 `OrderPriceType`、`TimeCondition`、`VolumeCondition`、`MinVolume` 四字段组合决定：限价单 LimitPrice+GFD+AV；FAK（任意数量）LimitPrice+IOC+AV；FAK（指定最小数量）LimitPrice+IOC+MV+MinVolume（仅上期所/中金所）；FOK LimitPrice+IOC+CV；市价单 AnyPrice+LimitPrice=0+IOC（郑商所/大商所市价用 GFD，中金所撤销型 IOC、转限价型 GFD）。止损/止盈仅大商所（Touch/TouchProfit+StopPrice，触发后另下新报单）。郑商所市价单价格必须填 0，否则被拒，建议所有市价单价格都填 0。上期所生产环境暂不支持市价单；大商所市价内部转涨跌停限价撮合，成交价可能不等于对手价。郑商所期货官方口径只有 FAK。FAK/FOK 不得用于集合竞价。
- 处理：封装“指令类型→四字段”的映射表，并按交易所校验可用性；见《08_交易所规则与特殊指令》。

**E-15 条件单与预埋单的行为差异**
- 现象：预埋单报入后没有任何通知；预埋单触发后的新单找不到对应关系；条件单保留状态 'b'/'c' 不出现。
- 原因：预埋单只能在非交易时间（集合竞价前或节间休息）报入，新交易时段开始时自动触发，触发后转为普通报单/撤单；预埋报单用 `ReqParkedOrderInsert`，只有响应函数 `OnRspParkedOrderInsert`，没有报单回报推送，报入、触发、删除都没有通知，只能靠查询（`ReqQryParkedOrder`）获知，对多处同时登录的业务有影响；用 `ParkedOrderID` 代替 `OrderSysID` 作为预埋单编号，状态 `Status`：NotSend 未触发、Send 已触发、Deleted 已删除；预埋撤单用 `ReqParkedOrderAction`（编号 `ParkedOrderActionID`）；删除用 `ReqRemoveParkedOrder` / `ReqRemoveParkedOrderAction`。预埋报单报入时不检查合法性（可预埋去平没有的持仓），预埋撤单会检查合法性（允许重复撤同一单，撤单字段最好用 `ExchangeID+OrderSysID`，曾发现用 `FrontID+SessionID+OrderRef+InstrumentID` 在仿真环境无法通过检测）。预埋单存储在期货公司机房服务器，使用前应咨询期货公司支持情况；预埋单触发后的新报单 `SessionID` 与 `FrontID` 为 0，OrderRef 由系统生成，且没有字段与触发它的预埋单关联（条件单则通过 `RelativeOrderSysID` 关联）。
- 处理：预埋/条件单只作为盘前准备手段；触发后以查询报单 + 回报重建关联（工程建议）；GTC 过夜挂单不支持。

**E-16 市价单价格与新规则**
- 现象：市价单被郑商所拒绝；上期所市价单行为变化。
- 原因：郑商所市价类报单必须把 `LimitPrice` 填为 0，否则被拒，其他交易所暂无此规定但不排除未来出台；资料记载自 2026 年 7 月 6 日起，上期所和能源中心将在所有合约上支持市价单，届时市价单的 `LimitPrice` 表示“保护价”（可接受的最差成交价），必须在涨跌停板范围内（不能为 0）。
- 处理：封装市价单时按“交易所+日期/版本”分支：郑商所价格填 0；上期所/能源中心在新规生效后填保护价（以交易所公告和期货公司通知为准，不臆断）。

## F. 撤单：并发与失败

**F-01 撤单必须带的字段与两种定位方式**
- 现象：撤单被拒“找不到相应报单”或收不到撤单错误回报。
- 原因：撤单必填 `BrokerID`、`InvestorID`，另填 `UserID`（非必填，但不填会收不到 `OnErrRtnOrderAction`）；定位原始报单有两组序号可选：①`ExchangeID + OrderSysID`（官方推荐；但第 1 次回报中 OrderSysID 为空）；②`FrontID + SessionID + OrderRef`（用这组时还必须填 `InstrumentID`；部分交易所在订单被接收前不支持这种撤单）。第三组 `ExchangeID + TraderID + OrderLocalID` 也可用。`ActionFlag` 只支持 `THOST_FTDC_AF_Delete`（仅撤单）；`OrderActionRef` 用户自设并保持递增，不填由系统代设。
- 处理：封装撤单函数：优先用 `ExchangeID+OrderSysID`；OrderSysID 为空则回退到 `FrontID+SessionID+OrderRef+InstrumentID`；OrderSysID、OrderRef 若右对齐，撤单时必须原样（含空格）填写。

**F-02 “CTP:无此功能”：ActionFlag 只支持撤单**
- 现象：想“改单”或“挂起/激活”，收到“CTP:无此功能”。
- 原因：`ReqOrderAction` 目前只实现撤单，修改、挂起、激活都无此功能；GTC（过夜挂单）不支持，国内交易所不支持过夜挂单，CTP 只提供非交易时段的预埋单。
- 处理：改单用“撤单再报单”实现，注意中间的成交风险（工程建议：撤单确认（终态）后再发新单）。

**F-03 如何区分自己撤的单与被拒的单**
- 现象：收到已撤单回报，不知道是自撤还是被交易所拒单（废单）。
- 原因：自撤的单，`OrderSysID` 非空（进过交易所撮合队列），`ActiveUserID` 为本账户，`OrderSubmitStatus` 为 Accepted('3')；被拒/未进交易所的撤单，OrderSysID 为空，`OrderSubmitStatus` 为 InsertRejected('4')。
- 处理：用上述字段组合判断；业务上被动撤单要触发策略的“重新决策”逻辑。

**F-04 撤单被拒的常见原因**
- 现象：撤单返回错误。
- 原因：①“CTP:报单已全成交或已撤销，不能再撤”：OrderStatus 为 Canceled 或 AllTraded 时不允许再撤，其他状态都可以撤；②“CTP:无此权限”：账号字段没填对；③“CTP:撤单找不到相应报单”：序号没填对；④上期所特殊情形“报单已经全部成交”：单子在交易所已撮合成交但 CTP 尚未收到成交通知，撤单通过了 CTP 检查但被交易所因已成交而拒绝；⑤“CTP:下单频率限制”：报撤单流控。错误码 25（已全成交或已撤销）与 26（找不到相应报单）要区分。
- 处理：撤单失败不要无脑重试：先看本地订单是否已到终态；对上期所的④情况，稍后以成交回报为准；撤单被拒时通常有两个回调（`OnRspOrderAction` 与 `OnErrRtnOrderAction`），撤单拒绝“不需要对本地订单做任何状态变更”，也不要做解冻。

**F-05 撤单并发：同一订单被重复撤单**
- 现象：多个线程/策略对同一订单发出撤单，出现“已撤销，不能再撤”的拒单。
- 原因：撤单请求发出到收到终态回报之间有时间差，期间再次撤单会被拒。
- 处理：（工程建议）本地订单维护“撤单在途”标志，已发撤单的订单不再重复撤；收到撤单被拒时清除该标志；以终态回报关闭订单。

**F-06 撤单与成交并发：撤单时恰好成交**
- 现象：发出撤单，同时有成交，订单结果为“部成部撤”或撤单被拒。
- 原因：撤单与成交在交易所内竞争，先到者先生效；“部成部撤”的终态就是 Canceled，成交量以 `OnRtnTrade` 累计为准。
- 处理：撤单后不要假设订单一定被撤销，要等终态；结束判断仍采用 E-02 的 A==B。

**F-07 批量撤单与撤单数风控需自己实现**
- 现象：想批量撤单或担心撤单次数超限。
- 原因：`ReqBatchOrderAction` 看似批量撤单，但仅支持大商所，且仅做市商客户可用；CTP 内没有撤单数风控。交易所对频繁报撤单有异常交易管理规范。
- 处理：自行实现“遍历未结束订单逐个撤单”；并自行加入撤单计数风控（按合约统计），具体阈值见 N-07（工程建议）。

**F-08 报单与撤单的流控分开计算，按投资者级别**
- 现象：高频撤单时收到“CTP:下单频率限制”。
- 原因：后台对 `ReqOrderInsert` 与 `ReqOrderAction` 每秒允许的最大笔数分开计算；流控按投资者 `InvestorID` 级别，所以多开会话也没用；超限在相应错误回调中返回“CTP:下单频率限制”（错误码 116，勿与 91“CTP：交易所返回的错误”混用）。历史上（早期资料）的口径是每会话每秒约 6 笔、超限排队而不报错，现代柜台是显式拒绝。
- 处理：本地做令牌桶限速（工程建议），报单与撤单各自一桶；确需更高频率，只能分账户。

## G. 本地订单、持仓、资金维护

**G-01 冻结与解冻的时机**
- 现象：重复报平仓单被拒“CTP:平仓量超过持仓量”；可用资金与柜台不一致。
- 原因：报单时就要冻结：买开→多头持仓记录的 `LongFrozen`、`LongFrozenAmount`、`FrozenMargin`、`FrozenCommission` 增加；买平→空头持仓记录的 `LongFrozen`、`LongFrozenAmount`、`FrozenCommission` 增加（平仓没有冻结保证金）；卖开/卖平类似。可平数量：多头持仓 = `Position − ShortFrozen`（空头冻结数量），空头持仓 = `Position − LongFrozen`。冻结持仓数量决定可平手数；冻结资金决定可用资金。
- 处理：发出报单即冻结（工程建议：发出请求时先本地预冻结）；平仓前用“持仓−冻结”判断可平量，避免重复平仓。

**G-02 什么时候解冻**
- 现象：撤单或拒单后，资金/仓位仍被占用。
- 原因：撤单成功（OrderStatus='5'，可能是主动撤单，也可能是被动撤单）→ 订单关闭，须按未成交量 `VolumeTotal` 解冻仓位和资金；`OnRspOrderInsert`（被 CTP 拒单）→ 按报单量解冻；`'a'`/`'3'` 状态表示订单已到 CTP/交易所，无需更新持仓记录；撤单失败的错误回报不需要任何操作。多端登录时，须按 FrontID/SessionID 判断是否本端再解冻。
- 处理：解冻只依据终态/拒单事件；不要在 `OnRtnOrder` 的 '0'/'1' 状态里更新持仓（见 E-01）。

**G-03 成交回报到达时：先解冻、再计算实际**
- 现象：持仓、资金、冻结三者对不上。
- 原因：收到成交回报后，应先减掉原来报单时的仓位/资金冻结，再计算实际持仓和资金。买开成交：更新冻结字段和持仓字段，以及持仓成本、保证金等；卖平成交：`YdPosition` 仍保持原值（它是静态初值）；全部平仓：持仓成本、持仓盈亏、保证金占用直接归 0；部分平仓需按比例更新。
- 处理：成交处理顺序固定：①按成交比例释放冻结；②更新持仓；③更新盈亏、保证金、手续费；④记账。

**G-04 持仓记录的键与今昨仓**
- 现象：同一合约查出多条持仓；上期所持仓行数“多”。
- 原因：持仓记录键值为 `InstrumentID + ExchangeID + BrokerID + InvestorID + PosiDirection + HedgeFlag + PositionDate`。同合约的多空是不同记录；`PositionDate` 为 '1'（今仓）/'2'（昨仓），只有上期所/能源中心才可能有 '2' 的记录（今昨仓拆成两条记录），其他交易所昨仓与今仓在同一条记录里（`YdPosition` 与 `TodayPosition` 并存）。对个人投资者，合约、方向、持仓日期三项基本确定唯一一条持仓。
- 处理：本地持仓表按以上键建立；按行数统计持仓会错，应按字段汇总。

**G-05 YdPosition 是静态初值，不随平昨减少**
- 现象：平掉昨仓后，`YdPosition` 仍然不变，本地以为没平掉。
- 原因：`YdPosition` 是当前交易日开始时的历史仓位，是静态值，不随平昨减少；当前真实昨仓为 `Position − TodayPosition`。
- 处理：判断当前还剩多少昨仓用 `Position − TodayPosition`，不要用 `YdPosition`。

**G-06 持仓查询的返回形态**
- 现象：查不到持仓时程序崩溃；持仓为 0 的行被当成真实持仓；多出一条没报过的组合持仓记录。
- 原因：多条持仓会多次回调，每次一条，用 `bIsLast` 判断结束；没有任何持仓时，API 也会回调，只是 `pInvestorPosition` 指针为空、`bIsLast` 为 true；当日开仓后全部平仓或只是报单未成交，仍可能查到记录，`Position` 为 0；盘后交易所会自动把客户的相同持仓进行组合（组合后只收大单边保证金），所以会多出组合记录，组合包含记录有对应的单边持仓记录；没有开仓均价/持仓均价字段，需自算：开仓均价 = 开仓成本 / 持仓手数，持仓均价 = 持仓成本 / 持仓手数（成本还要考虑合约乘数）。
- 处理：回调中先判空；过滤 `Position==0` 的记录；对组合记录单独处理（见 L 组）；查询参数可以全部不填（全部持仓），但不填不是传 NULL，而应传一个清零的结构体。

**G-07 持仓明细：每笔开仓成交一条记录**
- 现象：不清楚明细何时增减、盈亏怎么算。
- 原因：持仓明细是每笔开仓成交形成的一条记录，有对应平仓时找出原开仓记录更新；明细键为 `InstrumentID + BrokerID + InvestorID + HedgeFlag + Direction + TradeType + OpenDate + TradeID`（常简化为 `OpenDate + TradeID`）。`TradeType`：'0' 普通成交，'4' 组合单生成成交（交易组合单或大商所盘后自动组合的明细为 '4'）；`Volume` 为该笔开仓目前对应的持仓数量，`CloseVolume` 为已平数量（两者实时更新，如开 8 手后平 3 手：Volume=5、CloseVolume=3）。
- 处理：明细按以上键维护；盈亏按明细逐笔计算（见 G-09）；查询持仓明细同样可以全部不填。

**G-08 平仓顺序：先开先平，各所细节不同**
- 现象：平仓盈亏、手续费与本地估算不一致。
- 原因：四个交易所持仓都按“先开先平”；上期所/能源中心报单时自行指定平今/平昨，各自内部先开先平；郑商所先单腿后组合；大商所/广期所/郑商所优先平昨，但当平今手续费有减免时优先平今；中金所持仓系统先开先平、优先平昨，但手续费按“优先平今”的另一套并行持仓系统计算。先开先平与今/昨是两个正交的维度：消耗明细只按开仓时间排序，平今/平昨只决定可以动用哪个年龄段，不是“今仓取最新”。
- 处理：本地持仓模型按交易所规则分别实现；手续费区分平今/平昨费率（即使是大商所也严格区分）；不能统一用平昨费率；与柜台持仓明细对账（见 Q 组）。

**G-09 盈亏口径：昨仓用昨结算价，今仓用开仓价**
- 现象：平仓盈亏与结算单对不上，差在昨仓上。
- 原因：逐日盯市下，平仓盈亏按明细计算：多头明细 `(成交价 − 持仓价) × N × 乘数`；空头明细 `(持仓价 − 成交价) × N × 乘数`；昨仓明细持仓价 = 昨结算价；今仓明细持仓价 = 开仓价（官方字段说明 `CloseProfitByDate` 为 `(closeprice − openprice or preSettlementPrice) × volume × RateMultiple`；`CloseProfitByTrade` 为逐笔平仓盈亏，无论今昨都用平仓价与开仓价之差）。例：昨结 3005、乘数 10，2 手昨仓（开 3006）+ 2 手今仓（开 3000），卖平 3 手 @3004，先开先平平 2 昨 + 1 今：昨 (3004−3005)×10×2=−20，今 (3004−3000)×10×1=+40，合计 +20。盯市盈亏是逐笔之和，不是“均价×手数”。
- 处理：账本必须保存持仓明细而非只有均价；同时保留逐日与逐笔两套盈亏口径。

**G-10 资金恒等式与 Balance 口径**
- 现象：本地算出的权益与 `ReqQryTradingAccount` 不一致。
- 原因：静态权益 = PreBalance + Deposit − Withdraw；`Balance`（动态权益）= 静态权益 + PositionProfit + CloseProfit + CashIn − Commission，`Balance` 字段含当日浮动/平仓盈亏，不是静态权益；`Available` = Balance − CurrMargin − FrozenMargin − FrozenCommission − FrozenCash − DeliveryMargin；账户字段多为按持仓汇总的当日值，结算后清零。持仓盈亏由行情驱动：多头 `(最新价 − 持仓均价) × 乘数 × 手数`，空头反向。
- 处理：账本按此恒等式实现并与查询对账；是否“可用含平仓盈利”由 `ReqQryBrokerTradingParams` 的 `AvailIncludeCloseProfit` 等参数决定；可用资金的算法是“汇总后再应用”，不是分笔算。

**G-11 盘中资金与结算单口径不同，不要混用**
- 现象：盘中 `Available` 与结算单“可用资金”对不上；结算单汇总项与明细不一致。
- 原因：结算单口径：期末结存 = 期初结存 + Σ出入金明细 + 持仓盯市盈亏 + 平仓盈亏 − 手续费 + 权利金收入 − 权利金支出；客户权益 = 期末结存；可用资金 = 客户权益 − 保证金占用。盘中 `Available` 含浮动盈亏（盘中口径），结算单可用资金是结算后权益减保证金，两者时点不同、各自自洽，差额为 `PositionProfit`。出入金必须从明细行求和，不能只读汇总字段（汇总字段可能为 0 而明细列有银期转账）；申报费不是独立字段，而是以“出入金”类型的一笔出金体现（说明栏为申报费出金），在结算时从权益中扣除，盘中实时资金不含申报费。
- 处理：盘中对账用 `ReqQryTradingAccount`；日终对账用结算单；两套口径各自核对。

**G-12 保证金：用公司保证金率，价格类型看经纪公司参数**
- 现象：计算的保证金与账户显示不同。
- 原因：期货保证金 = (按手数保证金费 + 按金额保证金率 × 价格 × 乘数) × 手数 = (MarginRatioByVolume + MarginRatioByMoney × Price × VolumeMultiple) × Volume；实际用公司保证金率（`ReqQryInstrumentMarginRate`，已含交易所率及调整的最终费率），`ReqQryInstrument` 返回的是交易所级别费率，不用于计算；`MarginPriceType`（`ReqQryBrokerTradingParams` 查）：昨仓恒用昨结算价；今仓按公司配置：'1' 昨结算价/'2' 最新价/'3' 成交均价/'4' 开仓价，只有 '2'/'3' 下今仓保证金随行情波动；冻结保证金按昨结算价×乘数×保证金率×报单量 + 按手数保证金×报单量（不同公司可有差异）。
- 处理：登录同步阶段查询并缓存 `BrokerTradingParams` 与各合约保证金率；盘前维护费率表（见 H-07）。

**G-13 保证金优惠与大单边**
- 现象：持仓双向（多空）时，保证金低于两边之和。
- 原因：上期所品种内大单边（由 `MaxMarginSideAlgorithm` 判断）、中金所跨品种大单边、大商所/郑商所套利合约取高；盘后交易所自动组合后只收大单边。组合保证金优惠系统（中金所 RCAMS、上期所 PMM、郑商所 SPBM、大商所组合保证金系统）规则复杂，要完全算准非常困难。
- 处理：（工程建议）本地只用简单通用规则（如大单边）做估算，权威数据以 `ReqQryTradingAccount` 为准；不要试图复刻全部组合保证金规则。

**G-14 手续费公式与申报费**
- 现象：手续费估算与实际偏差；账户里看不到申报费。
- 原因：手续费 = 成交量 × (成交价 × 乘数 × RatioByMoney + RatioByVolume)，两项相加；开仓、平仓、平今各一套；一笔平仓若同时平昨与平今，要按两部分分别计价；平今免手续费的品种差别很大。申报费（OrderCommRate）按笔收取，报单、撤单都计，FAK/FOK 的自动撤单也计（一个 FAK/FOK = 报单 + 撤单 = 2 次信息量）；当日信息量不超过 4000 笔（股指期货 2000 笔）时免收；`ReqQryInstrumentOrderCommRate` 的响应是空指针，查不到具体申报费率；盘中实时资金不含申报费，只在结算单体现。
- 处理：手续费区分开/平/平今三套费率；申报费不进盘中估算，日终以结算单为准。

**G-15 登录后以查询为准校正本地账本**
- 现象：长时间运行后本地账本漂移。
- 原因：任何增量维护都会因丢包、重复、规则差异产生误差。
- 处理：（工程建议）启动时、每日开盘前、收盘后以 `ReqQryInvestorPosition`、`ReqQryTradingAccount` 校正；盘中定时低频对账，不一致时以柜台为准并告警。

## H. 查询流控与在途限制

**H-01 在途查询只允许 1 笔：返回值 -2**
- 现象：循环/并发查询时，后面的查询函数返回 -2，没有任何回调。
- 原因：API 动态库底层每次只允许 1 个查询请求在途，在前一笔未收到全部响应前，不能发下一笔；`ReqQry*` 开头的函数都受此限制，被限制的请求在动态库中直接阻断，不会发往后台，调用无效。返回值：0 发送成功（仅表示发出）；-1 网络原因失败；-2 未处理请求超过许可数；-3 每秒发送请求数超过许可数。
- 处理：每次发查询都要检查返回值，非 0 说明根本没发出；查询必须串行：收到上一笔响应且 `bIsLast=true` 后再发下一笔（工程建议：一个查询队列 + 单线程消费，收到 `bIsLast` 才出队下一笔）。

**H-02 -2 用 sleep 治不好，-3 用 sleep 有效**
- 现象：在 SPI 回调里加了 sleep，查询仍然返回 -2。
- 原因：请求读取和 socket 读写与 SPI 回调由同一个底层线程负责，在 SPI 回调里 sleep 会阻塞读写，只有回调结束后查询才会从 socket 发出，所以在回调里写再多重查询、sleep 再长，最终都是同时发出，仍触发流控。-3（每秒超限）在异步线程中顺序多次查询时容易触发，两次查询之间 sleep 1~2 秒有效。
- 处理：-2：在一个 SPI 回调里只放一个查询，嵌套（在响应回调里发下一个查询）；或使用事件队列/独立线程顺序查询。-3：查询之间间隔一定时间；-3 是旧穿透式版本之前的行为，新版本每秒允许的次数由后台配置并在登录回报中传给动态库，具体值需向期货公司询问。

**H-03 查询每秒流控：CTP:查询未就绪，请稍后重试（错误码 90）**
- 现象：`OnRspError` 回调“CTP：查询未就绪，请稍后重试”，查询没有执行。
- 原因：除动态库端流控外，后台也对查询限流（防止用户用特殊手段不停查询）；每秒笔数在交易前置配置（历史上内置于 API，为 1 笔/秒）。流控针对投资者，不针对操作员；所有 `ReqQuery*`（非 `ReqQry*`）开头的函数不受查询流控限制，因为走交易核心不经查询核心。
- 处理：收到 90 号错误后退避约 1.1 秒再重试同一请求（工程建议：最多重试若干次，超限再报错）；不要并行查询。

**H-04 FTD 报文流控：超限不报错，只是延迟**
- 现象：突发报单后，后几笔延迟很大，没有任何错误。
- 原因：后台按单个 session 对所有请求（登录、查询、报单、撤单等）做 FTD 报文流控；超过的指令被缓存在前置，直到下一秒才发出，例如配置为 6，1 秒内报 10 笔，前 6 笔立即发送，剩余 4 笔延迟到下一秒；早期资料中的口径为每会话每秒 6 笔、同账户最多 6 个会话。
- 处理：对延迟敏感的策略必须了解该配置并限速；不要用“没有报错”推断没有流控。

**H-05 流控全景（客户端面对的几类）**
- 现象：不清楚某种异常属于哪类流控。
- 原因：①FTD 报文流控（无错误，超限延迟一秒）；②报撤单流控（“CTP:下单频率限制”，报/撤分开计算，按 InvestorID，多会话无用）；③查询在途（-2）与每秒（-3 或 90 号错误）；④前置连接数流控（被动断开 + `OnFrontDisconnected`，按前置分别配置）；⑤同一用户最大在线会话数（登录返回“CTP:用户在线会话超出上限”，按 UserID 计）；⑥交易所 API 流控（`OnRtnOrder` 提示“CTP：交易所每秒发送请求数超过许可数/未处理请求超过许可数”）。链路上交易所底层 API 与交易所后台也可设置流控，由柜台厂商处理。
- 处理：遇到异常先对照此清单定位；具体错误码见《14_错误码速查表》，更多说明见《09_流控错误与排障》。

**H-06 查询是否要在登录后立即发出**
- 现象：登录回调里连发多个查询，大部分失败。
- 原因：登录后需要同步的查询很多（合约、账户、持仓、明细、订单、成交、费率、结算确认），同时发出会触发 H-01/H-03。
- 处理：（工程建议）把初始化查询排成固定顺序的任务链：结算确认状态 → 合约 → 账户 → 持仓 → 持仓明细 → 订单 → 成交 → 费率，每步等待 `bIsLast` 再进入下一步，失败时按 H-03 退避重试。

**H-07 费率查询的坑**
- 现象：想一次拿到所有合约的保证金率/手续费率拿不到；查询返回的合约代码是品种代码。
- 原因：`ReqQryInstrumentMarginRate`、`ReqQryInstrumentCommissionRate` 返回的是最终费率（绝对值，已含交易所费率及调整）；`BrokerID`、`InvestorID`、`HedgeFlag` 必填；`InstrumentID` 留空时只返回当前持仓合约（含持仓量为 0 的记录，如今天开仓失败的合约）的费率，不是全市场；查询返回的 `InstrumentID` 若是品种代码（如查 IF2203 返回 IF）表示该合约使用品种通用费率；投资者代码返回 "000000" 表示所有投资者通用费率；v6.7.11 起新版本支持以品种代码查询，返回该品种及该品种下不同于品种设置的单一合约费率，并且按合约查询时响应的 `InstrumentID` 为合约代码。期权保证金率用 `ReqQryOptionInstrTradeCost`，期权手续费率用 `ReqQryOptionInstrCommRate`。
- 处理：需要全市场保证金率时，可由 `ReqQryInstrument`/`ReqQryClassifiedInstrument` 获得交易所级别的多头/空头保证金率，再加公司固定加成（经纪公司通常在交易所保证金率上加一个固定值，例如 1%，需向期货公司确认）；或逐合约查询（受流控，需排队）；交易所调整费率前会提前发公告，可维护本地费率表并随公告更新（工程建议）。新版 API 升级前务必确认期货公司柜台支持该版本。

## I. 行情

**I-01 必须登录后才能订阅；订阅任何代码都返回成功**
- 现象：订阅成功，没有行情。
- 原因：`OnRspSubMarketData` 无论合约对错都返回“CTP:No Error”，只有编码正确且未过期的合约才有行情。合约代码大小写规则：上期所/能源中心小写+4位数字（如 rb1909）；中金所大写+4位数字（如 IF2009）；郑商所大写+3位数字（如 TA001）；大商所小写+4位数字；过期合约没有行情。
- 处理：合约代码一律使用交易 API 查询得到的 `InstrumentID` 原样订阅（行情 API 没有合约查询功能）；订阅函数第二参数必须等于数组长度；订阅后用收到的第一笔行情验证。

**I-02 行情 API 与交易 API 完全独立，地址不能混用**
- 现象：订阅合约却收到退订响应；或 `Init` 后无反应。
- 原因：行情 API 连到了交易前置地址，或头文件与库版本不一致；行情与交易是两套前置、两个动态库，互不干扰。
- 处理：行情地址与交易地址分别配置；两个动态库各用独立流文件目录；核对 API 版本；先 telnet 前置地址。

**I-03 CTP 推送的是快照（切片），不是逐笔 tick**
- 现象：以为一笔成交对应一条行情；成交量/价格序列有跳跃。
- 原因：国内期货交易所目前只推送切片（快照）数据，将一定时间内的逐笔数据统计成一个快照；上期所/能源中心/中金所 Level1 约 500 毫秒一次（1 秒 2 笔），大商所/广期所 Level1 500 毫秒，郑商所 Level1 可配置为 250 毫秒（1 秒 4 次）或 500 毫秒，可能 1 秒多笔；业内称之为 tick，但并非真正的逐笔。有更新才推送，首次连接推送初始行情；推送时间不严格落在 000/500 毫秒。Level2 多档行情一般需要付费，CTP 通常无法获取。
- 处理：一切基于“快照”设计：不要假设一条行情等于一笔成交；多档行情通过其他行情柜台获取。

**I-04 Volume 是当日累计量，现手要自己减**
- 现象：把 `Volume` 当成本笔成交量，数值越来越大。
- 原因：`Volume` 是该交易日内的累计成交量；切片成交量 = 本切片 `Volume` − 上一切片 `Volume`。
- 处理：同一合约按时间序对前后两笔做差分，并用 `max(差, 0)` 兜底；跨交易日（新交易日开盘）重置上一笔 Volume；差分前先过滤非交易时段的行情（见 I-09）。

**I-05 现手、增仓、开平、对手盘全部要自己算**
- 现象：想要现手、增仓、开平方向，行情结构体里没有这些字段。
- 原因：这些数据只能由 `Volume`、`OpenInterest`、`LastPrice`、`AskPrice1`、`BidPrice1` 自行计算：现手 = 后一笔 Volume − 前一笔 Volume（≥0）；增仓 = 后一笔 OpenInterest − 前一笔 OpenInterest（可正可负）。开平性质：双开 现手=增仓>0；开仓 现手>增仓>0；平仓 现手>−增仓>0；换手 现手=增仓=0（多头互换或空头互换）；双平 现手>增仓=0；现手=增仓=0 且无法归类的记为“未知”仅作记录（“换手”与“未知”条件字面相同，需结合前后笔方向区分）。方向：后一笔 LastPrice ≥ 前一笔 AskPrice1 为向上；≤ 前一笔 BidPrice1 为向下；另有以后一笔买卖一价为基准的判断（后一笔 LastPrice > 后一笔 AskPrice1 向上，< 后一笔 BidPrice1 向下），其余为不变。性质 6 种 × 方向 3 种 = 18 种开平组合。对手单（2020 年 1 月 1 日起交易所统计改为单边）：设 S 为对手单中开平方向相同的操作，O 为相反的操作，则 S = |增仓| / 2，O = 现手 / 2 − S。
- 处理：按上述公式实现；这些数据只有同一合约前后两帧才有意义，累计量必须单调不减。

**I-06 无效值 DBL_MAX（1.7976931348623157e+308）**
- 现象：行情里出现 1.797e+308 之类的巨大数值，导致计算溢出或 K 线异常。
- 原因：这是 double 类型上限值，在 CTP 内部表示“无效”，例如盘中的 `SettlementPrice` 就是无效值，收盘结算后才有效；其他未赋值的价格字段也可能是该值。
- 处理：读取任何价格字段前判断是否 ≥ 1e300（或等于 DBL_MAX），无效值一律按“无数据”处理，不参与盈亏、均价、K 线计算；昨结算价等需要的参考价从交易 API 的合约/行情快照中取有效值。

**I-07 TradingDay 与 ActionDay：夜盘各所不一致**
- 现象：夜盘 K 线日期错乱；按日期汇总成交时夜盘归到错误的交易日。
- 原因：设计上 `TradingDay` 表示交易日，`ActionDay` 表示实际日期；日盘二者一致，夜盘属于下一交易日（周五夜盘属于下周一），但各交易所实现不一致。例如 20190830（周五）夜盘：上期所/能源中心 TradingDay=20190902、ActionDay=20190830；大商所 TradingDay=ActionDay=20190902（两个日期都是交易日）；郑商所两者都是 20190830（日夜盘都是当日日期）。只有上期所/能源中心的日期是准确的。
- 处理：交易日以登录响应中的 TradingDay 或静态函数 `GetTradingDay()` 为准；`OnRtnOrder`/`OnRtnTrade` 的 TradingDay 是准确的；行情里的 `ActionDay`、`TradeDate` 不可靠，不要直接用。取巧办法：用本地系统日期作实际日期，交易日取“当前时间 + 4 小时”（遇周五特判到周一），属工程经验，需结合节假日处理（工程建议）。

**I-08 UpdateMillisec 各交易所取值不同**
- 现象：用毫秒字段排序/去重出现异常。
- 原因：上期所/能源中心/中金所的 `UpdateMillisec` 只会出现 0 和 500 两个值；大商所是切片时的真实毫秒；郑商所恒为 0。
- 处理：不要把 `UpdateMillisec` 当作精确时间戳；同一秒内的先后以到达顺序为准；去重用 `UpdateTime + UpdateMillisec + Volume + LastPrice` 的组合（工程建议）。

**I-09 非交易时段也会收到行情**
- 现象：开盘前、收盘后收到行情，K 线多出奇怪的一根。
- 原因：日盘开始前可能收到夜盘行情的重演（CTP 日盘启动时会重演夜盘流水）；日盘结束后（一般 15:00~15:30，约 16 点前）交易所结算完成会推送一次包含当日结算价的快照，郑商所盘后继续推送；盘后期转现、TAS 仍可成交。
- 处理：按交易时间过滤行情；盘后快照可用于提前获取结算价；不要把 15:00 后的快照当作异常（工程建议：K 线合成只接受合约交易时段内的快照）。

**I-10 Turnover 与 AveragePrice 的口径各所不同**
- 现象：成交额下降；均价与行情软件相差一个合约乘数。
- 原因：郑商所 Level1 不推送成交金额，CTP 里郑商所的 `Turnover` 是用当日均价和成交量自行合成的近似值：后台版本 6.7.1 之前 成交额 = 均价 × 成交量，6.7.1 及之后 成交额 = 均价 × 成交量 × 合约乘数（组播行情前置仍为不乘乘数）；且郑商所推送的当日均价会按最小变动价位四舍五入，所以可能出现后一个快照的成交额反而比前一个低。除郑商所外，其他交易所不推送成交均价，CTP 的 `AveragePrice` 是由 `Turnover / Volume` 算出，需要再除以合约乘数才是真正均价（交易所官网公布的均价 = 成交额 / 成交量 / 乘数）；早期资料口径为：郑商所当日均价正确、成交金额需乘合约乘数；大商所/上期所均价需除以乘数、成交金额正确。
- 处理：使用均价/成交额前，按交易所和柜台版本核对一次口径（用已知合约实测）；成交额只做近似参考，不用于精确风控（工程建议）。

**I-11 K 线必须自己合成，各软件口径不同**
- 现象：自己合成的 K 线与行情软件对不上。
- 原因：CTP 不推送 K 线。分钟切换以 `UpdateTime` 的分钟数判定；周期成交量 = 本帧 Volume − 上一帧 Volume（用 `max(差,0)` 兜底）；新分钟时 OHLC 均置为当时 `LastPrice`、成交量归零。不同软件的合成方法本来就不同：有的以 0 秒整的快照作为新 K 线起点，有的将其作为上一根的终点；一小时 K 线有的按自然时间（商品期货白天 5 根：09:00~10:00、10:00~11:00、11:00~11:30、13:30~14:00、14:00~15:00），有的按完整交易一小时切割（白天 4 根：09:00~10:00、10:00~11:15、11:15~14:15、14:15~15:00）；K 线内创下的当日新高/新低若未体现在快照 `LastPrice` 中，有的软件忽略，有的用快照的 `HighestPrice`/`LowestPrice` 修正 High/Low（如发生乌龙指行情时差异明显）。
- 处理：先确定本系统的 K 线规则并写成文档；不要追求与任何软件完全一致（快照合成本身丢失了大量行情信息，仅用于粗略展示）；新交易日、新交易时段需重置状态。

**I-12 组合合约、主力合约、历史行情、持仓行情**
- 现象：订阅组合合约行情很少；找不到主力合约；想取历史行情。
- 原因：CTP 不计算组合合约行情，只转发交易所行情，以组合合约号订阅，郑商所和大商所会推但比实际少很多，行情软件里组合合约的最新价常是软件用两条腿价差合成的；CTP 查不到主力合约；CTP 只提供实时行情，不提供历史行情、不提供持仓行情，也没有 K 线、分时、期权 Gamma 等数据（这些来自软件行情商）；行情软件（快期、博易大师等）连的是软件商自建行情源，不是 CTP 行情前置，延时和量价数据与 CTP 有差别；现手、增仓等盘口数据需自行计算。
- 处理：组合行情订阅两条腿自己算价差；主力合约按持仓量/成交量自行筛选，注意换月逻辑；历史数据从外部来源获取。

**I-13 合约信息不可全信，盘中可能新增合约**
- 现象：合约名称、最小变动价位、品种表互相矛盾；夜盘前查不到某新合约。
- 原因：合约名称、品种名称、最小变动价位等字段由期货公司自行设置，没有统一标准，同一公司品种表和合约表可能互相矛盾；同一交易日内合约数量会变化（如新上市的期权，若该品种不开展夜盘，新合约在夜盘开始前查不到，日盘开盘前才能查到）；能否交易：当天能否交易看 `IsTrading`，此刻能否交易看合约状态（仅上期所）或交易所状态（`OnRtnInstrumentStatus`），`InstLifePhase` 不可靠（大商所/郑商所不盘中推送单合约状态）；v6.5.1 起有 `ReqQryClassifiedInstrument`，低版本只能查全部再按 `ProductClass` 过滤；使用新接口查全市场要给 `TradingType`/`ClassType` 有效值（如 TD_ALL/INS_ALL），不能设为 0。
- 处理：夜盘开盘前和日盘开盘前各查询一次合约；自建合约信息表并与交易所公告校验（工程建议）。

## J. 字符编码（GBK）

**J-01 CTP 所有字符串都是 GBK**
- 现象：在 UTF-8 终端/日志/数据库里打印错误信息、合约名称、结算单，全是乱码。
- 原因：CTP 返回的字符串（`ErrorMsg`、`StatusMsg`、合约名称、结算单内容等）一律为 GBK 编码，UTF-8 环境直接显示即乱码。
- 处理：在 SPI 边界处统一把 `char[]` 从 GBK 转成内部使用的 UTF-8；发送给 CTP 的字符串字段（如中文备注）从 UTF-8 转回 GBK；日志里同时记录原始字节的十六进制（工程建议）。

**J-02 中文被拆成两半：分片结算单必须先拼接再解码**
- 现象：结算单某些位置出现乱码或最后一个汉字解析失败。
- 原因：结算单 `Content` 分多条响应返回，一个汉字（双字节）可能被拆在两条响应的交界处；每条响应单独解码就会得到半个字符。
- 处理：用大的 byte/char 数组把全部响应拼接完成，最后统一解码（C++ 用 `strncpy`/`memcpy` 拼接；Python 等语言用 bytes 而不是 str 拼接）。

**J-03 二进制字段不能用字符串函数**
- 现象：终端信息采集结果在传递中被截断。
- 原因：终端信息是可能含 `'\0'` 的字符数组，用 `strcpy/strncpy` 会被截断。
- 处理：使用 `memcpy`；Python、Java 用 bytes/字符数组。

**J-04 UTF-8 终端字符列宽翻倍**
- 现象：把 GBK 字段转为 UTF-8 存入固定长度列时被截断。
- 原因：一个汉字在 GBK 中占 2 字节、在 UTF-8 中占 3 字节，列宽不足时会截断。
- 处理：数据库/内部结构的字符列宽按 GBK 长度的 1.5 倍预留（工程建议）。

## K. 结算单

**K-01 每个交易日首次登录必须确认结算单**
- 现象：登录成功但报单失败（结算单未确认）。
- 原因：交易规则要求每交易日首次登录后确认结算单；当天已确认的会话再次登录可直接交易。
- 处理：登录同步阶段固定流程：`ReqQrySettlementInfoConfirm` 查询是否已确认（无记录表示未确认）→ 未确认则 `ReqQrySettlementInfo`（不填日期取上一交易日）获取并展示 → `ReqSettlementInfoConfirm`（只需 BrokerID+InvestorID）确认。无人值守程序可自动确认，但仍应保存结算单正文留痕（工程建议）。

**K-02 结算单内容分多条返回，要用 bIsLast 判断结束**
- 现象：结算单只显示一部分。
- 原因：`OnRspQrySettlementInfo` 每次返回一段内容，最后一段 `bIsLast=true`。
- 处理：累积所有段，`bIsLast` 到达后再整体解码、解析（见 J-02）。

**K-03 结算单口径与盘中口径不同**
- 现象：结算单的“可用资金”、权益与盘中查询值不同。
- 原因：见 G-11：结算单是结算后口径；出入金必须从明细求和；申报费以出金形式体现。
- 处理：日终对账以结算单为准，盘中以查询为准；对账时先统一口径。

**K-04 结算单格式长期稳定，可自动解析；历史明细靠历史结算单**
- 现象：想获取历史成交、历史平仓明细。
- 原因：结算单格式长期稳定，可用格式化配置自动解析；CTP 没有历史成交/平仓明细的查询接口，历史成交与平仓明细可以从历史结算单获取。
- 处理：按日保存结算单并解析（工程建议）；持仓明细的历史由开仓日期 `OpenDate` + `TradeID` 追溯。

**K-05 结算后的日切行为**
- 现象：日切后本地数据与柜台不一致。
- 原因：逐日盯市制度下，结算后持仓明细按结算价重算盈亏与保证金，昨日的动态权益成为新交易日的 `PreBalance`，昨结算价成为新交易日的 `PreSettlementPrice`，账户中的当日字段（持仓盈亏、平仓盈亏、手续费、冻结等）清零，交易日推进；`FrontID`、`SessionID`、`MaxOrderRef` 也随新会话重置。
- 处理：新交易日首次登录后，全量以查询重建本地持仓/资金/明细（见 G-15）；不要沿用前一交易日的 OrderRef、本地订单状态；节假日交易日历由外部维护（工程建议）。

## L. 期权与组合

**L-01 组合合约开仓后，持仓查询会出现 3 条记录**
- 现象：开一手组合合约，持仓里出现三条记录，数量/盈亏看起来重复。
- 原因：组合合约开仓后生成：1 条组合合约持仓记录 + 2 条分腿合约持仓记录；近期合约分腿的多空方向与组合一致，远期合约分腿与组合相反。组合记录只计算上日持仓、今日持仓、总持仓、开仓量、保证金等字段，平仓量、平仓盈亏、持仓成本、持仓盈亏、手续费都在分腿记录中计算；分腿记录的持仓量、开仓量、平仓量是单一合约与组合形成的持仓的总和，要区分必须查持仓明细；分腿的保证金字段只含单一持仓的保证金，组合部分的保证金存放在组合记录里；而开仓成本、开仓均价、持仓成本、持仓均价、持仓盈亏、平仓金额、平仓盈亏、手续费这类字段是计算全部持仓（包括组合形成的）。
- 处理：汇总持仓、保证金时避免把组合记录与分腿记录重复累加；需要区分“单一持仓/组合持仓”时用持仓明细（`TradeType` 为 '4' 的是组合单生成成交）。

**L-02 组合平仓：先单一后组合，先开先平，会“打散”**
- 现象：平一个合约，却发现别的合约出现新的单一持仓；组合持仓数量在没有直接操作时减少。
- 原因：组合平仓遵循“先单一后组合、先开先平”：先平单一合约头寸（用哪一手按先开先平），单一不足再平组合头寸；用到组合头寸时要“打散”：自身分腿的组合头寸减少、平仓量增加，组合记录持仓量减少，另一条分腿的组合头寸减少并衍生出一个单一合约持仓（撮合编号与开仓时间延续原组合，因此常被优先平掉）。官方说明了 6 种情形：单一合约平仓用了单个/多个组合头寸；组合合约平仓只用自身头寸；用了其他组合合约的头寸；用了单一合约头寸（即使组合持仓为 0，只要两条腿各有单一持仓就可以平）；用了多个组合头寸（自身 + 其他）。例：A 单一 4 手、AB 组合 2 手；B 单一 3 手、AB 组合 2 手；平 A 5 手：A 单一 4 手全平，差 1 手则打散 1 手 AB 组合，结果 A 单一 0、AB 组合 1；B 单一 4（3 + 衍生 1）、AB 组合 1。
- 处理：本地持仓模型遇到组合要按此规则；难以复刻时，以柜台持仓查询为准并在每笔成交后查询校正（工程建议）。

**L-03 组合冻结**
- 现象：组合平仓报单后可平数量计算不对。
- 原因：组合合约的冻结体现在组合记录的多头/空头冻结字段及两条分腿的“组合多头/空头冻结”字段：多头开仓冻结：组合记录的多头冻结增加，近期分腿的组合多头冻结增加，远期分腿的组合空头冻结增加；多头平仓冻结：组合记录的空头冻结增加（可平数量减少），近期分腿的组合空头冻结增加，远期分腿的组合多头冻结增加。
- 处理：计算组合可平量时用组合记录的冻结字段（工程建议：保持与柜台查询返回一致）。

**L-04 盘后自动组合与大单边**
- 现象：没有报组合，却在持仓里多出组合记录，保证金变少。
- 原因：大商所/郑商所在结算后可能自动把合适持仓配对成组合持仓（跨品种、跨期），有的品种需要主动申请；组合后只收大单边保证金。
- 处理：持仓同步时识别并过滤/保留组合记录（见 L-01）；保证金估算采用简单通用规则（见 G-13）。

**L-05 期权保证金与手续费**
- 现象：期权保证金、冻结、权利金对不上。
- 原因：期权（卖方）保证金 = MAX(权利金 + 交易所期权合约保证金不变部分, 交易所期权合约最小保证金)（不变部分/最小保证金由 `ReqQryOptionInstrTradeCost` 查询，除上期所外最小保证金为 0）；投资者口径同理，用 `FixedMargin`/`MiniMargin`；昨仓权利金 = 结算价 × 乘数（上期所例外：max(昨收,昨结) × 乘数）；委托冻结一律用昨结算价；期权买入开仓不占保证金，改为冻结权利金；期权手续费 = 期货口径 + 执行手续费（`ReqQryOptionInstrCommRate`）；期权盈亏 = 期货式价差 + 权利金收支（`CashIn` 计入动态权益）；期权权利金价格类型在 `BrokerTradingParams.OptionRoyaltyPriceType`。
- 处理：期权保证金不要套用期货公式；各交易所分公式见《07_期权做市商组合与行权》（本篇不展开）。

**L-06 期权合约的查询方式**
- 现象：查询期权合约要么全部返回，要么返回空。
- 原因：v6.5.1 起 `ReqQryClassifiedInstrument` 可用 `ClassType=THOST_FTDC_INS_OPTION` 直接查期权；低于 v6.5.1 只能查全部再按 `ProductClass` 过滤；新接口查全市场要给 `TradingType`/`ClassType` 有效值，不能设为 0。
- 处理：按版本分支实现；盘中新增合约，见 I-13。

**L-07 做市商批量撤单仅大商所**
- 现象：对非大商所合约调用 `ReqBatchOrderAction` 无效。
- 原因：该接口仅支持大商所，且仅做市商客户可用。
- 处理：非做市商/其他交易所自行逐笔撤单（见 F-07）。

## M. 仿真与实盘差异

**M-01 SimNow 与交易所仿真环境是两套不同系统**
- 现象：在 SimNow 上通过的程序，到期货公司仿真或实盘出问题。
- 原因：SimNow 第一部分是与生产相同的 CTP 柜台系统，第二部分是上期技术基于上期所系统自行开发的模拟交易所，并非真正对应五个交易所的测试环境。两套仿真环境差异：SimNow 统一连接 SimNow 前置，转发实盘行情（有一定延迟），不含组合合约和大商所/郑商所的大部分期权，新品种上市或规则调整同步可能有几天延迟，含 7×24 盘后环境，不撮合（价格合适与对手价比较直接全部成交，不会部分成交、不会自成交），含结算功能（结算价同实盘），最后交易日现金交割，费率固定；交易所仿真环境连接各期货公司仿真前置，行情由各用户撮合成交产生（较难成交，行情与实盘不同），包含所有合约（还多出测试合约如外汇期货），新品种先在此测试，盘后不可交易（部分期货公司夜盘不开放），撮合方法同实盘（可能部分成交、可能自成交），结算价由内部交易数据产生，费率可联系期货公司调整。
- 处理：按“SimNow 做功能测试、交易所仿真做行为测试”分层测试；上线前必须在期货公司要求的仿真环境测试并保留测试报告（穿透式监管要求客户先在交易所仿真环境测试并填写测试报告）。

**M-02 SimNow 的平仓回报开平标志按上期所规则**
- 现象：SimNow 上成交回报里平今/平昨标志保留，实盘大商所/郑商所/中金所变成统一的平仓。
- 原因：见 E-10：SimNow 的规则按上期所处理，与实盘大商所等不一致。
- 处理：持仓更新逻辑不依赖成交回报里的平今/平昨标志；实盘环境前做一次专项验证。

**M-03 SimNow 的交易所拒单错误码按上期所赋值**
- 现象：不同交易所的拒单，错误码都一样。
- 原因：SimNow 环境中所有交易所拒单的错误码（`OnRtnOrder` 或 `OnErrRtnOrderAction` 的 `StatusMsg` 开头数字）都按上期所规则赋值，如报价超出涨停板的拒单回报中错误码都是 49（无论哪个交易所）。
- 处理：不要依赖 `StatusMsg` 开头数字区分交易所；以交易所仿真或实盘为准验证；错误码速查见《14_错误码速查表》。

**M-04 不同期货公司的仿真账户可能互相撮合**
- 现象：仿真成交的对手方是别的期货公司的账户。
- 原因：各期货公司的仿真环境都连接到各交易所的仿真环境中，因此 A 公司账户的订单可能与 B 公司账户的订单撮合成交，与实盘相同。
- 处理：部分成交、自成交类场景可在不活跃合约上与自己对手交易（自成交）来制造；中金所仿真有自成交风控，该办法不适用。

**M-05 仿真环境的限制与价格保护带**
- 现象：仿真环境里撤单被拒、查不到结算单、报价被拒。
- 原因：部分期货公司在仿真环境限制账户交易某些品种（如禁止交易中金所合约）或限制权限（如查询结算单、撤单）；中金所仿真环境有“价格保护带”（报单价格不得偏离当前最新价一定幅度，实盘未上线该功能）。
- 处理：先确认期货公司仿真环境的开放品种与权限；按保护带限制报价。

**M-06 SimNow 注册与使用的常见坑**
- 现象：收不到验证码；账号无法使用；资金用完无法入金。
- 原因：注册手机务必用非电信手机（电信手机收不到验证码）；填写账号信息时柜台选“标准 CTP”；短信中的账号密码就是登录用的 `InvestorID` 与 `Password`，首次登录需修改密码；注册成功得到 100 万模拟资金，资金亏完不支持入金，只能换手机号重新申请；SimNow 有两套环境，第一套与实际生产同步，只在交易日交易时间提供服务；7×24 地址不稳定；用户多时前置拥堵（见 B-02）；SimNow 暂无穿透式柜台时不需要 AppID 与 AuthCode，仿真与生产需使用同一套（版本匹配）API。
- 处理：用于功能测试，勿用于策略测试；6.7.11 起评测与生产版本合并，创建 API 时通过 `bIsProductionMode` 参数切换（true 生产，false 测评）。

**M-07 版本与评测**
- 现象：测评版和生产版混用导致接入失败。
- 原因：6.7.11 之前穿透式评测版本与生产版本分开发布，需切换不同 API 包；6.7.11 起合并，`CreateFtdcTraderApi(const char* pszFlowPath = "", bool bIsProductionMode = true)`，行情 `CreateFtdcMdApi` 同样增加该参数；v6.6.1 起不再支持 Windows XP 及更低系统。新版 API 升级前必须确认期货公司柜台支持。
- 处理：评测时传 false，生产时传 true；升级前向期货公司确认版本支持。

## N. 性能与日志

**N-01 SPI 回调内不做耗时操作**
- 现象：回报延迟累积，甚至断线。
- 原因：SPI 回调与 socket 读写同线程（见 A-01）。
- 处理：回调内仅拷贝与入队；写磁盘、数据库、网络、日志格式化放到工作线程（工程建议）。

**N-02 行情回调的吞吐**
- 现象：订阅全市场合约后，行情处理跟不上。
- 原因：全市场订阅会带来大量快照，每个合约约 1 秒 2 笔（郑商所可配置为 1 秒 4 笔）。
- 处理：行情回调只拷贝关键字段入无锁队列/环形缓冲，按合约分片处理；只订阅真正需要的合约（工程建议）。

**N-03 日志要记录什么**
- 现象：线上问题无法复盘（报单为什么被拒、回报为什么重复）。
- 原因：CTP 的问题大多与时序、返回值和字段细节有关，没有原始数据就无法复盘。
- 处理：（工程建议）记录：①每个 `Req*` 的返回值与 `nRequestID`；②每个回调的全部关键字段：`OrderRef`、`FrontID`、`SessionID`、`OrderSysID`、`OrderStatus`、`OrderSubmitStatus`、`VolumeTraded`、`StatusMsg`、`ErrorID`/`ErrorMsg`（GBK 转 UTF-8）；③`OnFrontConnected`/`OnFrontDisconnected(nReason)` 与重连、登录时间点；④API 版本与前置地址；⑤成交回报的 `TradeID`、`ExchangeID`、`Direction`；⑥每次对账的差异。

**N-04 日志不要放在 SPI 同线程里同步落盘**
- 现象：日志写盘阻塞导致回报延迟。
- 原因：同 N-01。
- 处理：使用异步日志；日志队列满时丢弃低级别日志而不是阻塞（工程建议）。

**N-05 流文件与日志的清理**
- 现象：流文件目录越来越大。
- 原因：每日产生流文件（`.con` 等）。
- 处理：按账户目录隔离，按交易日定期清理旧流文件；RESUME 模式依赖当日流文件，不要在交易时段删除（工程建议）。

**N-06 控制报撤单频率，避免触发“程序化交易”认定**
- 现象：被交易所要求报备程序化交易。
- 原因：“双 10”规则：同一交易日内，在同一家期货交易所下，1 秒内出现 10 笔及以上报单和撤单（合并统计），且单日累计出现 10 次及以上，会被纳入专项统计；它不是异常交易认定，但触及者可能被认定为程序化交易客户，需向交易所和监管部门报备所用交易程序（坊间还有“双 20”的说法）；该规则是唯一不按合约而是按“单个交易所”汇总统计的规则；近年监管趋严，程序化接入需经过测试认证，部分交易所会增加报单延时。
- 处理：了解并遵守报备要求；个人开发者要关注监管政策变化，必要时转用已完成监管认证的第三方量化平台（见后文工作流）。

**N-07 交易所异常交易风控与 CTP 柜台风控是两套独立规则**
- 现象：单子都能下进去，最后却被交易所警示、限制开仓。
- 原因：交易所异常交易以单个合约独立统计：①单边持仓限额（按合约）；②日内累计开仓限额（按合约）；③日内自成交次数：单个合约日内自成交 ≥5 次认定为异常交易；④日内频繁报撤单：该资料口径仅统计 IOC 订单（含 FAK/FOK）的未成交部分自动撤单：普通期货合约日内 ≥500 次、股指期货合约日内 ≥400 次认定异常；另有大额订单撤单管控、郑商所对停板价格上订单撤单的专项统计；⑤申报费统计不属于异常交易：所有合约按合约、阶梯收取，每日信息量（有效报单与撤单笔数）不超过 4000 笔（股指期货 2000 笔）免收。CTP 柜台只做两项基础校验：开仓验资（可用资金不足拒单）、平仓验仓（无对应持仓拒单）；CTP 不校验单边持仓/日内开仓是否超限、不统计自成交与报撤单次数、不校验挂单价是否超出涨跌停板、不校验是否在交易时段、不识别双 10 规则。另有资料称“上期所单合约撤单数不得超过 500 笔，FAK/FOK 的撤单不计入”；两类资料的统计口径存在不一致，应以各交易所最新公告为准。
- 处理：（工程建议）在自己的程序中按合约实现自成交预防（本地报单簿对敲检查）、撤单计数、开仓/持仓限额风控；价格与交易时段校验也自己做；阈值取交易所最新公告，并留安全余量。

**N-08 提高下单性能的注意点**
- 现象：下单延迟大。
- 原因：次席系统一般只做下单和撤单、追求低延迟，同时报出的相同订单次席的单子先到交易所；报单到交易所的速度由很多因素决定，测穿透时间有很多学问；一般客户都在主席系统上交易，主席系统功能全面（出入金、盘后结算等），追求高吞吐与高可靠。
- 处理：对延迟敏感的场景向期货公司了解次席与托管机房；不要期待同价位报单的成交归属可复现。

**N-09 监管趋势与接入方式的取舍**
- 现象：程序化接入门槛越来越高。
- 原因：近年程序化交易监管趋严：程序化接入需经过测试和认证；交易所托管机房开始清退投资者的托管机器；部分交易所会人为增加报单延时。资料的作者判断：一段时间内 CTP 等程序化接入仍可正常使用，但未来直接的程序化接入方式可能逐步减少对个人投资者的开放（这是个人判断，非官方结论）。
- 处理：了解期货公司对程序化接入的最新要求（测试报告、AppID/AuthCode 申请）；个人开发者可评估已完成监管认证的第三方量化平台作为备选；量化的核心是策略本身，工具不能代替策略验证（工程建议）。

## O. Agent 开发 CTP 应用的标准工作流

> 本节全部为（工程建议），把前文各组规则串成一条可执行的工作流，供 Agent（或开发者）开发、改造、排查 CTP 应用时逐步执行。每一步中的“见 X-nn”指向本篇对应条目。

**O-01 第 0 步：确认环境与版本（先于任何编码）**
- 确认：使用的 API 版本（`GetApiVersion()`）、头文件与动态库是否同一版本、期货公司前置所支持的版本（A-07）；使用评测还是生产模式（M-07）；目标环境是 SimNow、交易所仿真还是实盘（M-01）；是否需要 AppID/AuthCode（C-01、C-02）；前置地址（交易/行情分别）与 BrokerID（D-09）。
- 产出：一份环境清单（版本、地址、账号、认证信息、流文件目录规划）。

**O-02 第 1 步：搭建骨架——线程、生命周期、事件队列**
- 实现：SPI 只做“拷贝 + 入队”（A-01、N-01）；业务线程单线程消费事件；初始化顺序、释放顺序、`Join` 处理（A-03~A-05）；每个账号/实例独立流文件目录（A-06）；GBK↔UTF-8 转换层（J-01）。
- 产出：可连接、可打印回调日志的最小程序（含 `OnFrontConnected/Disconnected(nReason)` 的完整日志，B-02）。

**O-03 第 2 步：认证、登录与会话状态机**
- 实现：状态机 `Disconnected → Connected → Authenticated → LoggedIn → Syncing → Ready`；每次 `OnFrontConnected` 都认证并登录；登录失败（如密码错误）不得无限重试，避免死循环（C 组与 B-01）；保存 `FrontID/SessionID/MaxOrderRef`（C-06）；`Ready` 之前拒绝报单/撤单。
- 产出：登录、登出、掉线重连后均能回到 `Ready` 的状态机，附日志。

**O-04 第 3 步：登录后同步（初始化查询链）**
- 实现：串行查询链（H-06）：结算确认状态与确认（K-01）→ 合约（I-13）→ 账户 → 持仓 → 持仓明细 → 订单 → 成交 → 保证金率/手续费率/经纪公司交易参数（G-12、H-07）；每步等待 `bIsLast`，遇 -2/-3/90 号错误按 H-01~H-03 处理；按选择的私有流订阅模式（B-05）完成订单融合。
- 产出：同步完成后本地订单、持仓、资金与柜台查询一致（见 Q 组对账用例）。

**O-05 第 4 步：报单与回报状态机**
- 实现：统一的报单构造（D-10、E-14、E-16）；本地订单表以 `FrontID+SessionID+OrderRef` 与 `ExchangeID+OrderSysID` 双索引（D-03、D-04）；按 E-02 的 A==B 规则判定订单结束；去重（E-03、E-08）；三条拒单路径统一处理（E-05、E-06）；报单即冻结，拒单/撤单终态解冻（G-01、G-02）。
- 产出：回报时序用例全部通过（见 Q 组）。

**O-06 第 5 步：撤单与并发控制**
- 实现：撤单封装（F-01）；撤单在途标志（F-05）；撤单失败分类（F-04）；改单走“撤单→确认终态→再报”（F-02）；自带限速（F-08）。

**O-07 第 6 步：持仓、资金账本与对账**
- 实现：持仓键与今昨仓（G-04、G-05）；平仓顺序按交易所（G-08）；盈亏口径（G-09）；资金恒等式（G-10）；仅 `OnRtnTrade` 更新持仓（E-01）；定时对账与告警（G-15）。

**O-08 第 7 步：行情**
- 实现：订阅（I-01）；快照差分与 K 线（I-04、I-11）；无效值过滤（I-06）；交易日与夜盘归属（I-07）；非交易时段过滤（I-09）；字段口径校正（I-10）。

**O-09 第 8 步：风控、日志、监控**
- 实现：自成交预防、撤单计数、持仓/开仓限额、价格与时段校验（N-07）；完整日志（N-03）；掉线告警；对账不一致告警。

**O-10 第 9 步：分层测试与上线**
- 实现：先 SimNow 功能测试，再交易所仿真环境行为测试并保留测试报告（M-01）；执行 Q 组测试用例清单；逐项通过 P 组上线自检清单；上线初期小仓位、白天交易时段观察，夜盘、结算后各完整走一遍。

**O-11 Agent 排障的固定顺序**
- 现象排查时按此顺序，不要凭猜测改代码：①读日志里 `Req*` 返回值（-1/-2/-3）；②读 `OnRspError`/`pRspInfo` 的 `ErrorID/ErrorMsg`（GBK 转码后）并对照《14_错误码速查表》；③检查会话状态（是否已认证、登录、结算确认、同步完成）；④检查版本与前置；⑤检查回报时序是否被 E 组规则覆盖；⑥检查是否触发某类流控（H-05）；⑦与柜台查询结果对账；⑧最后才怀疑 API 或柜台缺陷（并向期货公司求证）。

**O-12 Agent 编码时的禁区**
- 不要在 SPI 回调里 `Release`、`sleep`、做同步网络/数据库操作；不要用 `OnRtnOrder` 的成交状态更新持仓；不要对同一订单重复撤单；不要在版本/地址未确认时连接实盘；不要把 4097 当作单纯网络抖动无限重连；不要依赖行情的 `ActionDay`；不要假设回报条数与顺序；不要假设查询无限制；不要在没有明确出处时臆测 CTP 行为——不确定的规则应以官方文档、SDK 头文件、实测日志三者交叉验证并写入注释。

## Q. 测试用例清单

> 全部为（工程建议）。每个用例列出“步骤 → 期望”，建议在 SimNow（功能）与交易所仿真（行为）上各做一遍；与环境相关的差异见 M 组。

### Q-1 登录与认证用例

| 编号 | 步骤 | 期望 |
|---|---|---|
| Q1-01 | 正常连接，认证成功后登录 | 依次收到 `OnFrontConnected`、`OnRspAuthenticate(ErrorID=0)`、`OnRspUserLogin(ErrorID=0)`；保存 FrontID/SessionID/MaxOrderRef |
| Q1-02 | 未认证直接登录（强制认证环境） | 登录被拒；程序不死循环 |
| Q1-03 | AppID 或 AuthCode 错误 | `OnRspAuthenticate` 返回错误；程序不发起登录，且不无限重试 |
| Q1-04 | 密码错误 | 登录失败；不无限自动重登（C 组；注意登录失败会导致断开并触发自动重连） |
| Q1-05 | 重复登录（同一会话再次登录） | 容错处理，不把“重复登录”视为致命错误 |
| Q1-06 | 同一用户多会话直至超限 | 超限会话在 `OnRspUserLogin` 收到“CTP:用户在线会话超出上限” |
| Q1-07 | 版本不匹配（如用错版本库） | 能通过日志发现 4097/无回调，并给出版本核对提示 |
| Q1-08 | 登出后重新登录，且复用 API 实例 | 状态机回到 `Ready`；OrderRef 以新的 `MaxOrderRef` 为起点 |

### Q-2 下单用例

| 编号 | 步骤 | 期望 |
|---|---|---|
| Q2-01 | 限价开仓，价格在盘口挂单（不成交） | 收到 `OnRtnOrder`(未知 'a') → `OnRtnOrder`('3')；`OnRspOrderInsert` 不触发；第 1 次回报 `OrderSysID` 为空，之后非空 |
| Q2-02 | 限价开仓，对手价成交 | 收到状态回报 + `OnRtnTrade`；订单结束按 A==B 判定；持仓/资金与成交对账一致 |
| Q2-03 | 分笔成交（如 4 手分 1+3） | `OnRtnTrade.Volume` 分别 1、3；订单累计 4；A==B 时才结束 |
| Q2-04 | 订单终态回报与成交回报顺序互换（模拟/注入） | 两种顺序下订单都能正确结束，不丢成交 |
| Q2-05 | 重复前态回报（模拟/注入） | 状态机幂等，不重复计成交、不重复解冻 |
| Q2-06 | 资金不足的开仓 | `OnRspOrderInsert` 报错；`OnErrRtnOrderInsert` 回报；本地冻结被回滚 |
| Q2-07 | 平仓量超过可平量 | 报“CTP:平仓量超过持仓量”；本地不重复冻结 |
| Q2-08 | 不填 `UserID` 的错单 | 验证收不到 `OnErrRtnOrderInsert`；填写后能收到（回归 D-06） |
| Q2-09 | 价格超出涨跌停板 / 非最小变动价位 | 被拒；识别 CTP 层拒绝与交易所层拒绝两种形态 |
| Q2-10 | 非交易时段报单 | 被拒或排队（视环境）；日志记录 `StatusMsg` |
| Q2-11 | 市价单（郑商所价格填 0） | 按交易所规则成交或被拒，行为与 E-14、E-16 一致 |
| Q2-12 | FAK / FOK 部分成交与全撤 | 回报形态因交易所而异；终态判定正确；成交量累计正确 |
| Q2-13 | 报单流控（超过每秒限额） | 出现“CTP:下单频率限制”或本地限速生效；报/撤分开计数 |
| Q2-14 | 平仓回报开平标志（大商所/郑商所/中金所） | 成交回报开平标志为 Close('1')；持仓更新不依赖平今/平昨标志 |

### Q-3 撤单用例

| 编号 | 步骤 | 期望 |
|---|---|---|
| Q3-01 | 对挂单用 `ExchangeID+OrderSysID` 撤单 | 收到 `OnRtnOrder` 撤单状态（'5'、OrderSubmitStatus='3'）；未成交量解冻 |
| Q3-02 | 对挂单用 `FrontID+SessionID+OrderRef+InstrumentID` 撤单 | 成功；去掉 `InstrumentID` 时被拒 |
| Q3-03 | 第 1 次回报后（OrderSysID 为空）立即撤单 | 用 OrderRef 方式能撤；OrderSysID 方式失败 |
| Q3-04 | 撤已全成交/已撤销的订单 | 报“已全成交或已撤销”；本地状态不变、不解冻；双回调 `OnRspOrderAction` 与 `OnErrRtnOrderAction` 均被处理 |
| Q3-05 | 撤不存在的订单 | 报“找不到相应报单” |
| Q3-06 | 并发对同一订单撤单 | 只发出一次撤单（撤单在途标志生效），无重复拒单风暴 |
| Q3-07 | 撤单与成交同时发生 | 订单以终态为准；成交量以 `OnRtnTrade` 累计 |
| Q3-08 | 部成部撤 | 终态 Canceled；成交累计与 `VolumeTraded` 一致 |
| Q3-09 | 被交易所拒绝的单（自撤与被拒的区分） | 能用 OrderSysID、`OrderSubmitStatus` 区分自撤与被拒 |
| Q3-10 | 尝试“改单”（ActionFlag 非删除） | 无此功能；改单走撤单再报 |
| Q3-11 | 撤单不填 `UserID` | 验证收不到 `OnErrRtnOrderAction`（回归 D-06） |

### Q-4 断线与恢复用例

| 编号 | 步骤 | 期望 |
|---|---|---|
| Q4-01 | 运行中断开网络，再恢复 | 收到 `OnFrontDisconnected(nReason)`；API 自动重连后 `OnFrontConnected`；自动认证、登录、同步；会话回到 `Ready` |
| Q4-02 | 断线期间有订单成交/撤单（用其他终端操作） | 恢复后本地订单、持仓与柜台一致（QUICK：靠查询；RESUME：靠历史回报；均再对账） |
| Q4-03 | 断线期间本地有在途报单 | 恢复后能确认每个在途订单的最终状态，不重复报单 |
| Q4-04 | 重连后 `FrontID/SessionID/MaxOrderRef` 变化 | OrderRef 计数器、会话过滤使用新值 |
| Q4-05 | 反复断线（模拟 4097 循环） | 退避重连，日志有 `nReason`，不会触发连接数流控 |
| Q4-06 | 进程重启（RESUME/QUICK/RESTART 三种模式各一次） | 按所选模式正确恢复；RESTART 重推的回报被幂等处理 |
| Q4-07 | 行情断线重连后重新订阅 | 重新登录后重新订阅；缺口被标记 |
| Q4-08 | 在 `OnFrontDisconnected` 中不做 `Release` | 无崩溃 |

### Q-6 持仓与资金对账用例

| 编号 | 步骤 | 期望 |
|---|---|---|
| Q6-01 | 无持仓时 `ReqQryInvestorPosition` | 回调中 `pInvestorPosition` 为空、`bIsLast=true`，程序不崩溃、无虚假持仓 |
| Q6-02 | 多头、空头各一笔 | 查询返回两条记录；本地按 `PosiDirection` 区分 |
| Q6-03 | 上期所/能源中心：隔日昨仓 + 今日新开 | 今仓与昨仓为两条记录，`PositionDate` 分别为 '1'、'2'；其他交易所在同一记录中 |
| Q6-04 | 平昨仓后 | `YdPosition` 不变；当前昨仓 = `Position − TodayPosition` |
| Q6-05 | 开仓后全部平仓 | 记录可能仍存在，`Position=0`；本地过滤 |
| Q6-06 | 挂平仓单未成交 | 对应冻结字段增加；可平量 = `Position − 冻结`；再次报平仓超量被拒 |
| Q6-07 | 先开先平：昨仓 + 今仓混合，一次平多手 | 盈亏逐明细计算，与结算后持仓明细一致；昨仓用昨结算价、今仓用开仓价 |
| Q6-08 | 持仓明细查询 | `Volume`/`CloseVolume` 与本地一致；键为 `OpenDate+TradeID`（自成交加 `Direction`） |
| Q6-09 | 账户资金恒等式 | 多个时点：本地计算的 `Balance`、`Available` 与 `ReqQryTradingAccount` 一致（允许结算前后口径差异） |
| Q6-10 | 保证金/手续费估算 | 与账户 `CurrMargin`、`Commission` 对账；偏差定位到费率/价格类型 |
| Q6-11 | 组合持仓（如适用） | 出现组合记录 + 两条分腿记录，汇总时不重复累加 |
| Q6-12 | 日终结算单对账 | 用结算单的明细求和核对出入金、盈亏、手续费；申报费以出金体现 |
| Q6-13 | 查询流控：连续发多个查询 | 串行处理；-2/-3/90 号错误有退避重试；无丢失 |
| Q6-14 | 重新登录/换日后的全量对账 | 以查询为准重建，与重启前本地账本差异为 0 或有明确原因 |
