## A. 一个错误码会推几个回调？——按层分，不是按回调分

M2-4 之前的实现把所有 insert 拒绝都走 `ERR_RTN_ORDER_INSERT`（错单回报）。这是**一个常见误解**：
「错单响应」和「错单回报」是两个不同层的回调，谁先谁后取决于拒绝发生在哪一层。

官方 API 文档把这两层分得很清楚：

| 层 | 拒绝内容 | 回调序列 | shim 呈现 |
|---|---|---|---|
| **报盘机（CTP 层）** | 会话未登录、字段解析失败、BrokerID 不一致、报单字段非法、ExchangeID 不符、条件单/预埋单不支持、流控超限、资金不足、持仓/平今平昨不足 | `OnRspOrderInsert(NULL, pRspInfo, bIsLast)` **仅此一个**；**不跟任何 `OnRtnOrder`** | `OnRspOrderInsert(nullptr, &rsp, nrid, true)`——`pInputOrder` 为 NULL |
| **交易所（撮合层）** | 涨跌停板价、数量规范、最小变动价位 | `OnRspOrderInsert(pInputOrder, {0}, true)` → 紧接着 `OnErrRtnOrderInsert(pInputOrder, pRspInfo)` | 先推成功响应帧，再推 `ERR_RTN_ORDER_INSERT` |
| **撤单拒绝（两层皆可能）** | 找不到报单(25)、状态不当(26)、流控(116)、字段错(23) | **双面**：`OnRspOrderAction(NULL, pRspInfo)` → `OnErrRtnOrderAction(pInputOrderAction, pRspInfo)` | 先 `RSP_ERROR`，再 `ERR_RTN_ORDER_ACTION` |

三条判据（`handlers.rs::reject_insert` 的分流条件就是这个）：

1. 拒绝是否发生在**本地字段/会话/风控校验**阶段——是则 CTP 层，仅响应面；
2. 拒绝码是否属于**交易所交易规则**（163/164/165）——是则交易所层，先成功响应后错单回报；
3. 撤单拒绝**一律双面**——官方《报单回调规则》场景 6/7 明文规定「先响应、后回报」成对出现，
   缺一个都算客户端挂钩不全。

### 为什么这条必须复刻（对齐项目最高原则）

下游客户端常见的两种真实 bug：

- **只挂 `OnRspOrderInsert` 的客户端**：在真实 CTP 上会漏掉全部 163/164/165——因为交易所层拒单
  的 `OnRspOrderInsert` 带的是 `{0}`（成功！），错误只在随后的 `OnErrRtnOrderInsert` 里。
  在 CTPBuddy 上若把 163 也做成 `RSP_ERROR`，这个 bug 就被仿真掩盖了，测试环境通过、上生产炸。
- **按条数计数的客户端**：`OnRtnOrder` 的「前态+新态」两笔本来就翻倍（notes/01），
  撤单再加 `ERR_RTN_ORDER_ACTION` 双面，计数模型必须自己去重。仿真若只推一面，计数 bug 同样被掩盖。

所以：**推错推送面比推错错误码更隐蔽**。错误码错了下游会打日志，推送面错了下游静默漏单。

## B. `ERR_RTN_*` 载荷是 composite：客户端自己的 struct ++ RspInfo

`ERR_RTN_ORDER_INSERT` 的 payload 不是裸 `RspInfoField`，而是

```
[ CThostFtdcInputOrderField (客户端原始请求) ][ CThostFtdcRspInfoField ]
```

`ERR_RTN_ORDER_ACTION` 同理，尾部拼 `CThostFtdcInputOrderActionField`。

- Rust 侧（`send_err_rtn` / `send_err_rtn_action`）：`payload = input.to_vec(); payload.extend_from_slice(&struct_to_bytes(&rsp));`
- shim codegen：`TD_DISPATCH` 行标 `{"payload_input": True}` / `{"payload_input": True, "synth_action": True}`，
  errrtn body 按 `SIZES[input]` 切出前半回填客户端 struct、后半取 RspInfo；
- py SDK：`rsp_info_of(payload)` 对 composite 读**尾部 n 字节**，对裸包读整体——两种都兼容。

**顺序不能反。** 早期实现先拼 RspInfo 再拼 input，shim/py 按相反约定解析，表现为
`m2_journal` 的 163 用例失败（ErrorID 读成垃圾值）。

### C.1 一个真实竞态：同 req_id 的第二帧曾被静默吞掉

第二帧与第一帧**共用请求的 req_id**（协议层如此，`Frame.req_id != 0` 即响应帧）。原 py SDK 读循环：

```python
q = self._pending.get(f.req_id)
if q is not None: q.put(f)          # ← 无条件塞进 pending 队列
elif self._is_rejection(f): self._note_late(f)
```

若两帧在请求线程 `q.get()` 返回并 `pop(_pending)` **之前**都到达，两帧会一起进同一个队列；
请求线程只读一帧，第二帧（错单回报）随队列一起被丢弃——**间歇性丢回报**，表现为
`m2_journal` 的 163 用例时好时坏（实测 4 次里 2 次失败）。

修法（`client.py::_Pending`）：pending 条目记录「是否多帧」与「是否已被应答」。

- unary 请求（`_request`）：第一帧应答请求；同 req_id 的后续 rejection 帧 → late 队列；
- streaming 请求（`_query_once`，`multi=True`）：持续收行直到 `QRY_LAST`，行为不变。

这个坑值得记：**协议允许一请求多帧时，「按 req_id 找队列」和「一请求一帧」的假设不能混用**。

## D. e2e 锁的是什么

`tests/e2e/m2_surface.py` 五段断言，全部对着真实核心跑：

| 段 | 场景 | 断言 |
|---|---|---|
| A1 | insert 116 流控 | `CTPError.kind == "RSP_ERROR"`，`wait_late(ERR_RTN_ORDER_INSERT)` 为 **None** |
| A2 | insert 31 资金不足 | 同上 |
| A3 | insert 16 未知合约 | 同上 |
| B | insert 165 非最小变动价位 | 请求**成功**返回 `RSP_ORDER_INSERT`，随后 `ERR_RTN_ORDER_INSERT` 带 165，且 payload 里能读回客户端自己的 `OrderRef="X1"` 与 `LimitPrice=3497.5` |
| C | cancel 25 找不到报单 | `RSP_ERROR` 先到，**且** `ERR_RTN_ORDER_ACTION` 后到，后者能读回 `OrderRef="NOPE7777"`、`InstrumentID` |

A 段「没有 late 面」是**反向断言**——比「有」更重要：如果哪天有人把 116/31 改成双面，
这条断言会立刻失败。同理 B 段断言的是**有** late 面。

驱动参数：`--order-freq 2`（默认 20/s 打不爆，见脚本内注释），段间 `new_window()` 睡 1.05s
让墙钟窗口翻转——流控是墙钟 1s 窗口，不是计数桶。

## E. 与 journal 的关系

journal 录制的是**核心侧指令生命周期**，与推送面正交：无论走哪个面，拒绝的报单都记
`order_insert` + `submit_status='4'`（拒付报单），撤单记 `order_cancel` + `submit_status='5'`。
`m2_journal.py` 的 163 用例从 journal 侧验证（163 → `late` 面消费 → 抛出 163），
`m2_surface.py` 从客户端侧验证——两侧对着同一份核心行为，互为交叉验证。

## F. 遗留

- `91 EXCHANGE_RTNERROR`：常量已留、语义是「交易所返回的错误」，但交易所侧拒单**转发**路径
  尚未接线（真实 CTP 用它承载交易所回单的失败原因）。与 #43 相邻。
- `42 SETTLEMENT_INFO_NOT_CONFIRMED`：确认报文已收并回显，但报单**尚未做结算确认前置门禁**——
  真实 CTP 未结算确认就报单会拒；这是「可落地」缺口，已登记在错误码全集。
