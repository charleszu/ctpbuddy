# CTP 爬坑笔记（B-pitfalls）

> 来源：《CTP开发爬坑指北》一~四、《CTP爬坑指北》五~七、《综合交易平台交易API特别说明》、《综合交易平台API开发常见问题列表》（2009，上期技术）。
> 下文简称：指北一~四、指北五~七、API特别说明、FAQ。
> 组织方式：坑 → 真实原因 → 正确做法。适用于「实现一个 CTP 兼容柜台/网关」时的行为对齐。

---

## A. 查询 / 会话相关

### A1. 查询流控：1 秒最多 1 个查询
- 坑：并发/循环查询被拒，返回 -2/-3。
- 原因：CTP 只对查询限流、不对交易指令限流。"综合交易平台仅对查询进行流量限制，对交易指令没有限制。如果有在途的查询，不允许发新的查询。1 秒钟最多允许发送 1 个查询。返回值"-2"表示"未处理请求超过许可数"，"-3"表示"每秒发送请求数超过许可数"。"（FAQ #41）
- 正确做法：网关侧串行化查询队列；有在途查询时缓存后续请求；收到 -2/-3 做退避重试而非立即重发。

### A2. 单账户多会话（多点登录）
- 坑：多实例登录后，回报里混有别的会话的单子。
- 原因："Thost 支持同一个投资者帐号创建多个 TradeApi 对象同时登入系统进行交易。"（API特别说明）
- 正确做法：登录后记录本会话 FrontID+SessionID；收 OnRtnOrder 用它过滤自己的单；再由 FrontID+SessionID+OrderRef 映射到 ExchangeID+OrderSysID，用后者过滤 OnRtnTrade。注意该办法仅对当前会话内报单有效。

### A3. 断连时崩溃 / 无法退出
- 坑：OnFrontDisconnected 里调 Release() 崩溃。
- 原因：SPI 回调线程与 API 线程模型冲突；低版本 API 频繁断连本身也有极低概率崩溃（6.3.19 起修复）。
- 正确做法："如果要释放 API，需要在别的线程中进行，而不能在 SPI 函数中直接执行释放操作，而且，创建与释放 API 实例，最好是在同一个线程中。"（指北三 #04）；或用 6.3.19+ 版本；非交易时段释放、开盘前重建。

### A4. 初始化与释放顺序
- 初始化顺序（API特别说明 第5节）：CreateFtdcTraderApi → RegisterSpi → SubscribePublicTopic / SubscribePrivateTopic → RegisterFront（可多个，自动择一）→ Init → OnFrontConnected → ReqUserLogin。
- 释放顺序（FAQ #20）：`RegisterSpi(NULL)` → `Release()` → `delete SPI`。先摘 SPI 再 Release，否则 Release 时死机概率很高。
- 每天首次登录成功后必须 ReqQrySettlementInfo + ReqSettlementInfoConfirm 才能发报单/撤单/预埋单；当天已确认过的会话再次登录可直接交易（API特别说明、指北五 #03）。

### A5. 线程模型
- 坑：多线程调用 API 是否安全？SPI 里能做重活吗？
- 结论："api,spi 是不同的线程、api 可以同时被多个线程调用……这些特性和平台无关。"（FAQ #19；指北五 #02 同）
- 正确做法：API（Req*）可多线程并发调用；SPI 回调在独立线程，网关应把回报入队后转业务线程处理，不在 SPI 内阻塞。

### A6. 流缓存策略 THOST_TERT_RESTART / QUICK / RESUME
- 含义（API特别说明样例注释）：
  - `TERT_RESTART`：从本交易日开始重传；
  - `TERT_RESUME`：从上次收到的续传；
  - `TERT_QUICK`：只传送登录后（私有/公共）流的内容。
- 坑1：登录后把上次下单结果重推一遍。原因：订阅时选了 TERT_RESTART（FAQ #34）。不想要重传就选 QUICK/RESUME。
- 坑2：TradeApi 与 MdApi 两个 dll 放同一目录且用 Resume 模式，会互相覆盖本地流文件，重启后数据流不连续。正确做法：CreateFtdcUserApi 时用第一个参数指定各自不同的流文件路径（FAQ #18）。
- 坑3：流文件是本地二进制缓存，RESUME 依赖它跨重启续传——网关自实现时必须定义清楚流缓存语义。

### A7. 头文件与库版本、ABI
- 坑：订阅合约收到退订响应；结构怪异的崩溃。
- 原因："不同版本的 CTP 的 API，是不能混用头文件和库文件的……包括接口的新增、修改、删除，新增数据结构，数据结构体的新增、修改、删除字段等。"（指北六 #02）；头文件 v6.3.15 配库 v6.3.19 即出现"订阅却收到退订响应"（指北三 #03）。
- 另：CTP 的 LIB 是标准 8 字节对齐（指北六 #02、FAQ #24）。网关协议设计注意对齐与字段序。
- GDB 调试时程序莫名停止：CTP API 内部用 SIGUSR1，需 `handle SIGUSR1 nostop noprint`（指北二 #02）。

## B. 报单 / 回报相关

### B1. 报单被拒却收不到 OnErrRtnOrderInsert
- 原因："报单时没有填写 UserID 字段。CTP 交易核心在收到报单时，并不会校验 UserID 字段，但拒单后处理向该账户的各个 API 会话推送 OnErrRtnOrderInsert 通知时，却和报单中的 UserID 字段相关。"（指北二 #01）
- 正确做法：报单请求里 UserID 与 InvestorID 都填有效值（普通用户二者同为投资者代码；操作员代客下单时 UserID=操作员、InvestorID=客户）（指北四 #04、FAQ #21）。

### B2. 报单/撤单的两阶段响应语义
- "因为 TraderApi 是异步处理的，所以交易指令都是分 2 阶段提交。"（API特别说明 第1节）
- 报单：参数校验不过 → OnRspOrderInsert（含错误码）；接受 → 不返回 OnRspOrderInsert，而是 OnRtnOrder；交易所通过校验 → OnRtnOrder + OnRtnTrade；交易所判错 → OnErrRtnOrder。撤单同理（OnRspOrderAction / OnRtnOrder / OnErrRtnOrderAction）。
- 注意 OnRspOrderInsert 只在被拒时出现——"用户报单后，如果正确根本不会'马上收到报单响应 OnRspOrderInsert'"（FAQ #36）。
- 涨跌停板外的单：CTP 先收单，"CTP 收到报单就新增一条记录，然后收到交易所的 OnErrRtnOrder 后，修改委托表里的记录，触发 OnRtnOrder"（FAQ #36）——即超停板的废单也只体现为 OnRtnOrder 状态变化 + OnErrRtnOrder，OnRtnOrder 本身不带错误码，网关要在回报里补错误信息。

### B3. OnRtnOrder 重复推送
- 现象：报一个单先推"已报"，发起撤单后又推一次"未成交"再推"撤消"。
- 原因："投资者发出 1 个操作，都会收到 2 条回报……就是 CTP 应答一下，然后交易所又应答一下。"（FAQ #37）
- 正确做法：状态机按 OrderStatus 推进，对同状态重复推送做去重/幂等，别当成新事件。

### B4. 订单唯一性与三种撤单 key
- 坑：不知道拿什么字段撤单、关联成交。
- 三种 key（指北一 #02、API特别说明 第2节）：
  1. ExchangeID + OrderSysID（推荐）。OrderSysID 是数字字符串、可能右对齐带空格（如" 012865"），不同交易所位数不齐——"不建议对它的空格部分进行截断处理"；且"CTP 报单的第一个回报里面，报单编号是空值，这个是无法拿来撤单的"。
  2. FrontID + SessionID + OrderRef。需另填 InstrumentID；"部分交易所在订单被交易所接收之前……不支持这种撤单方式"。
  3. ExchangeID + TraderID + OrderLocalID（TraderID 是交易所交易员代码，不是 TradeID 成交编号）。
- 撤单还需 BrokerID/UserID/InvestorID/InstrumentID 五个关键字 + OrderActionRef（用户自设、保持递增，不填则 Thost 代设）+ ActionFlag=THOST_FTDC_AF_Delete（API特别说明 第2节）。
- 关联回报还可用 RequestID，但"CTP 允许有重复的 RequestID……无法区分同一个账户的不同会话之间的下单"（指北一 #02）；且注意 RequestID ≠ nRequestID（函数参数）。

### B5. OrderRef 与 FrontID+SessionID 唯一性
- 登录响应给 FrontID、SessionID、MaxOrderRef；OrderRef 从 MaxOrderRef 起递增，不填则 Thost 分配（API特别说明 第1/5节）。
- "FrontID + SessionID + OrderRef，作为主键，当 FrontID + SessionID 变更后 MaxOrderRef 将重置。"（FAQ #32）；"报单引用由客户端自主管理，后台仅要求该字段单调递增。"（FAQ #33）
- OrderRef 本质是有符号 32 位整数（"读作字符串，写作整数"），允许负数，超范围（±2147483647 附近）"可能会被 CTP 服务器端判定为 0 从而不符合规则导致报单失败"；不自持递增会报"重复的报单"（指北一 #02）。部分公司柜台用 64 位，但建议按 32 位处理。

### B6. 成交回报与订单的关联、分笔成交量
- OnRtnTrade 中没有 FrontID+SessionID，要用 ExchangeID+OrderSysID 或 ExchangeID+TraderID+OrderLocalID 反查订单（指北一 #03、API特别说明 第4节）。
- OnRtnTrade.Volume 只是本笔成交数量，总成交量看 OnRtnOrder.VolumeTraded（例：4 手单分 1+3 两笔成交）（指北一 #03）。
- 组合合约订单会按腿分别推送至少 2 次 OnRtnTrade（指北一 #03）。

### B7. 成交开平标志 ≠ 报单开平标志
- "对于上期所和能源中心，成交与报单的开平方向，是相同的。而对大商所、郑商所和中金所……如果是平仓，则无论你报单时使用的开平方向是什么（平今，平昨等），成交通知中的开平方向都是 THOST_FTDC_OF_Close ('1')。"（指北三 #01）
- SimNow 却按上期所规则随报单返回平今/平昨——仿真环境与实盘规则不一致，是隐藏的坑（指北三 #01）。

### B8. 撤单来源区分（自撤 vs 被拒）
- 判断 OrderSysID 是否为空：非空说明进过交易所撮合队列，是自撤；空则是被拒或未进交易所就被撤（指北三 #02）。
- 或看 ActiveUserID：自撤时为本账户名，否则为空；或看 OrderSubmitStatus：自撤时为 OSS_Accepted('3')，否则为 OSS_InsertRejected('4')（指北三 #02）。

### B9. 最终状态与自动挂起
- 最终状态：AllTraded、PartTradedNotQueueing、NoTradeNotQueueing、Canceled、Touched（条件单特有）；"部成部撤"的最终状态就是 Canceled（指北四 #01、FAQ #40）。
- "部分成交不在队列中/未成交不在队列中"是历史产物：来自上期所的自动挂起标志，断线客户的未成交单会被挂起离队；目前系统该标志为 0，永不挂起（指北四 #01、FAQ #31）。
- ReqOrderAction 目前只实现撤单，挂起/激活/修改"无此功能"（FAQ #42）——这就是"CTP:无此功能"类报错的一类真实原因：功能压根未实现。

### B10. 报单字段固定值 / 市价单
- 报单时须设：VolumeCondition=THOST_FTDC_VC_AV；MinVolume=1；ForceCloseReason=THOST_FTDC_FCC_NotForceClose；IsAutoSuspend=0；UserForceClose=0（API特别说明 第1节）。
- 立即市价单：OrderPriceType=AnyPrice、LimitPrice=0、TimeCondition=IOC；触发单填 ContingentCondition+StopPrice、限价、GFD（API特别说明 第1节）。
- "目前郑商所(CZCE)的市价类型报单，需要报单时将报单价格(LimitPrice)填为 0，否则郑商所会拒绝报单"——建议所有市价单价格都填 0（指北四 #02）。
- CombOffsetFlag/CombHedgeFlag 虽为数组，现在所有合约只填 [0] 位即可（指北五 #01、FAQ #45）。
- 平仓标志：上期所区分昨仓（Close）与今仓（CloseToday）；其他交易所统一 Close，填 CloseToday 后台也会转换（API特别说明 第1节、FAQ #43）。

### B11. 策略标识 InvestUnitID（取巧）
- 发单/回报/成交都有 InvestUnitID(char[17])："回报中的 InvestUnitID 值等于报单时填写的 InvestUnitID 值，而且它也不像 OrderRef 要求必须实际是一个整数，同时它是允许重复的。"（指北七 #02）可借它传策略编号；但作者明言这是"投机取巧钻系统的空子"，网关实现不应依赖。

### B12. 条件单 / GTC / 预埋单
- 条件单 v4.1 起支持；"gtc 不会支持，现在国内的期货交易所还不支持过夜挂单！"CTP 只提供非交易时段预埋单（FAQ #13）。即 GTC 类请求在 CTP 网关应直接拒绝。

## C. 资金 / 持仓相关

### C1. 保证金计算参数从哪来
- 公式：持仓保证金 = 持仓数量 × 合约乘数 × 基准价格 × 合约保证金率（指北二 #03）。
- 基准价格类型四种：昨结算价('1')、最新价('2')、成交均价('3')、开仓价('4')，由期货公司后台配置，"可通过 CTP 查询经纪公司交易参数获得你的账户的盈亏算法和保证金价格类型等"——ReqQryBrokerTradingParams / OnRspQryBrokerTradingParams（MarginPriceType、Algorithm、AvailIncludeCloseProfit、OptionRoyaltyPriceType 等）（指北二 #03）。
- "保证金算法：历史仓用昨结算价计算，今仓可以选择（成交均价/开仓价/结算价）……该项配置由期货公司管理人员在后台进行配置"（FAQ #14）。快期等把参数放配置文件（指北二 #03）。
- 冻结保证金 = 价格 × 未成交手数 × 合约乘数 × 保证金率(按金额) + 未成交手数 × 保证金率(按手)（FAQ #15）。

### C2. 费率查询的返回语义
- ReqQryInstrumentMarginRate / ReqQryInstrumentCommissionRate 返回的是最终费率（绝对值），已含交易所费率及调整（FAQ #28、指北一 #04）。
- 返回合约代码是品种代码（如查 IF2203 返回 IF）= 该合约用品种通用费率；Investor 返回 "000000" = 所有投资者通用费率（指北一 #04、FAQ #35）。
- 查询时合约代码填空 = 只返回持仓中合约的费率（需当日曾有持仓）；要知道全市场费率只能逐合约查（指北一 #04）。
- 交易所标准保证金率：查合约 OnRspQryInstrument 响应里的多头/空头保证金率（指北一 #04）。

### C3. 持仓字段语义
- 昨持仓是当日开盘前的初始值，不随平仓减少："当前时侯的昨持仓=总持仓-今持仓。YdPosition := Position - TodayPosition。"（FAQ #29）
- 可用资金的算法（如浮盈可开仓）是"汇总计算后再应用相应算法"，不是分笔算（FAQ #17）。基本保证金/保底资金 = Reserve（FAQ #16）。

### C4. 各交易所平仓顺序与手续费"双持仓"
- 大商所/广期所/郑商所：先开先平、优先平昨；但平今手续费有减免时优先平今（指北一 #05）。
- 中金所：持仓系统先开先平优先平昨，但手续费按"优先平今"的另一套并行持仓系统计算（指北一 #05 给了 2 昨+1 今、两次卖平 = 300+20=320 元的完整例子）。
- 上期所/能源中心：报单时自行指定平今/平昨，各自内部先开先平（指北一 #05）。

### C5. 申报费（OrderCommRate）
- 中金所股指、上期能源原油、大商所棕榈油、郑商所 PTA 等按笔收申报费，报单、撤单都计；FAK/FOK 的自动撤单也计入，"一个自动撤单的 FAK/FOK 单，就等于是 2 次的信息量(报单+撤单)"（指北六 #01）。
- 坑：ReqQryInstrumentOrderCommRate 可查，但"这个接口查询得到的响应里数据是空指针，即查不到具体的申报费率"；且"CTP 盘中实时资金也不包含申报费，即是说申报费只体现在结算单中"（指北六 #01）。

### C6. 结算单（乱码、分片、确认）
- 编码：CTP 字符串一律 GBK，UTF8 终端显示即乱码（指北三 #05）。
- 分片：Content 分多条返回，中文可能在两条响应交界处被拆半个字符——"每次收到一条查询结算单响应，就把它解码显示出来……就无法解析最后一个被拆成两半的中文字符了"。正确做法：用大 char 数组拼接全部响应，最后统一解码（指北三 #05 给了 strncpy 拼接示例；python 等语言要用 byte 数组而非 string）。
- 流程：ReqQrySettlementInfoConfirm 先查当天是否已确认（无记录=未确认），未确认才展示+ReqSettlementInfoConfirm（指北五 #03、FAQ #12）。
- 结算单格式长期稳定可自动解析，指北五 #04 给出完整 settlement_*.ini 格式化文件模板；历史成交/平仓明细也靠历史结算单获取（FAQ #27）。

### C7. 组合持仓与组合保证金
- 大商所/郑商所结算后可能自动把合适持仓配对成组合持仓（跨品种、跨期），有的品种需主动申请（指北七 #03）。
- 组合保证金优惠系统：中金所 RCAMS、上期所 PMM、郑商所 SPBM、大商所"汝乐"，规则复杂——"要在这么多复杂规则的加持下算准保证金，实际是非常困难的"，建议用简单通用规则（如大额单边）维护（指北七 #03）。

## D. 行情相关

### D1. TradingDay / ActionDay / 时间戳
- 日盘 TradingDay=ActionDay=交易日；夜盘属于下一交易日的日盘（周五夜盘属于下周一）。各交易所规则不一，"只有上期所/能源中心的日期，是准确的"（指北一 #01）。
- 稳妥取法：用交易/行情 API 登录响应里的 TradingDay，或静态函数 GetTradingDay()；OnRtnTrade/OnRtnOrder 的 TradingDay 都准确；TradeDate/ActionDay 不可靠（指北一 #01）。
- 取巧办法：本地系统日期作实际日期，交易日取"当前时间+4 小时"（特判周五→周一）（指北一 #01）。

### D2. 行情量价字段需自校正
- OnRtnDepthMarketData 的 Turnover 与 AveragePrice "是不正确的……交易终端用到该数据时需要自行调整"（FAQ #23）：
  - 郑商所：当日均价正确、成交金额需乘合约乘数；
  - 大商所：当日均价需除以合约乘数、成交金额正确；
  - 上期所：同大商所（均价除乘数、金额正确）。

### D3. 订阅/退订异常
- 订阅合约却收到退订响应：①行情 API 连到了交易前置地址；②头文件与库版本不一致（指北三 #03）。
- 断线后行情不回补、无历史行情："综合交易平台也不提供行情回补机制……程序化交易终端可以通过多路连接的方式降低断线风险，或是托管策略服务器"（FAQ #11）。网关设计必须考虑补行情/容灾。
- OnHeartBeatWarning"永远不会发生，已经对 API 用户屏蔽了该响应"（FAQ #30）——不要拿它做心跳逻辑。

### D4. 收盘后仍有行情
- 盘后期转现、TAS 继续成交推送；郑商所盘后继续推；"在盘后（一般16点前），会推送一次包含当天的结算价的行情快照，我们可以从中提前一步取得结算价"（指北七 #04）。别把 15:00 后的快照当异常。

### D5. 第三方行情软件数据不一致
- 快期3/博易大师等连的是软件商自建行情源，不是 CTP 行情前置；现手/增仓等盘口数据需自行从 CTP 行情计算；组合套利合约"最新价"是软件用两腿价差合成的（指北四 #03）。对标快 CTP 网关时这些字段都不应由网关提供。

## E. 其他（实现 CTP 兼容柜台/网关的陷阱）

### E1. 认证与穿透式监管（ReqAuthenticate / 终端信息上报）
- 直连模式：终端连前置后先 ReqAuthenticate，认证成功再 ReqUserLogin，"这一流程中 CTP API 自动采集终端信息并上报到期货公司"，全程一个 API 实例（指北六 #03）。
- 中继模式：终端用 CTP 采集库 CTP_GetSystemInfo 采集 ClientSystemInfo，连 AppID 一起给中继服务器，由中继服务器上报 CTP。上报接口："多对多"用 RegisterUserSystemInfo（终端认证成功后、用户登录前调用），"一对多"用 SubmitUserSystemInfo（操作员登录后可多次调用上报客户信息）（指北六 #03）。
- 上报接口返回 0 = 成功，非 0 = "CTP 对这个终端认证失败"；终端 ClientAppID 不正确会上报失败，此时应断开与该终端的连接——中继服务器对终端的认证是间接通过 CTP 上报接口完成的（指北六 #03）。
- 终端信息不是字符串而是可能含 '\0' 的字符数组，必须 memcpy 不能用 strncpy/strcpy；python/java 用字符数组而非 string（指北六 #03）。
- "一对多"（操作员登录）只有一个 API 实例，操作员登录后即可代客户下单，客户无需给密码；多账户回报靠 InvestorID 区分（指北六 #03）。"多对多"每终端一个 API 实例，终端断开即销毁（指北六 #03）。
- 穿透式监管落地要求：期货公司账户申请 CTP 程序化接入时，客户须先在交易所仿真环境测试并填测试报告（指北二 #04）。

### E2. 仿真环境的差异
- SimNow 与交易所仿真环境是两套系统；期货公司仿真环境都接交易所仿真环境，不同公司账户可能相互撮合；部分公司在仿真环境限制品种/权限（禁查结算单、禁撤单等）；中金所仿真有自成交风控和"价格保护带"（报单价不得偏离最新价一定幅度）（指北二 #04）。
- SimNow 行情开平价等规则走上期所规则，与实盘大商所等不一致（见 B7）；模拟环境（2009 FAQ 时代）在"连续交易→非交易状态"切换时会停行情转发 5 分钟、且不像生产环境每天校时（FAQ #6）。

### E3. 合约/品种查询
- ReqQryProduct / ReqQryInstrument；v6.5.1+ 有 ReqQryClassifiedInstrument，ClassType=THOST_FTDC_INS_OPTION 可直接查期权；低于 v6.5.1 只能查全部再按 ProductClass 过滤（指北七 #01）。
- 新接口查全市场也要给 TradingType/ClassType 有效值（如 TD_ALL/INS_ALL），"切不可直接将它们设为 0"（指北七 #01）。
- 合约名称、品种名称、最小变动价位等字段由期货公司自行设置、无统一标准，同公司品种表与合约表都可能互相矛盾——"我们不能期待这些信息它们是完全正确的"，建议自建合约信息表（指北七 #01）。
- 能否交易：当天能否交易查 IsTrading；此刻能否交易看合约状态（仅上期所）或交易所状态；InstLifePhase 不可靠（DCE/CZCE 不盘中推单合约状态）（FAQ #44）。交易所状态变化走 OnRtnInstrumentStatus（FAQ #39）。

### E4. 银期转账 TradeCode
- 业务功能码为 6 位数字，两端发起规则不同：101xxx 银行发起转帐开户/销户/账号变更；102xxx 银行发起资金划转；202001/202002 期货发起入金/出金；204002 期货端查银行余额；901001/901002 个人银期直通车开关；905001~905003 平台期商签到/签退/同步密钥等（指北四 #05、FAQ #26 完整列表）。网关实现银期功能时 TradeCode 必须严格按此枚举，填错即"无此功能/业务不支持"。

### E5. "CTP:无此功能"类报错的真实原因归类
- 功能未实现：ReqOrderAction 只支持撤单（挂起/激活/修改未实现，FAQ #42）；GTC 挂单不支持（FAQ #13）。
- 版本不够：ReqQryClassifiedInstrument 需 v6.5.1+（指北七 #01）；OnErrRtnOrderInsert 依赖报单填了 UserID（指北二 #01）。
- 数据为空/未维护：申报费查询返回空指针（指北六 #01）；行情不回补（FAQ #11）；OnHeartBeatWarning 被屏蔽（FAQ #30）。
- 参数非法：OrderRef 超 32 位范围被判定为 0、不自增报"重复的报单"（指北一 #02）；郑商所市价单价格非 0 被拒（指北四 #02）。
- 结论：实现兼容柜台时，对"未实现/不支持"的功能应尽早返回明确错误码，而不是静默丢弃。

### E6. 其他杂项
- 代理服务器：RegisterFront 连接字符串支持 sock4/sock4a/sock5，如 `tcp://front:26205 sock5://user:pass@127.0.0.1:10001`（FAQ #25）。
- 报单必要条件回顾：每天首次登录须结算单确认（A4）；报单必填 UserID（B1）；报单被交易所拒也走 OnRtnOrder+OnErrRtnOrder 而非 OnRspOrderInsert（B2）。
- CTP 字符串全 GBK（结算单/合约中文名等）（指北三 #05）；LIB 8 字节对齐（FAQ #24）；API/SPI 分线程、API 多线程安全（A5）。
- 模拟环境接入地址与申请方式（FAQ #1~#5，2009 年资料）：asp-sim2-front1...:26205 / md1...:26213，BrokerID=2030——仅作功能测试，勿做策略测试。
