## A. 柜台系统结构（S1）

### A1. 为什么必须经期货公司（监管要求）

客户端**不能直连交易所**，中间必须经过期货公司（Broker）的系统，即「柜台系统」。

```
客户端 (程序化 API)  →  期货公司「柜台系统」  →  上期所 / 交易所中心 / 中金所 / 大商所 / 郑商所
```

### A2. 主席 vs 次席（S1，重要）

期货公司有**多套**柜台系统，功能上分两类：

| 类型 | 功能 | 定位 |
|---|---|---|
| **主席系统** | 功能全面，支持出入金、盘后结算等 | **一般客户都在主席系统上交易** |
| 次席系统 | 一般只做下单及撤单，追求低延迟 | 为对时延要求高的客户准备 |

原文："讲就的是高吞吐量与高可靠性，一般客户都是在主席系统上交易。"

**次席的排队规则**：同时报出的相同订单，**次席的单子会先到交易所撮合**。不过报单如何最快地到达交易所由很多因素决定，测穿透时间有很多学问。

> **CTPBuddy 落点**：本地仿真没有主席/次席之分，也**不应有**——复刻"次席先到"会破坏确定性（§11.2 确定性不变量）。但这条解释了真实 CTP 上同价位同品种报单时**成交归属为何不可复现**：报单在柜台侧的排队位置本身就是不确定量。本地仿真给出确定答案，正是它作为测试基础设施的价值所在（对照知识库 §1 关于延迟不承诺的立场）。

## B. 登录所需的六项信息（S1 §2）

| # | 信息 | 说明 |
|---|---|---|
| 1 | `BrokerID` | 期货公司在 CTP 上的编码，**四位**（如海通 8000） |
| 2 | `TradeFront` / `MarketFront` | 交易前置 / 行情前置 IP 地址 |
| 3 | `InvestorID`（`UserID`, `InvestUnitID`） | 客户在 CTP 上的唯一 ID，开户后由期货公司分配。`UserID` 是操作员代码，`InvestUnitID` 是投资单元代码，普通投资者**填 `InvestID` 即可** |
| 4 | `Password` | 开户时设置的密码。**开户首次登录必须修改密码** |
| 5 | `AppID` | 客户端软件代码（配合穿透式监管，见 §D） |
| 6 | `AuthCode` | 客户端软件认证码（期货公司发出，与 AppID 一一对应） |

要点：1~2 对**同一期货公司同一套系统的所有客户都一样**；开户时在哪家期货公司就用哪家公司的信息；也可向期货公司索取或查客服。

## C. API 架构与初始化（S2）

### C1. 三段式调用（异步）

以登录为例（原文顺序）：

1. 客户端调用 API 函数 `ReqUserLogin`，将登录信息写入动态库底层维护的缓存；
2. 动态库**从缓存取数据**通过 tcp 链接发往 CTP 前置；
3. 动态库内**直接线程**通过 tcp 链接读取 CTP 的回复，然后回调 API 中的函数 `OnRspUserLogin`；
4. 客户端在继承实现 `OnRspUserLogin` 函数中处理自己的业务逻辑。

"其实这也是国内市场上（包括交易所）大部分异步 API 的基本架构。"

**关键推论（对 CTPBuddy 架构的直接约束）**：请求读取（缓存）与响应读取（socket）是**同一个底层线程**的两段。这解释了之九 §一 的"sleep 治不好查询流控"（见 notes/12 §A2）。

### C2. 接口文件清单（S2 §2，以 win64 为例）

| 文件 | 职责 |
|---|---|
| `thosttraderapi.py` | 交易头文件 |
| `_thosttraderapi.pyd` | 交易库转换文件 |
| `thosttraderapi.dll` | 交易官方动态库（穿透式为 `thosttraderapi_se.dll`） |
| `thostmduserapi.py` / `_thostmduserapi.pyd` | 行情同上两个 |
| `thostmduserapi.dll` | 行情官方动态库（穿透式 `thostmduserapi_se.dll`） |

"API 分为交易 3 个文件，主要负责认证，登录，报单，撤单，查资金，查持仓等功能；行情 3 个文件，主要负责订阅收取行情。**两部分可以独立运行**。"

> **CTPBuddy 落点**：CTPBuddy 走 **DLL 同名替换**路线（DESIGN ADR），因此下游只需替换 `thosttraderapi.dll` / `thostmduserapi.dll`，**不需要**切换到 `_se.dll`。这与本文档作者的用法一致。

### C3. 初始化函数序列（S2 §3）

```python
traderapi = api.CThostFtdcTraderApi_CreateFtdcTraderApi()  # 1 创建 API 实例
tradespi = CTradeSpi(traderapi)                          # 2 创建 SPI 实例（可继承）
tradespi.RegisterSpi(tradespi)                           # 3 向创建的 SPI 实例注册实例
traderapi.RegisterFront(tradeapi.FrontAddr)               # 4 注册前置地址
tradeapi.SubscribePrivateTopic(api.THOST_TERT_QUICK)      # 5 订阅私有流
tradeapi.SubscribePublicTopic(api.THOST_TERT_QUICK)       #   订阅公共流
tradeapi.Init()                                          # 6 API 启动，后台自动连接注册地址
tradeapi.Join()                                          # 7 Join 阻塞等待 api 实例创建内部线程结束
```

每一步注释（原文）：

| 步 | 作用 |
|---|---|
| 4 | 订阅/连接/断开 三种，分断点续传 |
| 5 | 订阅主题是将 CTP 前置的 IP 地址注册进 API 实例内 |
| 6 | Init 之后**启动一个内部线程读写**，并连接 CTP 前置 |
| 7 | **Join 函数是使得函数阻塞在这里**，等待 api 实例创建的内部线程的结束；内部线程需要调用 `Release` 才会释放结束 |

**顺序要点**：`Init()` 必须在 `RegisterFront` 之后；`RegisterSpi` 必须在 `Init()` 之前（否则收不到任何回调）。

### C4. 请求/回调函数名一一对应

`CThostFtdcTraderApi` 类的**请求函数**与 `CThostFtdcTraderSpi` 类的**回调函数**名**存在一一对应关系**。例如请求 `ReqUserLogin` ↔ 回调 `OnRspUserLogin`。实现时继承 `CThostFtdcTraderSpi` 并重写对应函数即可接住回复。

## D. 穿透式监管与认证（S3，全新）

### D1. 背景与范围

依据证监会《关于进一步加强期货经营机构客户交易终端信息采集有关事项的公告》及期货市场监控中心《期货公司客户交易终端信息采集及接入认证技术规范》：

> **监控中心为了方便监管，需求采集所有通过期货公司入场交易的客户的本地终端信息。**

- 采集范围 = **所有在监控中心报备过的平台厂商**都必须提供该功能；其他主席（如金仕达）不采集，次席（如闪策、易盛）不采集。
- 采集内容：IP、MAC、操作系统版本、硬盘序列号、系统分区等。**不是如某些传言"扫描硬盘文件"**。
- **API 底层已用监控中心下发的公钥加密，只有监控中心持有私钥解密**；柜台厂商、期货公司、交易所都**无法看到明文**。

### D2. 四种接入模式

| 模式 | 含义 |
|---|---|
| **直连模式** | 客户直接用 CTP API 连期货公司柜台。市场上绝大多数程序化投资者属此模式；**像快期这样的客户端也是直连** |
| **中继模式** | 第三方软件厂商在第三方服务器上接单，再在服务器上调用 CTP API 报单。第三方厂商即中继 |
| **多对多中继** | 第三方厂商为每个投资者单独创建与 CTP 的链路。如文华财经云条件单——投资者订单保存在文华云服务器上，**与 CTP 的链路仍在文华服务器**，条件到达就发到 CTP |
| **多对一** | 第三方厂商只建一个与 CTP 的链路，所有投资者共用。**只能为该交易员/下单投资者报单**，多用于期货公司内部软件和场外中介 |

### D3. 自开发投资者必须做什么（CTPBuddy 强约束）

> **一句话：在 `ReqUserLogin` 之前需要先调用 `ReqAuthenticate`。**

用第三方厂商客户端（如快期、博易）的投资者**什么都不需要做**——厂商已向期货公司报备 AppID，软件内部逻辑写好了。

自开发投资者须做两步：

1. 向期货公司申请认证码（从官网开用户或联系经纪人），提交：

| 字段 | 填写 |
|---|---|
| 客户号 | 就是交易账号 |
| 软件名称 | 如 `**量化软件` |
| APPID | **自己命名的**，监控中心给出命名规范 |
| 连接方式 | 直连类型终端 |

APPID 命名示例：`client_abcdf_1.0.0`（个人开发终端）、`pobo_iee_1.4.0.0`（第三方终端）、`poboAPP_ijsse_2.0.0.0`（中继厂商）。

2. 修改程序登录逻辑（**关键：改在 `OnFrontConnected` 里**）：

```cpp
void CUser::OnFrontConnected() {
    static const char *version = m_pUserApi->GetApiVersion();
    CThostFtdcReqAuthenticateField field;
    memset(&field, 0, sizeof(field));
    strcpy(field.BrokerID, "8000");
    strcpy(field.UserID, "001888");
    strcpy(field.AppID, "XY_Q7_V1.0");
    strcpy(field.AuthCode, "5A5P4V7AZ5LCFEAK");
    return m_pUserApi->ReqAuthenticate(&field, 5);
}
```

在 `OnRspAuthenticate` 中判 `ErrorID == 0` 再调 `ReqUserLogin()`；否则打印错误、**不发登录**。

> **⚠️ 字段易错点（原文）**："其实 `ReqAuthenticate` 函数早就有 了，但以前是通过 `UserProductInfo` 和 `AuthCode` 这两个字段绑定验证，现 在 `UserProductInfo` 废弃不用，改为 `AppID` 了，填写时注意不要出错。"
>
> 即：**`UserProductInfo` 已废弃**，认证走 `AppID` + `AuthCode`，两者由期货公司发给客户、**一一对应**。

> **CTPBuddy 落点（任务 20 已实现）**：标准 `ReqAuthenticate` 已接入现有 CTPBuddy JSON `AUTH` handshake，并在显式请求完成时回调 `OnRspAuthenticate`；显式认证成功后保存并绑定 `BrokerID/UserID`，后续 `ReqUserLogin` 必须使用同一身份，服务端 `on_login` 再校验连接认证绑定，防止 Auth A → Login B。自动由 `ReqUserLogin` 触发的内部 AUTH 仍保持兼容，且不会额外触发 `OnRspAuthenticate`。`AuthCode`/`AppID` 作为协议字段透传，当前核心只校验身份绑定，不伪造柜台授权规则。本地空字段错误使用官方 `15 BAD_FIELD`，未认证登录使用 `64 NOT_AUTHENT`；`auth_in_flight` 时 `ReqAuthenticate` 同步返回 `-2`，不再返回 0 后异步 `-3`。已认证重复认证和断线认证失败没有确认精确柜台重复码，采用已实现 `63 AUTH_FAILED`（`CTP:客户端认证失败`）兼容策略，网络原因另由 `OnFrontDisconnected` 报告。官方 `RspAuthenticateField.UserProductInfo` 回填，`AppType` 未配置不编造标值。

## E. 4097 错误根源（S4，全新补知识库 §1）

### E1. 出处

在 dll 底层代码中，检测到与 CTP 前置网络断开时会输出一段代码：

```cpp
printf("CThostFtdcUserApiImplBase::OnSessionDisconnected ...
```

并回调到 API 的 spi 函数 `OnFrontDisconnected`。在写策略时，如果打印 `nReason` 参数，遇到网络断开就会输出 4097。

> 本文同样适用于：**为什么没有 `OnFrontConnected` 回调、`Decrypt handshake data failed`、8193 等错误**。

### E2. 断连原因码表（`nReason`，知识库 §1 未收录）

| 十六进制 | 十进制 | 含义 |
|---|---|---|
| `0x1001` | **4097** | 网络读失败 |
| `0x1002` | 4098 | 网络写失败 |
| `0x2001` | **8193** | 接收心跳超时 |
| `0x2002` | 8194 | 发送心跳失败 |
| `0x2003` | 8195 | 收到错误报文 |

### E3. 原因排查

1. **核对版本**：CTP 要求 API 版本和后台版本**一致**才能有正确的 `OnFrontConnected` 回调。版本不对会**不停地回调 `OnFrontDisconnected`**，或输出 `Decrypt handshake data failed`，或**没有任何反应**。检查方法：调 `GetApiVersion`。
   - **期货公司正式生产和 simnow 上均是 v6.3.15_20190220 版本**；期货公司评测使用 v6.3.13 或 v6.3.16（**小版本号不影响评测**）。
2. **核对网络**：正常生产上不会出这问题，但 **simnow 因为用户很多，有时会导致前置拥堵**；且 simnow **7×24 小时地址也不是很稳定**。
   - 办法：切换到其他两档模拟地址试一下；仍不行则只能问客服。

> **CTPBuddy 落点**：本册解释了 §1「自动重连」中"为什么会出现持续 4097 循环"的真实成因——**版本不匹配**是其中一类，且**重连无法解决**。知识库 §1 已记「重连需按指数退避 + 区分『已连接但未登录』」，此处补充：诊断时应先排除版本/前置拥堵，**不要把 4097 一律当成网络抖动而无限重试**。

## F. Simnow 仿真环境（S1 §3）

Simnow 真实环境分两部分：

| 部分 | 内容 |
|---|---|
| 第一部分 | **CTP 柜台系统**，与生产环境相同。客户可拿官网下载的 CTP API 在 simnow 测试，然后无缝切换到期货公司生产环境 |
| 第二部分 | **模拟交易所系统**，目前是上期技术基于上期所系统自己开发的模拟交易所，**并非真正的对应五个交易所的测试环境** |

Simnow 上仿真交易**也需要登录信息**（因 simnow 暂时没有上穿透式版本 CTP 柜台，所以暂时不需要 5、6 信息）。

**提示（易踩坑）**：

1. 注册手机**务必用非电信手机**，因为电信手机收不到验证码；
2. 填写账号信息时，柜台选择选**"标准 CTP"**；
3. 收到的短信中**账号密码即登录系统的 `InvestorID` 和 `Password`**，首次登录时需要修改密码（可在 simnow 主页常用下载页面上选择下载"快期新一代交易系统"，安装后在上面修改密码）；
4. 注册成功后将得到**100 万模拟资金**，如果资金号完**并不支持入金**，就只能换个手机号重新申请账号了。
5. simnow 有**两套环境，注意服务时间**：第一套与实际生产同步，**只在交易日交易时间提供服务**。
