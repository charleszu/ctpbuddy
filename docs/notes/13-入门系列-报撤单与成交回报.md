## A. 报单流程与三个回调（S6 §1、S7 §1）

### A1. 流程图（文字化，S6 图1）

```
客户交易程序                     CTP                        交易所
ReqOrderInsert  下单请求 ──────►  验资/验仓/检查等
                                  │ CTP 风控未通过 (红) ──┐
OnRspOrderInsert ◄────────────────┤                        │
OnErrRtnOrderInsert ◄─────────────┘                        │
①  OnRtnOrder  ◄──────────── CTP 风控通过 (绿) ──► 报往交易所
                                  │                        │ 检查
OnRtnOrder  ◄──── 交易所风控未通过 (红) ◄────────────────┤ False
②  OnRtnOrder  ◄──── 交易所风控通过 (绿) ────────────────┤ True
                                  │ 更新资金/仓位          │
③  OnRtnOrder  ◄──── 部分/全部成交 (绿) ─────────────────┘
    OnRtnTrade  ◄────
```

调用 `ReqOrderInsert` 报单后：

- **CTP 端**验资验仓等**不通过** → 回调 `OnRspOrderInsert` **和** `OnErrRtnOrderInsert`；
- **通过** → **先回调一次** `OnRtnOrder`（①，此时报单请求第一次到达 CTP，风险检查通过，尚未发到交易所）；
- CTP 再把报单挂往交易所，**交易所风控没通过** → 返回错误给 CTP，CTP 再次回调 `OnRtnOrder`（②）；
- **交易所风控通过也未必成交**，会再回 `OnRtnOrder`（③），并可能带 `OnRtnTrade`。

**关键结论（S6 原文）**："那两次 `OnRtnOrder` 有何区别，如何分别有 `OnRspOrderInsert` 和 `OnErrRtnOrderInsert`？错误提示在哪？如何看是否成交？这些我们留到（二）讲。"

> **CTPBuddy 落点**：此图与知识库 §5.1 回调分流表、§5.2 固定回调顺序一致；`#42` 已把「CTP 层拒绝仅 `OnRspOrderInsert(NULL)`，交易所层 163/164/165 先成功响应再 `OnErrRtnOrderInsert`」落为代码与 e2e 断言。本册提供客户端侧的解读闭环。

### A2. 三个回调的职责划分（S7 §1）

客户端从报单请求到回报可能看到三个函数：

```python
def OnRtnOrder(self, pOrder: 'CThostFtdcOrderField') -> "void"        # ①
def OnErrRtnOrderInsert(self, pInputOrder, pRspInfo)                  # ②
def OnRspOrderInsert(self, pInputOrder, pRspInfo)                      # ③
```

"下面分别为**正确被 CTP 和交易所接收**、**被 CTP 拒单**和**被交易所拒单**三部分来讲解。"

- **图 1 情形**：只回调 `OnRtnOrder`（如有成交则单独回调 `OnRtnTrade`），**回调参数类型为 `CThostFtdcOrderField`**（注意不是 InputOrder）。
- **被交易所拒单**：也只回调 `OnRtnOrder`，此时该笔订单**被交易所撤单**——判断状态靠字段组合（见 §C）。

## B. 报单字段详解（S6 §2）

### B1. 函数签名

```cpp
virtual int ReqOrderInsert(CThostFtdcInputOrderField *pInputOrder, int nRequestID);
```

`CThostFtdcInputOrderField` 一看有近 30 个字段，**但并不是每个字段都必须要**。下面按**报单所必须**填写字段解释。

### B2. 必填字段（按组）

**01 账号**

| 字段 | 说明 |
|---|---|
| `BrokerID` | 经纪公司代码 |
| `InvestorID` | 投资者代码 |

`InvestorID` 与 `UserID`、`InvestUnitID`、`AccountID` 对绝大多数数据投资者来说是**不需要管的**，具体就不展开了。

**02 交易所、合约号**

| 字段 | 说明 |
|---|---|
| `ExchangeID` | 交易所代码，**全部大写** `CFFEX`、`CZCE`、`DCE`、`INE`、`SHFE` |
| `InstrumentID` | 合约代码（注意大小写规范，见 notes/12 §C1） |

> `ExchangeID` **目前 simnow 为必填，生产还不必填，未来必填**。

**03 价格类型、方向、价格、数量**

| 字段 | 说明 |
|---|---|
| `OrderPriceType` | 报单价格类型，**枚举**。最常用 `THOST_FTDC_OPT_LimitPrice`（限价）和 `THOST_FTDC_OPT_AnyPrice`（市价）。**并不是交易所支持这里所有的价格类型，具体支持哪些后面详细写** |
| `Direction` | 买卖类型，**只有两种**：买或卖 |
| `LimitPrice` | 报单价，**只有 `OrderPriceType` 是限价单的时候需要填写**；填写的时候**注意价格主要是最小报价单位的整数倍，否则会被拒单** |
| `VolumeTotalOriginal` | 报单数量，**必须大于 0** |

**04 开平标志、投机套保标志**

| 字段 | 说明 |
|---|---|
| `CombOffsetFlag` | 组合开平标志 |
| `CombHedgeFlag` | 组合投机套保标志 |

C++ 中这两个字段对应的类型是**数组**，普通单只有**第一个字符是有用的**，用枚举值填充。枚举值填头文件中对应的 `TThostFtdcOffsetFlagType` 和 `TThostFtdcHedgeFlagType` 类型。

> 重点说明：`THOST_FTDC_OF_Open` 是**开仓**，`THOST_FTDC_OF_Close` 是**平仓 / 平昨**，`THOST_FTDC_OF_CloseToday` 是**平今**。**除了上期所 / 能源中心外，不区分平今和平昨，平仓统一使用 `THOST_FTDC_OF_Close`。**

> **CTPBuddy 落点**：这一条是 M2-1「**平今转换（非上期所一律 Close）**」的官方出处，DESIGN §8 已有实现（`平今转换` 规则表）。

**05 触发条件**

| 字段 | 说明 |
|---|---|
| `ContingentCondition` | 触发条件，**枚举**类型 |

1. 一般填写 `THOST_FTDC_CC_Immediately`，即**报单立即有效**；
2. `THOST_FTDC_CC_Touch`/`THOST_FTDC_CC_TouchProfit` 是**止盈止损单**，需要交易所支持才能填；
3. `THOST_FTDC_CC_ParkedOrder` 是**预埋单**。预埋单是指预埋单在 CTP 服务端，**需要非交易时间投入，开市后自动激活**；
4. 其他枚举类型则为**条件单**，报单存入 CTP 服务端，**CTP 判断条件达到后自动报入交易所**。

**06 有效期、成交量、最小成交量**（表：普通/FAK/FOK）

| 字段 | 普通 | FAK | FOK |
|---|---|---|---|
| `TimeCondition` | `THOST_FTDC_TC_GFD` | `THOST_FTDC_TC_IOC` | `THOST_FTDC_TC_IOC` |
| `VolumeCondition` | `THOST_FTDC_VC_AV` | `THOST_FTDC_VC_AV` / `THOST_FTDC_VC_MV` | `THOST_FTDC_VC_CV` |
| `MinVolume` | 不需要填 | 如果 `VolumeCondition` 为 `THOST_FTDC_VC_AV`，**则不需要**填；如果是 `THOST_FTDC_VC_MV`，则**设为要求的最小成交的手数** | 不需要填 |

- `TimeCondition` 是枚举型，目前**只有 `THOST_FTDC_TC_GFD` 和 `THOST_FTDC_TC_IOC` 这两种类型有用**。GFD 是指当日有效，报单会挂在交易所直到成交或收盘自动撤销。IOC 是立即完成否则撤销。
- 和 `VolumeCondition`、`MinVolume` 字段配合用于**设置 FAK 或 FOK**。

**07 其他必输字段**

| 字段 | 说明 |
|---|---|
| `ForceCloseReason` | 强平原因，**枚举值，填写 `THOST_FTDC_FCC_NotForceClose`** |

### B3. 限价 GFD 单完整示例（原文 C++）

```cpp
CThostFtdcInputOrderField orderfield = {0};
strcpy(orderfield.BrokerID, "9999");
strcpy(orderfield.InvestorID, "000001");
strcpy(orderfield.ExchangeID, "SHFE");
strcpy(orderfield.InstrumentID, "au1912");
orderfield.OrderPriceType = THOST_FTDC_OPT_LimitPrice;
orderfield.Direction       = THOST_FTDC_D_Sell;
orderfield.LimitPrice      = 400.0;
orderfield.VolumeTotalOriginal = 10;
orderfield.ContingentCondition = THOST_FTDC_CC_Immediately;
orderfield.CombOffsetFlag[0] = THOST_FTDC_OF_Open;

```

## C. 报单回报解析（S7 §一）

### C1. 确定对应的原始报单：订单号三组序列（全新，知识库未收录）

| 组 | 字段 | 归属 | 语义 |
|---|---|---|---|
| **1** | `FrontID` + `SessionID` + `OrderRef` | 客户端可维护 | `FrontID` 是 CTP 后台前置编号，`SessionID` 是这次链接的编号，**登录成功回报中也会返回这两个字段，这两个编号在此次连接中是不变的**。`OrderRef` 返回的是客户报单请求时填写的对应字段——若请求时填了 100，回报里也是 100；**请求的 `OrderRef` 不是必填项，不填 CTP 会自动递增**（但若是 CTP 自动生成的，**该字段是否右对齐，后面使用该字段时都要保持一致**） |
| **2** | `ExchangeID` + `TraderID` + `OrderLocalID` | CTP 内部维护，**客户无法改变** | `OrderLocalID` 在前两个字段固定情况下单腿递增，**随着每次报单返回给客户**。**建议不用本地维护这一组序号，可以直接忽略** |
| **3** | `ExchangeID` + `OrderSysID` | 交易所给出 | 报单**摄入到交易所时交易所所给的唯一编号**。加 `ExchangeID` 可用来唯一定唯一一笔报单。**需要特别注意的是，在上图里，该笔报单请求首次到达 CTP、风险通过后返回的第 1 个 `OnRtnOrder` 回报时，该字段是没有的**；所以**报单回报中 OrderSysID 为空，客户端无法知道它是哪一笔报单** |

"在 CTP 中，**每笔报单都有一组唯一序列号**，保证其与其他报单是不重复的。"

回报中还有 `RequestID`、`NotifySequence`、`SequenceNo`、`BrokerOrderSeq`、`RelativeOrderSysID`（用于条件单）等字段都和**顺序相关**，各有用途，**一般投资者用不到，这里为了避免混淆省略不讲了**。

### C2. 为什么成交回报找不到报单（S7 §一末、§S10 §02）

> **成交回报中是没有 `FrontID` 和 `SessionID` 字段的，只有 `OrderRef` 字段。**

原文给出的两种维护订单表的方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **01** | 报单时用 `FrontID + SessionID + OrderRef` 维护本地报单；首条 `OnRtnOrder` 的 `OrderSysID` 为空，待交易所接受边界按实际布局更新本地最终系统号，后面可用 `ExchangeID + OrderSysID` 维护订单 | 依赖前两个字段在连接内不变；不能把第 2 个回报绝对化 |
| **02** | 本地维护 `OrderRef` 字段，当前交易日内不管多少链接都一直单调递增，这样**可以不管 `FrontID` 和 `SessionID`**，每次根据 `OrderRef` 就可以确定唯一报单 | 但这对**多策略多链接**交易开发可能存在问题，因为涉及到多个 API 链接间 `OrderRef` 字段的**互相同步** |

> **⚠️ CTPBuddy 落点（重要）**：首条 `OnRtnOrder` 固定保持空号；后续首次非空的位置由交易所布局决定，不能把“第 2 个回报”绝对化。客户端应先用 `FrontID + SessionID + OrderRef` 维护本地订单，收到最终非空系统号后再切换到 `ExchangeID + OrderSysID` 路径。
>
> 另外 M3-4 的 `PositionDetail` 以 `TradeID` 为主键之一，见 notes/14 §A2 的 TradeID 复用问题——**`OrderRef` 同理，跨连接可能重复**（方案 02 的代价），CTPBuddy 多连接场景须保证 `OrderRef` 全局单调。

### C3. 当前报单状态

三个字段：`OrderStatus`（报单状态）、`OrderSubmitStatus`（报单提交状态）、`StatusMsg`（状态信息）。"其他单独根据 `OrderStatus` 判断就可以了。"

### C4. 被 CTP 拒单（S7 §二 / S13 §二）

被 CTP 或交易所拒单，会回调 `OnRspOrderAction`（撤单时）或 `OnRspOrderInsert`（报单时）与 `OnErrRtn*`；**只要打印回调函数的参数 `pRspInfo` 就可以知道被拒原因**。常见拒单原因：

| # | 原因 | 判定 |
|---|---|---|
| 1 | **CTP：报单已全成交或已撤销，不能再撤** | 报单回报中 `OrderStatus` 为 `THOST_FTDC_OST_Canceled` 或 `THOST_FTDC_OST_AllTraded` 这两种情况下不允许撤单，**其他状态都可以** |
| 2 | **CTP：无此权限** | 第 1 部分的账号没有填对 |
| 3 | **CTP：撤单找不到相应报单** | 第 2 部分的序号没有填对 |

**用第 1 组序号时**，要注意 CTP 返回的 `OrderSysID` 是**右对齐**的，撤单填写时必须和 CTP 返回的一致。例如按头文件，`OrderSysID` 有效位为 20 个字节，如果 CTP 返回的 `OrderSysID` 为 `"    121"`，该字符串一共有 20 个字节，**前面 17 个为空格，撤单时也要原样右对齐填写**。

**用第 2 组序号时**，如果报单时 `OrderRef` 为客户自己赋值，**撤单时也要同样赋值**；如果报单时填空，则 CTP 会自动赋值，注意此时 `OrderRef` 和上面的 `OrderSysID` 字段一样，也是右对齐的，**撤单时也要原样右对齐填写**。

### C5. 被交易所拒单（S7 §三）

该笔报单通过 CTP 柜台风控报往交易所后，被交易所拒单，**这个时候只回调函数 `OnRtnOrder`，且这笔订单会被撤单**。可通过 §C2 第一组序号判断该笔订单此时的状态：

> 回报 `OnRtnOrder` 中的 `OrderStatus` 为 `THOST_FTDC_OST_Canceled`（"撤单"），`OrderSubmitStatus` 为 `THOST_FTDC_OSS_InsertRejected`（"报单已经被拒绝"）即说明该笔电子被交易所拒单（处于**被动撤单**状态）。`StatusMsg` 字段有具体的拒单原因，**是由交易所直接返回给 CTP 的中文字符串**。

常见交易所拒单原因（即 `StatusMsg` 字段值）：**前、后半部分都是一样的**（CTP 层的拒单原文在前半部分，**交易所直接返回给 CTP 的拒单原因在后半部分**，CTP 再转发给投资者）。

> **CTPBuddy 落点**：这条是 `#42` 交易所层双推送面（先 `OnRspOrderInsert{0}` 成功响应再 `OnErrRtnOrderInsert`）与 `#43` FAK 三所形状的**客户端侧判据**。DESIGN §8.12/§8.13 已实现，本册确认 `OrderStatus='5'` + `OrderSubmitStatus='3'`（InsertRejected）这个组合正是"被动撤单"的官方标记。

## D. 撤单（S8）

### D1. 撤单流程

`ReqOrderAction` 指令申请撤单：

- 通过 CTP 端检查 → 返回**第 1 个** `OnRtnOrder` 回报（与上次收到的 `OnRtnOrder` 一致，例如该笔报单在 CTP 内现状为 `THOST_FTDC_OSS_Accepted`，则该状态的 `OnRtnOrder` 会再收到一次）；
- 不通过 → 返回 `OnRspOrderAction` 和 `OnErrRtnOrderAction`；
- 通过后报入交易所，交易所被检查通过 → 返回**第 2 个** `OnRtnOrder`（表明该笔报单已经**成功撤销**），此笔回报中 `OrderSubmitStatus` 为 `THOST_FTDC_OSS_Accepted`，`OrderStatus` 为 `THOST_FTDC_OST_Canceled`；
- 交易所检查不通过 → `OnErrRtnOrderAction`。

### D2. 撤单必填字段（S8 §一）

**01 账号**：`BrokerID`、`InvestorID`（必填）；`UserID`（非必填，是操作员账号，**不填写会收不到 `OnErrRtnOrderAction` 回报**，一般客户和 `InvestorID` 填写一样就可以）。

> 原文补充：`InvestorID` 类似的 `InvestUnitID` 不需要管，"这其实是当年为子账号分组设计的，后来该功能被证监会判定违规，率先推出该功能的某公司也被处以巨额罚款，**该字段于是废弃不用了**"。`UserID` 非必填，不填收不到 `OnErrRtnOrderAction`。

**02 确定所要撤的原始报单号**（CTP 支持其中**两组**序号）：

| 组 | 字段 | 特别注意 |
|---|---|---|
| 1 | `ExchangeID` + `OrderSysID` | **第 1 个报单回报中 `OrderSysID` 为空，此时如果需要撤单只能用下面这组序号**，官方推荐用这种方式撤单 |
| 2 | `FrontID` + `SessionID` + `OrderRef` | **用这组序号撤单还需要填写字段 `InstrumentID`** |

**03 操作标志**：`ActionFlag`，**枚举值，有删除和修改两种，目前只支持删除，即撤单**。

"这样用第 1 部分的账号 3 个字段 + 第 2 部分的任意一组 + 第 3 部分 `ActionFlag` 就可以撤单了。"

> **⚠️ CTPBuddy 落点**：`用 FrontID+SessionID+OrderRef 撤单必须填 InstrumentID` —— 这是一条**具体的字段校验规则**。DESIGN §4.4 目前只记了"`ActionFlag` 仅 Delete；`OrderSysID` 空值不撤"，**未见 InstrumentID 的必填校验**。真实 CTP 上漏填会导致撤单被拒，仿真上若不校验就是一处"仿真比真实宽松"的缺口。已登记入 notes/11 结尾的实现影响清单。

### D3. 撤单常见问题（S8 §三）

| # | 问题 | 结论 |
|---|---|---|
| 1 | CTP 不支持批量撤单？ | **暂不支持**。API 里面有个迷惑性的接口 `ReqBatchOrderAction`，看着是批量撤单请求，但**该接口仅支持大商所，而且只有做市商客户才能用**。所以目前批量撤单只能客户自己实现该逻辑 |
| 2 | 撤单数多是否属于异常交易 | 为了防止盘口侮辱，**各交易所将频繁撤单列入异常交易管理规范**。目前上期所明确规定**单个合约撤单数不能超过 500 笔**，但 **CTP 内并没有该项风控**，建议策略自行加入该项风控。其他交易所没有看到有明确数量规定，建议查看对应交易所公告后自行风控。另外，**FAK 和 FOK 的撤单不计入该数**，所以如果策略可能会有大量撤单，**建议使用 FOK 和 FAK 报单** |
| 3 | 是否可以指定撤单数量？ | （原文图未加载，SDK 语义以官方 API 文档为准） |

> **CTPBuddy 落点**：`ReqBatchOrderAction` **仅支持大商所且仅做市商客户**——这条应登记为"暂不可达/可落地"错误码分类的依据之一（与 error.xml 中 `RULEINTRAPARAM_NOT_FOUND` 等策略单类错误码同类：业务域存在但 v1 不实现）。

### D4. 交易所返回的特殊错误（S8 §二4）

**SHFE：报单已经全部成交**——"这种情况比较特殊，这是笔单子已经在交易所被撮合成交但 CTP 还没有收到交易所的成交通知。所以**撤单通过了 CTP 的检查，报到交易所后被交易所因为成交完而拒绝**。"

> **CTPBuddy 落点**：这解释了 M2-4 为何需要 `terminal_refs` 终态记忆——官方错误码 25（"已全成交或已撤销"）与 26（"找不到相应报单"）的区分依赖"曾收到过终态"这一记忆（DESIGN §5 已记"撤单失败 25/26 区分（终态 vs 找不到）已按官方场景 6/7 实现"）。本条为其成因。

## E. 成交回报（S10）

### E1. 唯一确定一笔成交（S10 §01）

| 字段 | 说明 |
|---|---|
| `ExchangeID` | 交易所代码 |
| `TradeID` | 成交编号 |
| `Direction` | 买卖方向 |

> **`TradeID` 是交易所对每一笔成交的编号**，因为除郑商所外的交易所对**成交通知时互为对手方的两笔成交编号是一样的**，所以**还需要加上 `Direction` 这个字段**。有这三个字段重复的成交回报**可以直接 return 不处理**。

> **⚠️ CTPBuddy 落点（重要）**：这是**成交回报去重**的官方规则，且明确「**除郑商所外**两笔成交号相同」。CTPBuddy 的引擎若为每笔成交生成全局唯一 `TradeID`，则**与真实 CTP 的形状不同**——真实客户端按 `(ExchangeID, TradeID, Direction)` 去重；CTPBuddy 给出更唯一的 `TradeID` 虽不致错，但会让依赖"同号双向"的下游逻辑（如按成交号配对买卖双向持仓变动）在仿真上不成立。**建议 CTPBuddy 按交易所规则生成 `TradeID`（同号双向），并提供唯一的内部成交 id 另行管理**。已登记。

### E2. 与报单回报的对应（S10 §02）

报单回报 = **每次报单状态有更新**时 CTP 发给 API 用户的消息；成交回报 = **每次报单有成交**时 CTP 发给用户的消息。如有**成交**的话必然对应报单状态变化，所以**成交回报之前会有报单回报**。

定位用四个字段：`OrderRef`（报单引用）、`OrderSysID`（报单编号）、`TraderID`（交易所交易员代码）、`OrderLocalID`（本地报单编号）——"这四个字段涉及到三组序号，可以确定唯一一笔报单"。

> 但如 §C.2 所述：**成交回报中没有 `FrontID` 和 `SessionID` 字段，只有 `OrderRef` 字段**。客户端一般需要根据**成交回报**去找到自己本地原本存储的报单，来更新报单状态、管理报单，这就需要这几个字段。

### E3. 用于更新持仓（S10 §03）

| 字段 | 说明 |
|---|---|
| `InstrumentID` | 合约代码 |
| `Direction` | 买卖方向 |
| `OffsetFlag` | 开平标志 |

> **国内持仓需要区分多头和空头，对于上期和能源还需要区分昨仓今仓。** 这些根据**成交里面的 `Direction` 和 `OffsetFlag` 两个字段**就能确定该笔成交需要更新到哪个持仓里面去。

> **CTPBuddy 落点**：与 notes/04 B3 一致（大商所不区分今昨但**手续费仍要区分平今平昨**；上期/能源中心区分平今平昨）。DESIGN M2-1 已有按所归一化。

### E4. 成交价格与数量（S10 §04）

| 字段 | 说明 |
|---|---|
| `Price` | 成交价，指本次成交的价格，**由撮合时买卖委托价，委托在上一价成交这三个值取其中** |
| `Volume` | 数量，指本次成交数量 |

> 原文表述："**成交价是指本次成交的价格，由撮合时买卖委托价，委托在上一价成交这二值取其中**"（此处 OCR 有衍字，语义为撮合时的买卖委托价、或上一次成交价二者取一）。
>
> **CTPBuddy 落点**：这与 CTPBuddy 撮合引擎"成交价按**对手方**价"的实现一致（e2e 记忆：报 3502 成交 3502、报 3499 成交 3500）——即买方成交取卖一、卖方成交取买一，与"撮合时买卖委托价"是同一件事的两面。

### E5. 极其实用的两条警告（S10 文末「特别提醒」）

> 1）**有些客户喜欢用 `OnRtnOrder` 中的状态来更新报单状态**，因为理论上相应的报单回报都比成交回报快。**官方建议客户以成交回报 `OnRtnTrade` 为准判断报单是否成交，以及成交数量和价格。** 若以报单回报中数量或状态为准，**由于报单回报与成交回报之间存在理论上时间差（微乎其微），而 CTP 后台是以成交回报为准更新持仓状态的，因此有可能导致平仓不成功。**

> **⚠️ CTPBuddy 落点（重要）**：这条是**账本更新时序的最高权威**——**只有 `OnRtnTrade` 能动持仓/资金，`OnRtnOrder` 不得改仓位**。DESIGN 的事件序（"引擎事件 order_update/fill 先于请求事件 order_insert 落账"，M2-3 确定性不变量）需核对其是否被误读为"两种事件都更新账本"；M2-3 的记忆原文是**事件落账顺序**，与"哪些事件允许改账本"是两件事，不能混。

> 2）**CTP 不支持持仓行情**；CTP 只提供国内五大期货交易所期货行情。但 CTP 也有股票柜台，可以咨询上期技术哪些券商上了 CTP 股票柜台，用股票 API 获取股票行情。
