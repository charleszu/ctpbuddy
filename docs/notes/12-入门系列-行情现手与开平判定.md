## A. 行情 API 与订阅流程（S3）

### A1. 行情与交易完全独立

只对行情感兴趣的话，只需三个文件：`thostmduserapi.py` / `_thostmduserapi.pyd` / `thostmduserapi_se.dll`（或非穿透式 dll）。交易与行情"两者是完全独立的，互不干扰"。

订阅函数（第一参数为 list，写成 `["au1912", "IC1909"]`；第二参数必须为前面 list 的**长度**）：

```python
def SubscribeMarketData(self, ppInstrumentID: 'char *[]', nCount: 'int') -> '...'
```

回报函数：

```python
def OnRtnDepthMarketData(self, pDepthMarketData: 'CThostFtdcDepthMarketDataField')
```

`CThostFtdcDepthMarketDataField` 主要字段：`UpdateTime`（更新时间）、`LastPrice`（最新成交价）、`BidPrice1`/`BidVolume1`、`AskPrice1`/`AskVolume1`、累计成交量 `Volume` 等。

## B. 切片（快照）而非 tick —— 全文最关键的行情事实（S3 §四、S4 Q5）

### B1. 术语界定

| 名称 | 定义 |
|---|---|
| **逐笔数据（tick）** | 市场上的逐笔数据，例如**一笔委托会产生一笔行情，一笔成交也会产生一笔行情** |
| **切片（快照）数据** | 将一定时间内的逐笔数据**统计成一个快照发出** |

**国内期货交易所目前还不支持推送逐笔的数据，只推送切片（快照）数据。**

- 切片**一般是 1 秒 2 笔**，但**郑商所有点特殊，可能是 1 秒多笔**，就不展开讲了。
- **CTP 发出的行情是交易所行情的转发，所以是 500ms 一次快照。** 一般业内把这个快照数据称之为 tick，虽然这不是真正的 tick，但依照惯例，下文都称为 tick 数据。

> **⚠️ 对 CTPBuddy 的直接含义**：撮合引擎按"每根 tick 是一次独立行情事件"来实现是**符合真实**的（500ms 一帧），但**不能假设"一 tick = 一笔成交"**。任何"一笔报单产生一条行情"式的推理在真实 CTP 上不成立。

### B2. K 线必须客户端自己合成

**CTP 不推送 K 线数据**，所以需要客户自己根据 tick 数据计算得出。

K 线六要素：`Time`、`Volume`、`Price`、`Open`、`High`、`Low`、`Close`，由 tick 中的 `UpdateTime`、`LastPrice`、`Volume` 算出。以 1 分钟 K 线为例（原文代码，已按 CTPBuddy 语境补注释）：

```python
st = pDepthMarketData.UpdateTime.split(':')
if not self.bar:
    newMinute = True
else:
    if int(st[1]) == self.bar.updateTime.minute:
        newMinute = False
    else:
        newMinute = True
if newMinute:
    self.bar = CBarData()
    self.bar.instrumentID = pDepthMarketData.InstrumentID
    self.bar.exchangeID  = pDepthMarketData.ExchangeID
    self.bar.updateTime  = time(int(st[0]), int(st[1]), 0, 0)
    self.bar.volume      = 0
    self.bar.openInterest = pDepthMarketData.OpenInterest
    self.bar.openPrice  = pDepthMarketData.LastPrice
    self.bar.highPrice  = pDepthMarketData.LastPrice
    self.bar.lowPrice   = pDepthMarketData.LastPrice
    self.bar.closePrice = pDepthMarketData.LastPrice
else:
    self.bar.highPrice  = max(self.bar.highPrice,  pDepthMarketData.LastPrice)
    self.bar.lowPrice   = min(self.bar.lowPrice,   pDepthMarketData.LastPrice)
    self.bar.closePrice = pDepthMarketData.LastPrice
    self.bar.openInterest = pDepthMarketData.OpenInterest
    # 注意 Volume 字段是累计成交量，所以这个时间段内成交量为该值与上一时间段的差值
    if not self.lastVolume:
        self.bar.volume += max(pDepthMarketData.Volume - self.lastVolume, 0)
    self.lastVolume = pDepthMarketData.Volume
```

**两个必须记住的点**：

1. **`Volume` 是累计成交量**（当日/本交易日累计），所以**周期内成交量 = 当前值 − 上一值**；且用 `max(..., 0)` 兜底（防止某帧未推送导致计数回退）。
2. **新分钟的判定只看 `UpdateTime` 的分钟数**（`st[1]`），不看日期——跨交易日需自行重置。

> **CTPBuddy 落点**：S2 的 journal/场景 DSL 里 `ticks` 已是"场景行数"而非"时点数"（notes 记忆里为此踩过坑：3 时点 × 2 合约 + 1 = 7）。本节给出官方口径佐证——`Volume` 累计语义意味着**回放若要复刻真实客户端的 K 线合成，必须先做差分**。DESIGN 的行情回放是否提供 K 线合成、或只提供原始切片，需明确（见实现影响清单）。

### C3. 字段级坑（对 M3 对账直接相关）

| # | 问题 | 结论 |
|---|---|---|
| 13 | 如何获取当前切片内的成交量 | `Volume` 字段是**累计**成交量，指这个交易日内的累计成交量。**需要用这个切片内该字段值，减去上一切片相应值，差额即这个切片内成交量** |

> - Q15 的 `1.7976931348623157e+308`（DBL_MAX）是"无效值"哨兵。**DESIGN 的 M3-4 已知问题**——首笔成交早于 mark-to-market 时，若从持仓副本读昨结算会得 0；这里官方口径是**盘中 `SettlementPrice` 字段直接就是 DBL_MAX**。e2e 构造 refdata 时若不显式给昨结算，可能喂进 DBL_MAX 而非 0，需检查（列为待核项）。
> - Q16 `AveragePrice` 的"郑商所不除乘数、其余所要除"是一条**极易重复踩**的规则，且真实结算单的「开仓均价」列同样受此影响（notes/04 记忆里已确认结算单「买/卖」列语义左右手问题，但未记此乘数差异）。**M3 对账能过是因为真实数据走了各自的正确口径**，一旦 CTPBuddy 要自己算均价就必须实现这个分支。

### C4. TradingDay 与 ActionDay 的夜盘差异（S4 Q6，全新精确对照）

> 在 CTP 的设计里，`TradingDay` 用来表示**交易日**，`ActionDay` 表示**当前实际日期**。期货交易分为**日盘、夜盘**，这两个日期在日盘的时候是一致的，但在夜盘就有了区别，因为当天夜盘是属于**第二天**这个交易日。

例：**20190830（周五）晚上 21 点开始交易**，交易日 `TradingDay` 是 **20190902（周一）**，但实际日期 `ActionDay` 是 **20190830**。

> "这是设计的初衷，但事实**上夜盘各交易所这两个日期很混乱**。"

| 交易所 | tradingday | actionday |
|---|---|---|
| 上期/能源源 | 20190902 | 20190830 |
| **大商所** | **20190902** | **20190902** |
| **郑商所** | **20190830** | **20190830** |

**总结就是：大商所夜盘两个日期都是 tradingday，郑商所日夜盘都是当日日期。**

> **CTPBuddy 落点**：知识库 §7 已记"TradingDay 各所混乱"但无精确对照表，DESIGN M2-3 的 `next_conn_id` 场景时钟与 journal 归一化均依赖 trading_day。本表是补全该口径的权威依据。**注意大商所与另两所相反**——按"夜盘属于下一交易日"这条通则去推断大商所会推错。

## D. 现手、增仓、开平、对手盘计算（S5，全新）

### D0. 前提：这些数据都要自己算

行情推送结构体 `CThostFtdcDepthMarketDataField` **并无**现手、增仓、开平等字段，但 CTP 平台对接的交易所行情源和这些客户端所对接的行情源基本一致，所以**客户端的这些数据都是自己算出来的**。只需用 `Volume`、`OpenInterest`、`LastPrice`、`AskPrice1`、`BidPrice1` 五个字段。

### D1. 现手与增仓

- **现手** = 当前两个行情切片之间的**成交量**
- **增仓** = 对应成交量增加的**持仓量**。**现手是大于等于 0 的，但是增仓却可正可负**

| 量 | 公式（表1） |
|---|---|
| 现手 | `volume_delta = 后一笔 Volume − 前一笔 volume` |
| 增仓 | `open_interest_delta = 后一笔 OpenInterest − 前一笔 OpenInterest` |

> 因 CTP 行情推送是 500ms 一次切片，`Volume` 与 `OpenInterest` 都是**累计量**，所以根据同一合约的**前后两笔行情**就可计算出现手、增仓。

### D2. 开平（不带方向）真值表（表2）

| 性质 | 现手与增仓 | 含义 |
|---|---|---|
| **双开** | `现手 = 增仓 > 0` | 多头和空头同时开仓 |
| **开仓** | `现手 > 增仓 > 0` | 主动开仓数量大于平仓数量 |
| **平仓** | `现手 > −(增仓) > 0` | 主动平仓数量大于开仓数量 |
| **换手** | `现手 = 增仓 = 0` | 多头互换或者空头互换仓位 |
| **双平** | `现手 > 增仓 = 0` | 多头和空头同时平仓 |
| **未知** | `现手 = 增仓 = 0` | **异常情况，仅为记录** |

> **注意"未知"与"换手"两行条件字面相同**（都是 `现手 = 增仓 = 0`）——原文如此，实际由上下文（前后笔方向）区分。实现时不要机械照抄这张表当作函数真值。

### D3. 价格涨跌方向（表3）

| 方向 | 价格条件 |
|---|---|
| 向上 | 后一笔最新价 `LastPrice` **>=** 前一笔卖一价 `AskPrice1` |
| 向下 | 后一笔最新价 `LastPrice` **<=** 前一笔买一价 `BidPrice1` |
| 向上 | 后一笔最新价 `LastPrice` **>** 后一笔买一价 `AskPrice1` |
| 向下 | 后一笔最新价 `LastPrice` **<** 后一笔卖一价 `BidPrice1` |
| 不变 | 除上面四种外 |

> 原文注："有了（表格2）和（表格3）后，就可以计算出真正的**开平**了。表2 中性质有 6 种，表3 中方向有 3 种，所以一共有 **18 种开平组合**。"
> 示例（表4）：换手/向上 = 多换，红色；换手/向下 = 空换，绿色；双开/向上 = 双开，红色；平仓/向下 = 多平，绿色。

### D4. 对手单（单边计算，2020 年起）

> **先要说明一点，按证监会要求，期货市场数据统计将从 2020 年 1 月 1 日起统一调整为单边计算。** 下面的计算还是按照目前的双边说明的。

以 20191015 夜盘数据第一单为例：

| 现手 | 增仓 | 解读 |
|---|---|---|
| 72 手 | 单边成交 36 手 | 意味着**空头主动买入平仓 36 手** |
| — | 单边减持 28 手 | 意味着**28 手空头买入平仓和 28 手多头卖出平仓** |

所以对手单是 **28 手多头卖平**，**36 − 28 = 8** 这 8 手为**空头开仓与空头平仓互换**。

```
买方：36 = 28 + .8    →  28 是影响仓位的空头买入平仓，8 是不影响仓位的空头买入平仓
卖方：36 = 28 + .8    →  28 是影响仓位的多头卖出平仓，8 是不影响仓位的多头卖出开仓
```

**总结公式（1）**：设 S 是对手单中**开平方向相同**的操作，O 是对手单中**开平方向相反**的操作。

```
S + O = volume_delta / 2
S − O = abs(open_interest_delta) − volume_delta / 2
```

解得：

```
S = abs(open_interest_delta) / 2
O = volume_delta / 2 − S
```

在上例中：`S = abs(-56)/2 = 28`，`O = 72/2 − 28 = 8`。与空买平方向相同的**多头卖出平仓 28 手**，方向相反的**空头卖出开仓 8 手**。

> **CTPBuddy 落点**：
> - 这套公式是**纯客户端侧派生量**——CTPBuddy 不必实现，但文档需要记录，因为**下游客户端会在收到 CTPBuddy 的行情后自己算**，而它们的正确性依赖 CTPBuddy 提供的 tick 满足"同一合约前后两帧、累计量、500ms 间隔"这三个前提。场景 DSL 的 `ticks` 若不满足（如同一时刻多合约、跨日不重置 Volume），客户端算出的现手/增仓会与真实柜台不一致。**场景 tick 应显式给出 `Volume`/`OpenInterest` 累计值并保证时间序单调不减**。
> - **2020-01-01 起改为单边计算**：与 CTPBuddy 无关（本项目不做统计口径），但真实柜台的成交/持仓数据从该年起已是单边口径——真实导出数据（2024-2026）当然也是单边，这解释了 §D.4 算例在今天的适用性。
