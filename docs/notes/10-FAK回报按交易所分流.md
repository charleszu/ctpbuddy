## A. 官方原文（逐字）

## B. 三所形状对照

| 所族 | `IocLayout` | 顺序（省略开头的 `OnRtnOrder` 未知单） | 每笔成交的 `OnRtnOrder` 行数 |
|---|---|---|---|
| 上期所 / 能源中心 / 中金所 | `CancelFirst` | `5`（**先于**成交，VolumeTraded 已有值）→ 每笔成交 `5` + `OnRtnTrade` | **1**（就是那个 `'5'`） |
| 大商所 / 广期所 | `TradeDriven` | `3` → 每笔成交 `1` + `OnRtnTrade` → `5` | **1**（合成的 `'1'`） |
| 郑商所 | `StatusDriven` | `3` → 每笔成交 `前态` + `1` + `OnRtnTrade` → `5` | **2**（前态 + 新态） |

三条不可归并的差异：

1. **只有后两族推 `'3'` 进簿确认。** IOC 在上期所不进簿，所以没有 `'3'`；大商所/郑商所的 IOC 会
   短暂进簿并被确认（场景 9 原文对大商所另有一句明文：「大商所不管会不会立即成交，只要委托
   进入报单簿后都会返回一笔未成交报单回报」）。**口径影响**：`'3'` 的判定从 M2-4 的
   `exchange_id == "DCE"` 改为按 `IocLayout`——`TradeDriven` / `StatusDriven` 两族的 **GFD**
   单也拿这一行。依据是场景 9/10 都写了 CZCE/GFEX 报单在成交前先收到「未成交」回报，而场景 9
   那句明文把规则表述为「**进入报单簿**」的属性、不是「是大商所」的属性。FOK 与市价单永不进簿，
   始终无此行。
2. **只有郑商所重复推前一状态。** 大商所只推一行合成的 `'1'`——这与大商所 §3 的「CTP 补充
   生成，且不重复推送前一状态」是同一条规则的外延。
3. **只有上期所把撤单行放在所有成交回报之前。** 官方特别注明该行「VolumeTraded 字段此时已有
   值」——也就是说这一行**已经把全部成交量带走了**，后面的每笔成交行不再改变成交量口径。

### 为什么上期所每笔成交只有一行

场景 8 的成交回报是 `OnRtnOrder（已撤单）` + `OnRtnTrade` 两行，**没有前态 '5' 重复**。
原因不是漏写：此时订单状态**已经是终态 `'5'`**，前一状态与新态相同，CTP 没有理由再推一行
相同的状态。这正是大商所 §3「不重复推送前一状态」规则的一般化——**状态没变就不重复推**。

> 这条是本任务实现时最容易踩的坑：直觉上「每笔成交都前态+新态」会写成 `['a','5','5','5']`
> （3 个状态行），而官方是 `['a','5','5']`（2 个状态行 + 1 个 Trade）。

## C. 为什么必须复刻而不是统一

按项目最高原则（本地仿真 = 对真实 CTP 的忠实复刻，含其缺陷）：

- 一个「按 `OnRtnOrder` 条数累计成交状态」的下游客户端，在上期所会**多算**状态迁移次数；
- 一个「靠 `'1'`（部分成交）行累加成交量」的客户端，在上期所**根本收不到 `'1'`**（场景 8
  明确无 `'1'`），成交量会漏成 0；在郑商所则会**重复计数**（前态 `'3'` + 新态 `'1'` 两行）。
- 一个「先收到终态 `'5'` 就认为订单已死、不再处理后续回报」的客户端，在上期所会**丢掉全部
  `OnRtnTrade`**——因为撤单行先到。

也就是说：**统一成任何一种形状，都会在另外两组上产生静默错误**。这不是可以「顺手简化」的地方。

## D. 实现要点

- **判定**：`is_fak = is_ioc && !is_fok`（FAK = IOC 且非 FOK；含 `VC_AV` 与 `VC_MV`）。
  `ioc_layout(exchange_id)`：`DCE`/`GFEX` → `TradeDriven`，`CZCE` → `StatusDriven`，
  其余 → `CancelFirst`（未知交易所码落上期所组，即历史 CTP 默认）。
- **必须缓冲成交**：报告形状取决于**是否还有 leftover**（官方三场景只写「部成部撤」），而上期所
  的撤单行还要排在成交行**之前**——撮合循环结束前无法确定任何一行。故 taker 侧每笔成交先记
  `(前态快照, 新态快照, price, volume, trade_id)` 进 `fak_fills`，循环后由 `emit_fak_reports`
  一次性铺开（类型别名 `FakFill`）。非 FAK 走 `record_taker_fill` 的即时分支，行为与改动前
  逐字节一致。
- **终态行只推一行**：三所收尾的都是**交易所主动撤单**（FAK 剩余量被交易所撤掉，不是客户端
  `ReqOrderAction`），所以不带前态重复——这与 §2 场景 3/5 客户端主动撤单的前态+新态形状
  **刻意不同**。FAK 一手未成时同样只有 `a` → `5`。
- **FAK 全成官方无形状**：三场景都只规定部成部撤。全成时退回 §8.9 场景 2 的一般规则
  （`a` → `a` → `0` + `OnRtnTrade`），大商所沿用 §3 的「不重复推送前一状态」。
- **账本释放顺序无副作用**：上期所 `CancelFirst` 下终态 `'5'` 事件先于 Trade 到达，
  `dispatch_event` 先 `unfreeze_order`（移除 `frozen` 条目、全额释放剩余），随后每笔 `on_fill`
  因 `frozen.get_mut()` 返回 `None` 而释放 0。净额仍正确——pro-rata 本就按**原始**估算额 ×
  本次量/原申报量计算，佣金 / 保证金 / 持仓移动都在 `on_fill` 里独立进行。
- **catalog 补齐**：`builtin()` 增 CZCE `TA609`（**3 位 `YMM` 后缀**，`parse_delivery_ym` 加了
  decade 分支 `2020 + decade`）与 GFEX `si2610`，否则三族都不可交易、e2e 驱不动场景 8/9/10。
  合约数 5 → 7（`m1_smoke` / `m2_book` 的 `instruments` 断言同步）。
