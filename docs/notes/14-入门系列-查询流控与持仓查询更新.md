## A. 查询流控全景（S9，全新细化）

### A1. 链路图与流控分布

```
客户交易程序 --① 底层动态库--> CTP柜台 --②--> 交易所底层API --③--> 交易所后台程序
                                ↑④ CTP后台程序流控        ↑③ 交易所后台程序流控
```

- **①** 底层动态库（`API 动态库` 侧）
- **②** CTP 后台程序
- **③** 交易所底层 API
- **④** 交易所后台程序

"**交易所在系统层面考虑系统压力及安全，同样也可以在 ③ 处（交易所底层API）和 ④ 处（交易所后台程序）设置流控**，控制各台的查询及报单频率。"

"所以在这条链路上共有**如上 ①②③④ 处在设置流控，其中 ③④ 流控是柜台系统厂商需要考虑的问题**，文末会附带提一下，就不展开讲了。**这里主要讲客户面对的 ① 和 ② 处的流控及处理方案**。"

> **CTPBuddy 落点**：与知识库 §1「流控全景（六类）」一致。本册给出的是**客户端侧机制与返回值**，补齐了知识库记的"① API 侧 / ② 前置 / ③ 交易所 API / ④ 后台"的**逐类具体表现**。

### A2. 底层动态库中的查询流控（返回 `-2` 与 `-3`）

> 目前底层动态库中的流控**只针对查询**，即 API 中所有以 `ReqQry` 开头的函数，大家常用的查询资金、持仓、合约等函数都会在底层动态库被流控。

> 如果调用查询函数被流控，则**该请求会直接在底层动态库中被阻断，不会发向 CTP 后台，此次调用也会无效**。

**排查方法**：以查询合约为例，查询时加入如下逻辑——如果查询没返回，首先打印查询函数返回值，**如果为非 0，说明查询根本没发出，更别提有返回值了**。此处查询流控分为两种：

| # | 流控 | 返回值 | 机理 |
|---|---|---|---|
| 1 | **未处理请求超过许可数** | **-2** | 因为目前动态库底层设置**每次只允许 1 个查询请求在途**，即当前这笔查询请求发出后，**在未收到响应前，不能发起下一笔查询** |
| 2 | **每秒发送请求数超过许可数** | **-3** | **旧**穿透式版本之前，动态库底层设置了 API 每秒只允许发出 1 次查询请求。升级新版本后，每秒允许查询次数由后台设定，在登录回报中传动态库。所以**具体 1 秒中允许发起查询多少次对用户是未知的**，用户可以询问期货公司该设置值 |

> **⚠️ 注意"穿越版本"措辞**："此时调用函数返回值为 -3。**在穿越式版本之前**……"（"穿越"应为"穿透"之误）。即 **`-3` 是旧穿透式版本的行为**，新版本改为后台配置。CTPBuddy 若要复刻，应按新口径（后台可配），但需保留 `-3` 的历史记录。

**两种流控的解法（不同）**：

| 流控 | sleep 是否有效 | 正确解法 |
|---|---|---|
| **-2**（在途） | **无效** | 在**一个 spi 回调函数里面只放一个查询**，嵌套运行。也可以运用事件队列或者自己另开线程去顺序查询 |
| **-3**（每秒超限） | **有效** | 两次查询中间 `sleep` 一定时间即可解决（1~2 秒）；"这个流控一般是**异步**线程中顺序多次查询时会触发" |

> **"-2 用 sleep 治不好"的机理（原文）**："这是因为从《系列之二》中学习到，**spi 函数和 socket 的读写都是动态库底层一个线程负责调用的，在 spi 函数中 sleep 会阻塞读写，只有当 spi 函数结束后，查询才会从 socket 发送出去**。所以在 spi 回调中写再多重查询，sleep 再长时间，**最终都是由 socket 同时发出去**，这就会导致触发流控。"
>
> **CTPBuddy 落点**：这条从**线程模型**层面解释了知识库 §2.3 与 §10.1 的实现选择——SDK 的 `_query_stream` 透明重试（90 → 1.1s 退避重用同一 req 流）之所以有效，正是因为它**串行化**了查询：一次只发一笔、等响应收完再发下一笔。**在途查询闸门（上限 1 笔、再发返回 -2）不是 CTPBuddy 的人为限制，而是对真实 API 行为的复刻**（DESIGN §8.8、M1 落地项）。

### A3. CTP 后台处的五类流控

| # | 流控 | 机制 | 超限表现 |
|---|---|---|---|
| **01** | **请求数流控** | 官方文档提到的 **FTD 报文流控**，针对**单个 session 的所有请求**。如配置为 6，则可以理解为**用户仅能调用 6 次 API 请求指令**，包括登录、查询、报单撤单等 | **不会调用错误信息或错误返回**。超过 FTD 报文流控，则**超过的指令会被缓存到前置，直到下一秒发出**。例：1 秒内报单 10 笔，则前 6 笔立即发送，剩余 4 笔缓存在前置，到下一秒才发出。**这对用户体验就是后 4 笔报单延迟很大，实际是受到了流控** |
| **02** | **报撤单流控** | 后台对报单（`ReqOrderInsert`）、撤单（`ReqOrderAction`）**每秒钟允许的最大笔数，这两个函数流控是分开计算的** | 触发则在**相应的错误回调函数中**返回 **"CTP:下单频率限制"**。该流控是**按投资者 `InvestorID` 级别**的，**所以多开 session 也没法**。策略需高频则**只能分账户**解决 |
| **03** | **查询流控** | 除在动态库端流控外，CTP 后台也流控（为防止用户用特殊手段不停查询后台） | 回调 `OnRspError`，提示 **"CTP: 查询未就绪，请稍后重试"** |
| **04** | **前置连接数流控** | CTP 中**每秒允许的最大 API 连接请求数**。如配置 20，则 1 秒内最多有 20 个 session 建立与 CTP 的连接 | 超过则**被动断开连接，回调 `OnFrontDisconnected`**。因此用户如果发现自己的程序**一连接前置就被断开**，则除了版本问题外，**有可能是遇到了连接数流控**。该流控是**设到不同的前置的（也就是说不同的 IP 地址）**，如 simnow 有 3 套地址，如果某套前置触发流控，可换一套 |
| **05** | **同一用户最大允许在线会话数** | 同一个用户（`UserID`）在 CTP 同时登录在线的最大允许会话数。**登录成功在线即算 1 个会话**，用其他客户端登录在线也计算在内 | 触发则会在 `OnRspUserLogin` 回调中返回 **"CTP:用户在线会话超出上限"** 的错误 |

> **CTPBuddy 落点（逐条对照）**：
> - **02 报撤单流控** = M2-4 已实现的 `order_gate`（每 (broker, investor) 每秒预算，超限 116「CTP:下单频率限制」）。**本册确认了 CTP 官方文案就是"CTP:下单频率限制"，且明确"insert+cancel 分开计算"**——CTPBuddy 已按 `GateStream::Insert/Cancel` 拆成两条独立预算流，e2e `m2_flow` 已锁定混做报撤不互相挤占。
> - **03 查询流控** = 90 号错误「CTP:查询未就绪，请稍后重试」，M1 已落地（`--qry-freq`）。本册确认了文案与"回 `OnRspError`"的推送面。
> - **04 前置连接数流控** = 知识库 §10.3 待办「前置连接数流控」。本册补充：超限表现是**被动断开 + `OnFrontDisconnected`**，且按 IP 分别配置。⚠️ 这条与 §1 自动重连有交互——**若因连接数流控被踢，重连会立刻再被踢**，需退避。
> - **05 同一用户最大在线会话数** = 知识库 §10.3 待办「同用户最大在线会话数」。本册确认错误文案「CTP:用户在线会话超出上限」，且**按 `UserID` 计**（注意不是 `InvestorID`），"登录成功在线即算 1 个会话"。
> - **01 FTD 报文流控** = 知识库 §10.3 待办「FTD 报文流控（无错误仅延迟缓存）」。本册补充精确机理：**超限指令被缓存到前置、下一秒才发出**，所以表现为"延迟很大"而非报错。

## B. 持仓查询（S12 上）

### B1. 请求与"什么都能不填"

```python
def ReqQryInvestorPosition(self, pQryInvestorPosition: 'CThostFtdcQryInvestorPositionField', nRequestID: int)
```

> **这个查询的参数是可以什么都不填的，如果什么都不填去查询则返回的是当前账户的所有持仓记录。**
> 但是要注意**什么都不填不是说参数直接写个 NULL 或 None 就行**，具体参考下面的示例。

选填字段只有 `InstrumentID`（只想查某个合约的持仓就填它）。

### B2. 持仓记录键值（**6 个字段**，全新）

开头 6 个字段称"持仓记录键值（Key）"，通过这 6 个字段就可以**区分唯一一条持仓记录**：

| 字段 | 说明 |
|---|---|
| `InstrumentID` | 合约 ID，**例如通过这个字段可以区分究竟是 au2012 的持仓还是 ag2012 的持仓记录** |
| `ExchangeID` | 交易所代码 |
| `BrokerID` | 经纪公司代码 |
| `InvestorID` | 投资者代码 |
| `PosiDirection` | **持仓多空方向**：`'2'` 表示多头持仓，`'3'` 表示空头持仓。**可见同一合约的不同方向的持仓在 CTP 是通过不同的记录返回的** |
| `HedgeFlag` | 投保套保标志，多数投资者是 `'1'`，表示投机 |
| `PositionDate` | **区分是否历史仓的枚举值**：`'1'` 表示当前交易日持仓，`'2'` 表示历史仓（昨仓） |

> ⚠️ 原文写"开头 **6** 个字段"，但实际列举了 **7** 个。以列举为准（Key = 7 字段）。

**`PositionDate` 的精确定义（重要）**：

> **只有上期/能源交易所的合约才可能有 `PositionDate` 为 '2' 的持仓记录**，因为上期/能源区分今仓和昨仓记录，**昨仓平仓需要单独指定平今仓**。

**但对个人投资者关键值字段为合约、方向、持仓日期这 3 个**，有这 3 个基本就能确定唯一一条持仓。

> **CTPBuddy 落点（重要）**：
> - CTPBuddy 现有持仓键 = `(Investor, Instrument, Direction, HedgeFlag)`。**缺 `PositionDate`（今/昨）与 `ExchangeID`**。对**上期/能源中心**，`PositionDate='2'` 的昨仓应当是**独立一条记录**（原文 S12 §持仓数量 明确"对非上期/能源交易所的合约，昨仓 `YdPosition` 和今仓 `TodayPosition` 在一条记录里面，而上期/能源是分成了两条记录"）。**CTPBuddy 是否对上期所/能源把今昨仓拆成两行持仓记录，须核对**——这直接影响 `ReqQryInvestorPosition` 的返回行数（客户端按行数统计持仓会错）。
> - 另：M3-4 记忆里的 `PositionDetail` 键是 `(OpenDate, TradeID, OpenPrice, ...)`，而 S15 给的键是 8 字段（见 §D），**两者需要对齐**。

### B3. 持仓数量字段

| 字段 | 说明 |
|---|---|
| `Position` | **当前键值下的总持仓**，随着客户开仓平仓而变动 |
| `TodayPosition` | **当前键值下的今日新持仓数量**，随着客户开仓平今而变动 |
| `YdPosition` | 当前键值下的昨仓，**需要注意**：① 这是一个**静态值**，为**当前交易日开始时**客户该合约的历史仓位，**并不会随着客户平昨仓而减少**；② **当前真实的昨仓值为 `Position − TodayPosition`**；③ **对非上期/能源交易所的合约，合约的昨仓 `YdPosition` 和今仓 `TodayPosition` 在一条记录里面，而上期/能源是分成了两条记录** |

> **CTPBuddy 落点**：`YdPosition` 是**交易日起始的静态昨仓初值**，不随平昨减少——这与 CTPBuddy 知识库 §6.2 记的 `YdPosition = Position − TodayPosition` **不矛盾但需分清**：`Position − TodayPosition` 是**当前真实昨仓**，而查询返回的 `YdPosition` 字段是**昨仓初值**（静态）。**CTPBuddy 目前只实现了前者，缺 `YdPosition` 字段**。S13 §二 的算例也印证："au2012 卖平报单 1 手成交，此时**持仓 `YdPosition` 仍然为 1**，因为这表示的是静态的昨仓初值。"

### B4. 常见问题（S12 §三）

1. **没有开仓均价字段，可以自己计算**。公式为 `开仓均价 = 开仓成本 / 持仓手数`；
2. 没有持仓均价字段，同样自己计算。公式为 `持仓均价 = 持仓成本 / 持仓手数`；
3. 如果相应键值上当天开仓并全部平仓，或者只是报单未成交，依然可以查到相应的持仓数据，其中 **`position` 字段为 0**，其他字段有相应的值；
4. 如果客户有多条持仓记录的话，API 会**多次回调**该函数，**每次返回一条持仓记录**，根据 `bIsLast` 判断是否是最后一条；
5. **如果查询时客户没有任何持仓记录，API 也会回调该函数，只是 `pInvestorPosition` 指针为空，`bIsLast` 字段为 `true`**；
6. 有时候客户自己**没有报组合却在查询中得到组合持仓的记录**（最后一条）。这是因为**按交易所的规则，盘后会自动将客户的相同持仓进行组合**（组合规则有好几种），组合后**只会收大单边的保证金**，**减少客户保证金占用**，所以就多出来这条组合记录。**组合包含记录会有对应的单边持仓记录**。

> **⚠️ CTPBuddy 落点（第 5 条重要）**：**无持仓时回空指针 + `bIsLast=true`，而不是回一条空记录**。这是"空流"的具体形状。DESIGN/M1 的查询语义是"必填项缺失 = 空流而非错误"，但**"查询成功但无数据"的回法**（空指针 vs 空记录）是另一个层面，须核对 CTPBuddy 的实现是否回了一条全零记录。**回全零记录会让客户端把 `Position=0` 的一行当成真实持仓**。
>
> 第 6 条同时从**另一个来源**印证了 §notes/11（04 分册 C4）记录的保证金优惠：交易所盘后自动组合、组合只收大单边保证金——与真实结算单实测的 `保证金占用 = max(多, 空)` 互为印证。

## C. 持仓更新（S13 下）

### C1. 报单请求：冻结规则（与 notes/04 附表互为印证）

> 报单请求主要与**持仓记录里面所有带"冻结"字**的字段有关。
> 如果是**当前交易日内在相应合约方向上的新开仓报单**，则**首先需要建一条新的持仓记录**（键值如上所述）。如果是**再次开仓在之前已有的持仓记录上更新**。

| 报单方向 | 更新哪条持仓 | 冻结字段 |
|---|---|---|
| **买开仓报单** | **多头**对应的持仓记录 | 增加多头冻结 `LongFrozen`、多头冻结金额 `LongFrozenAmount`、冻结的保证金 `FrozenMargin`、冻结的手续费 `FrozenCommission` |
| **买平仓报单** | **空头**对应的持仓记录 | 增加**多头**冻结 `LongFrozen`、多头冻结金额 `LongFrozenAmount`、冻结的手续费 `FrozenCommission`，**因为是平仓操作所以没有冻结的保证金** |
| 卖开 / 卖平 | 类似 | — |

> 算例（au2012 无多头持仓，初始所有字段为 0，以 398.76 买开报单 1 手）：键值只展示关键的**合约、方向及持仓日期**；报单 1 手则多头冻结 `LongFrozen` 增加 1 手，`LongFrozenAmount` 增加 `报单价格 × 手数 × 合约乘数`，`FrozenMargin` =（价合约 × 乘数 × 保证金率 × 手数 + 保证金的手续费率）× 手数（注：保证金率有**复本**）；`FrozenCommission` 计算方法与冻结保证金相似。
>
> 算例（au2012 持有多头持仓 1 手，以 408.22 卖平报单 1 手，更新本地空头持仓）：其中 **`YdPosition = Position` 为 1 表示现在有昨仓 1 手，`ShortFrozen` 更新为 1**，其他值应计算更新。
>
> **对于开仓来说相应的冻结资金字段比较重要**，因为这些冻结资金字段涉及到可用资金的计算，关系到客户后面能继续开仓的数量；
> **对于平仓来说冻结持仓字段比较重要**，因为冻结持仓数量涉及到**可平手数**的计算：
> - 多头持仓下可平数量 = 持仓数量 − 空头冻结数量；
> - 空头持仓下可平数量 = 持仓数量 − 多头冻结数量。
>
> 例：au2012 多头持仓 1 手，报卖平仓 1 手，此时可平数量 = `Position − ShortFrozen = 0`，也就是说在这手平仓单没结果之前，**不能再报平仓单了**，否则就可能被 CTP 以如下错误而拒绝：**"CTP:平仓量超过持仓量"**。

> **CTPBuddy 落点**：与 notes/04 附表（报单—撤单—成交 ledger 时序）**完全一致**，且本册给出了**算例与公式**。特别地"**买平仓冻结的是空头持仓记录的 `LongFrozen`**"这一点是易错点，CTPBuddy 已按此实现（知识库 §6.2「买平→空头持仓 LongFrozen+=报单量」）。

### C2. 报单回报（**账本时序的关键**）

报单回报分 `OnRtnOrder` 与 `OnRspOrderInsert` 两种，前者说明报单已被 CTP 接收，可以根据回报中的 `OrderStatus` 字段判断报单具体状态。

`OrderStatus` 取值：

| 常量 | 含义 | 处理 |
|---|---|---|
| `'0'` `THOST_FTDC_OST_AllTraded` | 全部成交 | 用 `VolumeTotalOriginal`、`VolumeTraded` 及 `VolumeTotal` 能计算出这报单中已成交量等用于更新持仓记录。**但是按照 CTP 官方文档推荐，这里还是建议客户根据成交回报来更新成交数量及持仓** |
| `'1'` `THOST_FTDC_OST_PartTradedQueueing` | 部分成交，还在队列中 | 同上 |
| `'3'` `THOST_FTDC_OST_NotTradQueueing` | 未成交还在队列中 | 同上 |
| `'5'` `THOST_FTDC_OST_Canceled` | 撤单 | — |
| `'a'` `THOST_FTDC_OST_Unknown` | 未知 | 同上 |

各状态处理（原文）：

- **a.** `'0'` 和 `'1'` 状态**配合**报单回报中其他相应的字段能计算这报单中已成交量等用于更新持仓记录，**但是按照 CTP 官方文档推荐，这里还是建议客户根据成交回报来更新成交数量及持仓**；
- **b.** `'a'` 和 `'3'` 字**段分别表示订单已经到达 CTP 及交易所，此时无需更新持仓记录**；
- **c.** `'5'` 表示该笔订单已经被撤单（**可能是主动撤单也可能是被动撤单**），**此时这笔订单应当被关闭，不会有新的回报**。所以**应该需要在报单进行仓位和资金冻结**（此处原文语义为"解冻"，见下条注），**恢复原来的状态**。

> ⚠️ 原文 c 条有笔误，读作"所以应该需要在**报单进行仓位和资金冻结**"应为"**撤销**（解冻）"。结合 §C.4 的总结可确认正确语义。

> 如：买开报单 1 手 au2012 没成交后撤单（平仓撤单类似）。
> **如如果收到 `OnRspOrderInsert` 回报说明报单没通过 CTP 的验证，已被拒单，此时参照上述 `'5'` 状态进行相应的解冻即可。**

### C3. 撤单回报

> 根据《CTP 程序化交易入门系列之八：撤单》中介绍可知如果撤单成功，**正确回报就是上面所述的报单回报，报单状态为 `'5'`，需要做相应的仓位或资金解冻**。
> 如果是**错误回报**说明撤单没有成功，**则不需要任何操作**。

> **CTPBuddy 落点（账本时序的权威依据）**：
> - **撤单回报不做仓位变动**，只做**解冻**（`VolumeTotal` 减、保证金/手续费解冻）。
> - **只有成交回报才动持仓**（`'0'`/`'1'` 也要按 S10 §E5 的建议以成交回报为准）。
> - `OnRspOrderInsert`（报单被 CTP 拒）**也要做解冻**——与 M2-4 记忆里"报单错误 → 按报单量解冻"一致。
> - `'a'`/`'3'` 不更新持仓记录。

### C4. 成交回报

> 客户收到成交回报说明对应的报单已经成交了，**这时首先需要对记录中原来报单时对应的仓位冻结或资金冻结进行减掉解冻**，然后**再计算**相应的**实际仓位及资金情况**。

| 情形 | 持仓更新 |
|---|---|
| **买开 1 手成交** | 更新所有冻结字段及持仓字段外，也应更新对应记录里的其他一些字段 |
| **卖平 1 手成交** | **此时 `YdPosition` 仍然为 1**，因为这表示的是静态的昨仓初值。除此之外还需要更新一些字段 |
| **全部平仓** | **平仓需要更新的更加复杂些**，不止要更新相应的平仓字段，还要更新对应开仓引起的持仓成本、持仓盈亏、保证金占用等。**这个用例是全部平仓，所以持仓成本等直接更新为 0**。部分平仓情况如何更新请读者自行测试验证 |

> **CTPBuddy 落点**：与 M3-4 的 `on_fill` 流程一致（先按 `est.margin * frac` 释放冻结，再动持仓、盈亏、保证金）。本条确认了**"先解冻、再算实际"**的顺序。

## D. 持仓明细查询与更新（S15，M3-4 的正面印证）

> **持仓明细是每一笔开仓时根据成交回报形成的一条记录**，有对应的平仓时再找出原来的开仓记录而更新，**本篇将详细介绍持仓明细的查询与更新**。

### D1. 请求

```python
def ReqQryInvestorPositionDetail(self, pQryInvestorPositionDetail: 'CThostFtdcQryInvestorPositionDetailField', nRequestID: int)
```

> **这个查询的参数是可以什么都不填的，如果什么都不填去查询则返回的是当前账户的所有持仓明细记录。**

选填 `InstrumentID`（只查某合约的明细就填它）。

> **CTPBuddy 落点**：M3-4 新增的 `ReqQryInvestorPositionDetail`（0x1059/0x105A）"可全不填"语义**正确**，本文印证。

### D2. 持仓明细记录键值（**8 个字段**）

| # | 字段 | 说明 |
|---|---|---|
| 1 | `InstrumentID` | 合约代码 |
| 2 | `BrokerID` | 经纪公司代码 |
| 3 | `InvestorID` | 投资者代码 |
| 4 | `HedgeFlag` | 投机套保标志 |
| 5 | `Direction` | 买卖 |
| 6 | **`TradeType`** | 成交类型。**枚举值**，常见有 `'0'` 表示普通成交，`'4'` 表示组合单生成成交。**一般投资者的成交类型都是 `'0'`，交易组合单或者大商所盘后自动组合的持仓的持仓明细为 `'4'`** |
| 7 | **`OpenDate`** | 开仓日期，**是实际成交开仓时的日期** |
| 8 | **`TradeID`** | 成交编号 |

> "通常我们采用这个 **8 个字段**来作为持仓明细记录的键值（用于定位区分唯一一条持仓明细），这个字段中大部分之前都解释过（见《系列之十二：持仓的查询与更新》），这里着重介绍一下陌生字段"。

> ⚠️ 但原文随后又说："因为 `TradeID` 是交易所对每一笔成交的唯一编号，但**每个交易日可能会重复编号**，所以我们也可以**直接使用其中的 `OpenDate + TradeID` 这两个字段作为键值**（如果交易系统可能出现自成交的话还需要加上 `Direction` 字段，详见《量化风控系列之一：自成交》）。"

> **⚠️ CTPBuddy 落点（重要，TradeID 复用）**：
> - **`TradeID` 每个交易日可能重复编号**——真实柜台如此。而 S10 §E1 说成交回报的 `(ExchangeID, TradeID, Direction)` 可定位唯一一笔成交。二者不矛盾：**成交回报是一次性的（当日内存活），持仓明细是跨日持久化的**，所以明细必须用 `OpenDate + TradeID`。
> - CTPBuddy M3-4 的 `PositionDetail` 主键是 `(OpenDate, TradeID, Direction, ...)`（记忆：`PositionDetail` = `(OpenDate, TradeID, OpenPrice, Volume, Margin, open_volume, last_settlement_price, close_profit, close_amount)`），**已含 `Direction`**，与本文"出现自成交时需加 Direction"一致，**正确**。
> - 但 `TradeType`（`'0'` 普通 / `'4'` 组合单生成）**CTPBuddy 未建模**。按 S12 §三第 6 条，大商所盘后会把相同持仓自动组合、组合只收大单边保证金——这意味着**真实柜台的持仓明细里会出现 `TradeType='4'` 的组合生成记录**。CTPBuddy 若不生成这类记录，则**明细行数会少于真实柜台**。这是 §A 保证金优惠之外的**第二个关联缺口**。
> - 另注：组合单生成成交意味着**CFFEX/郑商所的备兑组合**等场景下明细会由交易所生成，**不是客户开仓形成的**——与"每笔开仓成交一条"的直觉有例外。

### D3. 数量

| 字段 | 说明 |
|---|---|
| `Volume` | 指这笔**开仓**目前对应的持仓数量 |
| `CloseVolume` | 指这笔开仓目前**已经平仓**的数量 |

两个值都是实时更新：例如一笔开仓成交 8 手，开始时 `Volume=8`、`CloseVolume=0`；假如又平仓 3 手，则此时 `Volume=5`、`CloseVolume=3`。

> **CTPBuddy 落点**：`CloseVolume` 是**独立于 `Volume` 的另一列**。CTPBuddy 的 `PositionDetail` 用 `open_volume` + `volume` 两个量表达（记忆：`Volume` 与 `open_volume`），语义等价但字段名不同——**查询返回时须确认映射到官方字段 `Volume` / `CloseVolume` 的对应**，避免把两个量填反（`m3_detail.py` 有逐笔断言，改动时须复查）。

### D4. 开仓价与盈亏（**官方口径印证 M3-4**）

| 字段 | 说明 |
|---|---|
| `OpenPrice` | 开仓价，**该笔开仓成交时的价格** |
| `CloseProfitByDate` | **逐日盯市盈亏**，昨日平仓盈亏，**昨仓是平仓均价与昨结算价计算出的盈亏**，**平仓价计算出的盈亏，计算公式为 `(closeprice − openprice or preSettlementPrice) × volume × RateMultiple`** |
| `CloseProfitByTrade` | **逐笔平仓盈亏**，**无论今仓昨仓都是通过平仓价与开仓价之差计算得到** |
| `PositionProfitByDate` | 逐日持仓盈亏 |
| `PositionProfitByTrade` | 逐笔持仓盈亏，**与平仓盈亏计算逻辑一样，只是用最新价计算** |

> **⚠️ CTPBuddy 落点（官方背书，M3-4 核心强化）**：公式里的 **`openprice or preSettlementPrice`（"或"字）是关键**——官方明确昨仓用**昨结算价**、今仓用**开仓价**。这与 CTPBuddy M3-4 在真实结算单驱动下强化的口径**完全一致**（记忆：IH2501 买 1 手昨仓平于 2616.4 → 按昨结算 2607.2 得 −2760.00，按开仓价会得 −2940）。
>
> **本文是 CTPBuddy 该设计的第一手官方依据**（此前该结论仅来自 P1《账户持仓和资金的维护》与真实结算单）。**知识库 §6.5 / notes/04 E2 应补上这条出处**。
>
> 另注意 `PositionProfitByDate` 与 `PositionProfitByTrade` **两列并存**（逐日 vs 逐笔），CTPBuddy 真实数据对账验证的正是"逐笔之和 = 汇总"（IH2501 4 笔 2520+5700+5640+3300=17160.00）——**对应 `PositionProfitByTrade` 口径**。DESIGN 可考虑在明细查询中一并返回这两列以对齐官方形状（当前只有一列）。
